第 02 章

Context 与 Service

第 1 章的 miniLoop(deps) 把 model、tools、log 当参数传进去。 参数在函数被调用的那一刻就冻住了。你没法在运行时把 fs 从本地实现换成沙箱实现， 也没法让两个会话同时各用一份自己的 fs。本章把名字变成第一公民： 能力登记在一张表上，谁要用就报名字。

§2.1参数传递到不了的地方

先把痛点说具体。第 1 章的循环需要一个文件系统能力，于是它出现在 deps 里：

ch01 的做法：能力从最外层一路传进去
const fs    = createLocalFs('/repo');
const tools = createTools({ fs });                 // 每个工具都需要 fs
const deps  = { model, tools, inbox, log, history, signal };

await miniLoop(deps);

现在提三个真实需求。

第一个：会话 A 用本地 fs，会话 B 用沙箱 fs，同一个进程里同时跑。 这个靠加参数还能扛。createTools({ fs }) 多一个入参，miniLoop 多一个入参， 每个调用点跟着改一遍，丑，但能用。

第二个：用户在会话跑到一半的时候打开了沙箱开关，fs 必须当场换掉。 到这里就扛不住了。deps 在进入循环时已经被读进闭包，换掉外面那个变量，循环里的人毫无感觉。

第三个：一个第三方插件想接管 fs。它不在你的代码里，改不了 createTools 的签名。 无解。参数列表是你的私有约定，外人拿不到那个位置。

问题的根不在参数太多，在于调用方必须知道被调用方需要什么。 把这层知识翻过来，让需求方自己按名字去要，链条就断开了：

依赖注入的做法：只约定名字
// 提供方：把一份实现登记到名字 "fs" 上，谁提供的、什么时候提供的，消费方都不需要知道
ctx.provide('fs', createLocalFs('/repo'));

// 消费方：声明"我需要 fs"，然后直接读 ctx.fs
ctx.plugin({
  name: 'reader',
  inject: ['fs'],
  apply(ctx) { ctx.fs.read('README.md'); },
});

这段代码换来的不只是"解耦"两个字。参数传递做不到的事，它一次给了四件：

能力参数传递服务注册表
晚绑定：provider 可以比 consumer 后出现不行，调用时必须齐可以，consumer 排队等
热替换：运行时换掉一份实现不行，闭包已冻结可以，consumer 重跑
撤销：provider 消失时依赖它的人一起停没有这个概念有，注册是有生命周期的
同名多份：两个会话两份 fs只能靠两套参数靠 isolate realm

§2.2Context 是一个 Proxy

ctx.fs 这个写法有点反常。它看起来是读一个普通属性，可 fs 是运行时才被登记进来的， 而且不同的 ctx 读同一个名字可能拿到不同的东西。普通属性做不到这个。 真实实现直接把整个 Context 包成了 Proxy，而且是在构造函数里包的，返回的不是 this：

vendor/cordis/src/context.ts · 构造函数（节选）
constructor() {
  this[symbols.isolate] = Object.create(null)
  this[symbols.intercept] = Object.create(null)
  const self = new Proxy<this>(this, ReflectService.handler)   // ← 关键这一行
  this.root = self
  this.fiber = new Fiber(self, {}, Object.create(null), null, () => [])
  this.reflect = new ReflectService(self)
  this.registry = new RegistryService(self)
  this.events = new EventsService(self)
  this.logger = new LoggerService(self)
  return self                                                  // ← 你拿到的永远是 Proxy
}

所有子 context 都是这个 Proxy 的原型后代。ctx.extend(meta) 做的是 Object.create(proxy)，然后把 meta 定义成自有属性。 Proxy 当原型用的时候，后代对象上找不到的属性读取依然会触发 Proxy 的 get trap， 而且 receiver 是那个后代对象。一份 trap 代码因此同时服务于成千上万个子 context， 每次都知道是谁在读。

trap 里的分派规则是这样的：

ctx.fs │ ├─ prop 是 symbol / "then" / "prototype" / 数字串 / _开头 ──► Reflect.get，当普通属性 ├─ target 上本来就有这个属性（root / fiber / reflect ...）──► Reflect.get，当普通属性 │ └─ 否则进入服务解析 ├─ 插件 ctx (fiber.runtime != null) │ ├─ inject 里声明过 ──► fiber.store["fs"].value ← 激活那一刻冻结的那份实现 │ └─ 没声明过 ──► throw cannot get property "fs" without inject │ └─ 根 ctx (fiber.runtime == null) └─ reflect.store[ ctx[isolate].fs ]?.value ← 查不到就是 undefined

把 then 排除掉不是洁癖：如果 ctx.then 被当成服务解析， 任何人 await ctx 都会炸。真实实现里这条规则叫 isSpecialProperty， 拒绝 symbol、prototype、then、纯数字字符串和下划线前缀。

另一半机制在存储层。服务表按隔离符号存，名字只用来查符号：

vendor/cordis/src/reflect.ts · ReflectService.provide 的核心（节选）
// 名字的"根 realm 符号"，只铸一次
this.ctx.root[symbols.isolate][name] ??= Symbol(name)
// 当前 ctx 所在 realm 的符号，两者可以不同
const key = this.ctx[symbols.isolate][name]
const impl: Impl = { name, value, fiber: this.ctx.fiber, check }
if (this.store[key]) {
  throw new Error(`service "${name}" has been registered at <${this.store[key].fiber.name}>`)
}
this.store[key] = impl
this.ctx.fiber.store![name] = impl

store 的类型是 Dict<Impl, symbol>，键是 symbol。 一个名字对应几个 symbol，就能同时存在几份实现，§2.5 全靠这一点。 Impl 里还记了 fiber，也就是说谁登记的，这份实现的寿命就跟谁一样长。

§2.3Service 是自注册的

上面用的是裸的 ctx.provide(name, value)。真实的 dsh 服务几乎不这么写， 它们继承 Service，注册动作藏在 super() 里：

vendor/cordis/src/service.ts · 构造函数（节选）
constructor(protected ctx: Context, name: string) {
  name ??= this.constructor['provide'] as string
  let self = this
  const tracker: Tracker = { associate: name, property: 'ctx' }
  if (self[symbols.invoke]) {
    // 带 invoke 体的服务会变成可调用对象，比如 ctx.logger('agent')
    const proto = joinPrototype(Object.getPrototypeOf(this), Function.prototype)
    self = createCallable(name, proto, tracker)
  }
  self.ctx = ctx
  self.name = name
  defineProperty(self, symbols.tracker, tracker)

  self.ctx.reflect.provide(name, self, this[symbols.check])    // ← 注册就是这一行
  return self
}

一个真实的例子，dsh 的工具运行时：

packages/core/tools/src/index.ts:787 · ToolRuntime（节选）
export class ToolRuntime extends Service {
  static inject = ['systemPrompt']

  constructor(ctx: Context, config: Config = {}) {
    super(ctx, 'tools')                                    // 从这一行起，ctx.tools 就是它
    this.defaultMode = config.mode ?? 'native'
    this.maxParallelSubCalls = resolveMaxParallelSubCalls(config.maxParallelSubCalls)
    ctx.systemPrompt.tools(context => this.wireSchemas(context.scope))   // 直接用，不判空
    ...
  }
}

这几行里有三个点。

第一，类本身就是插件。没有 register()，没有 init()， ctx.plugin(ToolRuntime) 就是挂载，构造完成即可用。

第二，static inject = ['systemPrompt'] 是构造函数敢直接写 ctx.systemPrompt.tools(...) 的全部理由。它不判空、不 try、不轮询， 因为 inject 已经保证了这个类根本不会在 systemPrompt 缺席时被构造。 依赖注入最实际的收益就在这儿：删掉防御性代码。

第三，注册的所有权属于挂载它的 fiber。provide 整个包在 this.ctx.fiber.effect(...) 里，fiber 卸载时 disposer 反序执行， ctx.tools 自动从 store 里消失，依赖它的插件跟着停。没有人需要手写 unregister()。

顺着"注册"这条线，有件事放在这里说正好。dsh 的多 provider 适配器 packages/llm/llm-pi-ai 依赖 @earendil-works/pi-ai@^0.82.1， 也就是 Pi 的模型层。极繁的这个 harness 直接拿极简那个 harness 的模型库来用。 而它接进来的方式，就是本节讲的这一套：export const inject = ['llm']， 然后在 apply() 里 ctx.llm.registerAdapter(routes, adapter)。 pi-ai 本身是一个被 import 进来的普通库， 它能在运行时被换掉，靠的是外面这层十几行的插件壳。

我们的 Service 只留骨架，而骨架就是它的全部意思：

顺序陷阱 super(ctx, name) 在子类字段赋值之前执行，也就是说服务被登记进 store 的那一刻， 它自己的字段还没初始化完。真实 cordis 为此留了 Service[Service.init]： 一个构造完成后才跑的实例方法。同步的消费方读不到半成品，是因为 provide 的通知发生在同一个同步块里，而 consumer 的 apply 会等到它自己被激活时才执行。

§2.4inject：加载顺序从依赖里长出来

现在回答一个很多插件系统答错的问题。consumer 先挂载，provider 后挂载，怎么办？

错答案有几种。按配置文件顺序加载，那等于手写启动序列。让 consumer 自己轮询等待， 那每个插件都得写一遍等待逻辑。报错、要求用户排好顺序，这个最省事， 代价是"第三方插件接管 fs"永远做不到。

Cordis 的做法是让 consumer 挂载后停在 PENDING，apply 一次都不跑。 provider 出现时，reflect.notify(['fs']) 扫一遍所有 fiber， 把 inject 了 fs 的那些重新算一次依赖状态，够条件的当场激活。 判断依赖状态变没变，用的是一个字符串，叫 epoch：

vendor/cordis/src/fiber.ts:611 · _refresh 的 epoch 计算（节选）
_refresh() {
  let epoch: string | boolean = false
  epoch = ''
  for (const name of Object.keys(this.inject)) {
    const impl = this._store[name]
    if (!impl) {
      epoch = INACTIVE        // 少一个依赖 -> 整体不可用
      break
    }
    epoch += ':' + impl.fiber.uid     // 拼的是"提供方 fiber 的身份"，不是服务的值
  }
  ...
}

拼的是 impl.fiber.uid，不是服务的值。这一个选择决定了四种行为：

  • 依赖齐了，epoch 从 INACTIVE 变成字符串，加载。
  • 依赖没了，epoch 变回 INACTIVE，卸载，而且是级联的。
  • 依赖换人了。名字没变，值可能长得一样，可 uid 变了，epoch 也就变了，先卸载再加载。
  • 依赖没动，epoch 相同，什么都不做。热重载时这一条最要紧，它避免了无谓的重启风暴。

第三条是"运行时换 provider"能成立的全部原因。它也带来一个必须接受的后果： 一个插件的 apply 可能被执行多次，所以它做的每件事都必须可撤销。 第 3 章的 ctx.effect() 就是为这个而生的。

Demo 2.2inject 驱动激活：consumer 先挂，provider 后到

"运行"是四幕：consumer 先挂着不动；本地 provider 到场，consumer 自动激活； provider 换成沙箱实现，consumer 卸载后再次激活；provider 全部撤走，consumer 掉回 pending。 全程没有一行代码在协调加载顺序，inject: ['fs'] 就是全部的协调。 旁边那个按钮把这一行删掉，你会看到它买的到底是什么。

§2.5isolate realm：同一个名字，两份实现

最后一个问题最有 harness 特色。ctx.fs 这个名字是全局约定， 所有工具、所有插件都写 ctx.fs.read(...)。 可两个会话可能需要两份完全不同的 fs，一个在 /work/session-1，一个在沙箱里。 名字不能改，改了工具全废。实现必须不同。

按名字存的表办不到这件事。按 symbol 存的表可以：

vendor/cordis/src/context.ts:121 · isolate
isolate(name: string, label?: symbol) {
  const shadow = Object.create(this[symbols.isolate])   // 原型链继承父 ctx 的 realm 映射
  shadow[name] = label ?? Symbol(name)                  // 只改一个名字的去向
  return this.extend({ [symbols.isolate]: shadow })
}

isolate 映射本身是一条原型链：子 ctx 只覆盖它关心的那个名字，其余全部沿用父 ctx 的符号。 所以"给会话一份自己的 fs"这件事的代价，是一个新 symbol 加一个新对象。

root[isolate] = { fs: Symbol(fs) } ← provide 无条件铸的根符号 ├─ s1[isolate] ─proto─► { fs: Symbol(fs) } s1 自己的符号 └─ s2[isolate] ─proto─► { fs: Symbol(fs) } s2 自己的符号 reflect.store = { [ s1 的符号 ]: { name: "fs", value: LocalFs("/work/session-1"), fiber: <fs@s1> }, [ s2 的符号 ]: { name: "fs", value: LocalFs("/work/session-2"), fiber: <fs@s2> }, [ 根 符 号 ]: 不存在 ← 根 realm 解析不出 fs，所以两个会话永远撞不上 }

这里有个反直觉的细节。provide 会无条件地为名字铸出根 realm 符号 （this.ctx.root[symbols.isolate][name] ??= Symbol(name)）， 所以"名字在根 realm 里"这半句是真的。可根符号下面没有任何实现， 所以"根 realm 能解析出这个服务"这半句是假的。dsh 的测试专门把这两半都钉住了：

packages/boot/app-boot/tests/config-reload.spec.ts:417 · 原文注释与断言
// `provide` mints the root symbol unconditionally (cordis `reflect.ts`),
// so the name IS in the root realm — pinned here because it is the half
// that looks like the claim and is not. The claim is the other half: no
// implementation is stored under that symbol, so the root realm cannot
// resolve the service and a second composition mounting the same rows
// cannot collide with this one.
const rootKey = ctx.root[Context.isolate].demoRealmSvc
expect(rootKey).toBeDefined()
expect(ctx.reflect.store[rootKey!]).toBeUndefined()

在 YAML 组合层（第 7 章），realm 是一个配置字段。cordis:group 行可以给一组行 （一个 provider 加它的若干 consumer）分配同一个 realm：

packages/boot/app-boot/tests/config-reload.spec.ts:397 · 真实的 group 配置
- id: realm

这在 dsh 里不是可选项 agent preset 的 mount() 会主动拒绝三种结果，其中一种是"把服务发布到 root realm 的行"。原文： "Such a service is process-global, so the second preset publishing the same name collides with the first, and a host reader would resolve one preset's instance for every session." 这条规则不是启动时审计一次就完事： "The package invariant re-checks that last rule on every service notification"， 因为定时器或异步续延里的 provide 会绕过一次性审计。 出处 packages/preset/agent-presets/README.md 的 "What a mount rejects"。
换成别的 harness per-session 的服务实例，是"一个进程同时服务多个能力集不同的会话"的前提。 会话 A 的 ctx.fs 落在沙箱里，会话 B 的落在工作区，两边的工具代码一个字都不用改， 它们读的名字一样，realm 不一样。agent preset 的 README 把这层复用说得更直白：entry-local realm "keep two presets' same-named services apart exactly as they once kept two sessions' apart"。 OpenCode 的 client/server 拆分解决的是另一个方向。 Go 服务端持有执行生命周期，对外开 OpenAPI 3.1，于是 CLI、桌面、网页、脚本可以同时贴到同一个会话上。 那是多客户端对一个会话，这里是一个进程里多个组装方式不同的会话。

"运行"里两个会话各自 isolate('fs') 之后挂载自己的 LocalFs， 两个 consumer 各读到自己那份，末尾把根 realm 的两半事实都打出来。 "对照"按钮把两个 provider 都留在根 realm，第二个 fiber 以 failed 收场， 错误消息里带着先注册者的 fiber 名字。preset 审计要拦的就是这个。

§2.6本章的产物

三段东西：三个 Proxy trap、一个 root context、一个 Service 基类， 去掉注释一百五十行出头。它有 Proxy 反射、有按 symbol 隔离的 store、有 inject 驱动的激活、 有 epoch 比较，够我们把后面几章的东西挂上去了。

mini-dsh v0.2 · createHandler() + createRoot() + Service · 页面上三个 demo 跑的都是它

和第 1 章的 miniLoop(deps) 接上：deps 里的每一项现在都可以是一个服务。 miniLoop 自己也可以变成一个插件，声明 inject: ['model', 'tools', 'sessions']， 然后由运行时决定它什么时候开始跑。

下一章预告 这版有三个地方明显在硬撑。fiber.disposers 是我手搓的数组，插件自己往里塞东西要越过封装； refresh 是同步的，真实的加载必须异步（provider 的 apply 里可能有 await），一异步就有"过期加载"问题；state 我只用了 pending / active / failed / disposed 四个值，缺了 LOADING 和 UNLOADING 这两个"正在切换"的中间态。 第 3 章把这个 fiber 记录换成真正的状态机，并且引入 ctx.effect()： 每一次注册都返回 disposer，卸载时反序回收。 那一章还要正面接一条 HN 上的技术质疑，OutOfHere 的 "Using memory to track inverses does not scale."

§2.7回到真实的 dsh

本章对应的真实代码在 vendor/cordis/src/。 最该读的是 get trap 里那段循环，它比我们的版本多做了一件事：沿 fiber 链向上找， 并在 realm 边界处停下来。

vendor/cordis/src/reflect.ts:153 · get trap 的核心（原文）
return ctx.events.waterfall('internal/get', ctx, prop, error, () => {
  const key = target[symbols.isolate][prop]
  let fiber = (ctx[symbols.shadow] ?? ctx).fiber
  while (true) {
    const impl = fiber.store?.[prop]
    if (impl) return getTraceable(ctx, impl.value)
    if (prop in fiber.inject) {
      error.message = `cannot get required service "${prop}" in inactive context`
      throw error
    }
    if (!fiber.runtime) throw error
    if (fiber.parent[symbols.isolate][prop] !== key) throw error
    fiber = fiber.parent.fiber
  }
})

注意第一行：整个解析过程本身是一个 waterfall 事件（internal/get）。 也就是说"读一个服务"这件事是可拦截的扩展点，不只是一次查表。第 4 章会专门讲 waterfall。 还有一处容易漏掉的事实：ctx 上一半的方法根本不是 Context 类的成员， 而是 ReflectService 构造时 mixin 上去的：

vendor/cordis/src/reflect.ts:219 · ctx 的方法从哪来
this.mixin('reflect', ['get', 'set', 'provide', 'accessor', 'mixin'])
this.mixin('fiber', ['runtime', 'effect'])
this.mixin('registry', ['inject', 'plugin'])
this.mixin('events', ['on', 'once', 'parallel', 'emit', 'serial', 'bail', 'waterfall'])

所以 ctx.provide 其实是 ctx.reflect.provide， ctx.plugin 是 ctx.registry.plugin，ctx.on 是 ctx.events.on， ctx.effect 是 ctx.fiber.effect。每个 mixin 都是一个 accessor， 随 fiber 卸载而消失。

几个我们刻意省掉的真实细节：

  • getTraceable。服务从 store 里取出来时会被 getTraceable(ctx, impl.value) 包一层 Proxy，让服务内部读到的 this.ctx 是调用方的 context，而不是注册方的。 所以 ctx.reflect.provide() 从子 ctx 调用时会登记到子 ctx 的 realm： reflect.ctx 是动态的。实现在 vendor/cordis/src/utils.ts 的 createTraceable。
  • check 谓词。provide(name, value, check) 的第三个参数是一个可用性判断。 实现存在但 check() 返回 false，依赖方照样进不了 active（见 Fiber._checkImpl）。 Service 子类通过 this[Service.check] 提供它。
  • 卸载是异步且有序的。provide 的 disposer 先删 store、再 notify， 然后 await Promise.allSettled(fibers.map(fiber => fiber.await()))， 最后才删 fiber.store[name]。源码注释写着 "ensure self access before dependencies cleanup"，意思是依赖方在自己的清理代码里还能读到这个服务。 我们的 disposer 是同步的，没有这个保证。
  • intercept。ctx.intercept(name, config) 沿原型链累积 per-service 配置， Service[symbols.resolveConfig] 合并时祖先在前、head 优先级最高。 同一个服务可以被不同子树看到不同配置。
  • ctx.accessor() 与 props 表。除了 'service'， 一个名字还可以被声明成 'accessor'（带 get/set 钩子的计算属性），两种声明互斥， 抢同一个名字会抛 property "x" is already declared as ...。
  • Context.is() 用全局 symbol 做品牌（Symbol.for('cordis.is')）， 不用 instanceof，这样跨 realm、跨多份 cordis 拷贝都能认出 context。
