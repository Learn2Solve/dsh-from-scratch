第 03 章

Fiber 与 effect

第 2 章的 context 能注册服务，却没法干净地反注册一棵插件子树。它的 disposers 是一个手写的扁数组：谁拥有谁看不出来，插件加载到一半失败也没人回滚。 本章把那个 record 换成一台生命周期状态机，顺手把"注册"重新定义成"副作用"。

§3.1插件不是一次函数调用

第 2 章的 ctx.plugin({ name, inject, apply }) 干的事是：等依赖齐了，同步调一次 apply(ctx)，把 fiber 记录标成 'active'。错在最后半句。

apply 返回之后，它留下的东西还活着：provide 进去的服务、挂上去的事件监听器、 开着的 timer、mount 出来的子插件、写进注册表的工具和 prompt section。函数出栈了，这些没有。 运行时于是需要一个对象来代表"这个插件的这一次加载"，Cordis 管它叫 fiber。 同一份插件代码在两个 context 下各 mount 一次，就是两个 fiber。

fiber 的生命周期有六个状态，名字直接来自真实实现。ch02 的 record 只用到其中四个， 因为同步加载不需要"正在加载"和"正在卸载"这两个中间态。

依赖齐了 插件体跑完 PENDING ─────────► LOADING ─────────► ACTIVE ▲ │ │ │ │ 抛异常 │ 依赖消失 / 被 dispose │ ▼ ▼ │ ┌───────────────────────────┐ │ │ UNLOADING │ 反序回收整个 owner list │ └───────────────────────────┘ │ │ │ │ └──────────────────┘ │ └──────────► DISPOSED epoch 仍是 INACTIVE │ uid 已清空，终态 └──────────► FAILED error 还留在 fiber 上 其余的边全部由 epoch 驱动（§3.4）：UNLOADING ─► LOADING、FAILED ─► LOADING、任何状态 ─► UNLOADING
state含义谁在读它

状态是推导出来的

六个状态里只有 LOADING 和 UNLOADING 是显式赋值的，另外四个从三个字段推出来： uid 清空了没有、有没有留着 error、epoch 是不是 INACTIVE。 所有转换都走同一个 _updateState()，它顺手广播 internal/status， 并在跨越 ACTIVE 边界时通知依赖方。

§3.2注册即副作用

dsh 仓库的 AGENTS.md 把这件事写成了一条硬规则，原文一个字都不用改：

Registrations are effects: every contribution goes through ctx.effect() / ctx.on(); a registry's register() returns the disposer.

反面更好理解。一个不可逆的注册会让 unload 变成谎言：插件卸载了，它塞进 tools 表里的工具还在，模型下一次请求照样看得见、照样会调，而执行体所属的插件已经不存在了。 所以每一个"贡献"都得可回收，工具、prompt section、事件监听器、LLM provider、adapter、子插件， 一个都不例外。

换成别的 harness "注册必须交回一个 disposer"这条规则，在另外几个 harness 的文档里我没找到对应物。Claude Code 里一个 MCP server 是一个进程，你起它、你停它；停掉之后它的工具从工具表里消失，而它在那个进程之外碰过的东西不会跟着回来。 Pi 的 TypeScript extension 往内核里注册工具、命令和 hook，这个方向是单向的，回收发生在进程退出的时候。 对一个跑完一个任务就退出的 CLI 来说，这完全够用。dsh 把它收紧成一条不许绕开的规则：每个 contribution 都从 ctx.effect() 出去，插件卸载时按反序退回来。第 9 章里模型现场写一个插件、挂进正在跑的进程、 发现写坏了再回滚到上一个版本，能成立的全部理由就是这条规则。cordis_run 的 mode:"run" 敢拿来做 rollback，前提是上一个包留下的注册确实退干净了。
omp 是这条规则最硬的对照组 omp 的扩展跑在宿主进程里，写的是 TypeScript，会话跑着的时候还能改工具表。上面那段话最该拿它检验。 一个 omp 扩展是默认导出 (pi: ExtensionAPI) => void | Promise<void> 的模块，工具从 pi.registerTool(...) 进去；pi.setActiveTools(names) 在运行中换掉当前会话的活动工具集， AgentSession 那一侧对应 setActiveToolsByName(names)，换完系统提示会跟着重建。 「工具表能运行时增删」因此不归 dsh 独有。分歧在别处。ExtensionAPI 的一整排注册方法（on、registerTool、registerCommand、registerShortcut、 registerFlag、registerMessageRenderer、registerProvider）在文档里都不交回撤销句柄； 扩展加载是一次带 ?mtime cache-buster 的动态 import()，文档没有给它配一条卸载路径。 带撤销语义的只有托管定时器：ctx.setInterval 返回一个能传给 ctx.clearTimer 的 handle， 并在 session_shutdown 时自动清掉。至于逐条注册的 disposer，以及"贡献单元卸下来的时候自动反绕整棵子树"， omp 文档里未查到。这一格写的是未查到：extensions.md 和 extension-loading.md 没提这件事，实现里有没有我没去数。 留给 dsh 的那半边因此窄了一圈，剩下的是作者和寿命：运行时改工具表的不止一家；让模型自己写出那个 contribution、再把它连着注册一起退干净，目前只有第 9 章那条路。

ctx.effect(body, label) 的契约有四条，每一条都是被真实 bug 逼出来的：

  • body 立刻执行，它产出的 disposer 被收集起来。合法形状只有三种：返回一个函数、 返回一个 yield 出 disposer 的 generator、什么都不返回。别的形状直接 TypeError。
  • 卸载时反序执行这些 disposer，并且串行 await，后一个要等前一个结束。
  • 返回的 disposer 单次生效，重复调用返回同一个结果，不会跑两遍。
  • body 中途抛异常，已经收集到的 disposer 立刻回滚，异常继续往外抛。半初始化的插件不许留下痕迹。
mini-dsh v0.3 · effect 原语

注意 fiber.disposables.push(wrapper) 排在 driveEffect() 之前。 如果 body 自己触发了 owner 的卸载（body 里 await 到一个失败的启动、上层决定 restart， 都会走到这一步），那次卸载必须看得见这个还没跑完的 effect，否则它收集的 disposer 就逃出了本次卸载的快照。

反序保证到什么粒度

这里几乎所有人第一次都会搞错。反序只在一个 effect 内部是严格的；同一个 fiber 上的多个兄弟 effect，卸载是"反序发起、并发完成"。

范围发起顺序完成顺序
一个 effect 内部的多个 disposer反序反序（前一个 await 完才轮到后一个）
同一个 fiber 上的多个兄弟 effect反序不保证

源码里看得很清楚：fiber 卸载是 await Promise.all(this._disposables.clear().map(async dispose => …))， 而 DisposableList.clear() 返回的是 values.reverse()。 反转给了你发起顺序，Promise.all 拿走了完成顺序。所以官方 primer 那句话是有牙的：

If teardown order matters, keep the related work in one effect so disposal unwinds in the intended sequence.

读数字 注册 列是注册顺序，发起 列是 disposer 被调用的顺序，完成 列是它跑完的顺序。 两种挂法的发起列都是 5→1；但兄弟挂法的完成列里，异步的 watcher.stop() 第一个发起、最后一个完成， 中间四个从它身上跨了过去。composite 挂法两列完全对称，代价也在输出里：严格反序意味着卸载期间早注册的资源 还活着，所以 composite 那次 ctx.setInterval() 会在等 watcher 停下来的 140ms 里多跳一次心跳。有序不免费。
第三个按钮：忘记返回 disposer 它挂的插件里，工具注册走的是 ctx.tools.register()，监听器却直接 push 到了一个外部 emitter 上， effect body 什么都没 return。driveEffect 认这个形状（"什么都不返回"本来就是三种合法形状之一）， 所以没有任何报错。卸载之后工具确实还回去了，那个回调还在响。更难受的是 fiber.getEffects() 也空了： 运行时看不出哪里漏了，label 随 wrapper 一起没了。真实 dsh 里这类 bug 的长相通常是 process.on()、 全局 setInterval，或者某个第三方 SDK 的 client.subscribe()。

这套记账贵不贵

dsh 开源当天的 HN 主线程（item 49285244，2026-08-13）里，OutOfHere 用一句话概括了对这个模型的技术怀疑：

Using memory to track inverses does not scale.

这句话得拆成两半看，一半站不住，一半站得住。记账本身很便宜：每条活着的注册占一个 closure、一个 Map 表项、一个 WeakMap 表项，DisposableList 的文档注释写的是 "Ordered collection of disposable values with O(1) deletion by value"，push() 返回的 remover 就是一句 map.delete(sn)。开销跟活着的注册条数成正比，跟进程跑了多久无关。

站得住的是另一半。disposer 是强引用，它捕获了"撤销这件事需要的一切"，所以只要那条注册还挂在 owner list 上， 被它捕获的对象图就活着。dsh 给每个会话挂一棵自己的插件子树（第 7 章），并发会话数直接乘上去； 任何一个忘了卸载的 fiber，会把它整棵子树的 disposer 一起钉在内存里。再加上刚才那个按钮演示的事： 这套模型的正确性上限是最不小心的那个插件，运行时没有办法知道 body 里本该 return 什么。 省内存的替代方案就是 MCP 那条路，把扩展关进子进程、要回收就杀掉，代价是进程内热插拔没了。 omp 在这项记账上一分钱不花，因为它不记：账单挪到了 §3.5 那一格，一个游离回调里的抛出能把整个会话带走。 OutOfHere 给的理由不对，担心的方向对。

§3.3父子 fiber 与级联卸载

真实实现在 vendor/cordis/src/fiber.ts 第 265 行的构造函数里，形状一模一样。 多出来的是三件事：emitPluginDisposed() 通知一圈、最后一个 fiber 走了就把插件从 registry 里删掉、以及 while (this.inertia) await this.inertia 上面的一大段注释。那段注释解释了为什么 这里不 catch：inertia 本身不该 reject，真 reject 了就只剩 logger 自己坏掉这一种可能， 而"再调一次 logger"正是刚刚失败的动作，所以让它炸上去，"process-level crash is the honest outcome"。

精确的那个 disposer

既然子 fiber 就是父 fiber 上的一个 effect，fiber.dispose 这个函数对象的身份 就成了可用的资源：把它 yield 进一个 composite effect，"卸载这棵子树"就被钉在那个 yield 的反序位置上。包一层 wrapper 会丢掉这个位置，退回 fiber 层面的并发兄弟，也就是上面那张表的第二行。

这是 dsh 所有 registry 的 register() 都直接 return Cordis effect disposer 的原因。 仓库里有一条测试专门钉住它：

packages/core/tools/tests/tools.spec.ts:2024 · 精确 disposer 的回归测试（节选）
it('register() returns the EXACT effect disposer', async () => {
  const fiber = await ctx.plugin(Object.assign((inner: Context) => {
    inner.effect(function* () {
      yield () => { order.push('disposed-last') }
      yield inner.tools.register({ ...echoTool, name: 'nested' })
      order.push('registered')
      yield async () => {
        await new Promise(resolve => setTimeout(resolve, 0))
        order.push(inner.tools.get('nested') ? 'first: still registered' : 'first: already gone')
      }
    })
  }, { inject: ['tools'] }))

  expect(order).toEqual(['registered', 'first: still registered', 'disposed-last'])

第三个 yield 的异步探针在自己那一步里看到工具还注册着，因为工具的反注册排在它后面（反序里它更早）。 如果 register() 返回的是个 wrapper，反注册就脱离了这个顺序，探针会看到 already gone。

dsh-scope 的全部实现也是这一招：createScope() mount 一个空插件当背板 fiber， 把 fiber.ctx.extend({ [kScope]: key }) 交出去，再把那个精确的 fiber.dispose 作为 rawDispose 暴露出来（见 packages/core/scope/src/index.ts:137）。 一个 agent 的所有注册就挂在这么一个能整体回收的 fiber 上。

§3.4依赖驱动的重载

epoch 第 2 章已经建好了：把每个被注入服务的实现所属 fiber 的 uid 拼成一个字符串， 缺任何一个就整体退化成哨兵值（真实实现里叫 INACTIVE）。uid 由 registry 单调递增发放 （get counter() { return ++this._counter }），所以 provider 热替换也逃不过去： model 服务从 A 实现换成 B 实现，名字没变，"依赖都在吗"的答案前后都是 yes， 可 uid 换了，epoch 就换了，这次替换于是被识别成"必须重载"。

本章要补的是另一半：epoch 变了之后到底发生什么。ch02 的重载是同步的，比一下字符串， 直接重跑 apply。真实世界里这一步是异步的（插件体可以 await， disposer 也可以 await），于是三个新问题冒出来：

  • 转换在飞的时候 epoch 又变了怎么办？不能再起一次转换，否则两次卸载会交叉。
  • 加载已经排上队，但在插件体执行之前就被作废了怎么办？不能白跑一遍插件体。
  • 卸载跑完，发现 epoch 又变回可用了怎么办？要接着加载，而不是停在 PENDING。

三个答案压缩成一个字段（inertia，在飞的那次转换）和一条规则： 同一时刻最多一次转换在飞。epoch 于是从一个被比较的值变成一个被守卫的目标。

mini-dsh v0.3 · epoch 计算与转换驱动

_setEpoch 里那句 if (this.inertia) return; 是这套机制扛得住并发的关键： 已经有一次转换在飞的时候，新 epoch 只被记下来，不启动第二次转换。在飞的那次会在自己的尾部 重新比对 epoch，再决定是收工还是接着翻。两个转换函数因此互相尾调用，形成一个稳定的乒乓：

§3.5失败被容纳

一个插件在启动时抛异常，正确的结果是三件事同时发生：

  • 它自己进 FAILED，错误留在 fiber 上，fiber.await() 会带原始 stack 重抛；
  • 它已经完成的那部分注册全部回滚，抛异常之前 provide 出去的服务、注册过的工具， 一件都不许留下；
  • 依赖它的 fiber 退回 PENDING（它们自己没错，只是缺依赖）， 不相关的兄弟插件照常运行。

第二条是 _reload 的 catch 分支自动做到的，不需要额外代码：catch 里把 epoch 设成 INACTIVE，尾部的比对发现 epoch 变了，于是接着走 _unload()， 把插件体半途收集到的 disposer 排空。

第三条的区分在真实 dsh 里有产品含义。启动审计 packages/boot/app-boot/src/index.ts 的 assertEntriesActivated() 对两种状态给的诊断完全不同：

  failures.push(`${entry.options.name}: pending (waiting for ${missing.join(', ') || 'unknown'})`)
}
换成别的 harness 用 import 加载扩展的 harness，在"加载好了"和"整个进程带着一个 stack trace 倒下"之间 没有中间格子。dsh 有 FAILED，还有"依赖它的 fiber 退回 PENDING"这一步， 是因为它的插件表来自一棵能热改的 YAML 配置树（第 7 章），坏掉一个条目不能牵连另外几十个。 启动审计对两种状态给的诊断也不同：FAILED 带原始 stack，PENDING 列出还缺哪些服务。 这台状态机是被"配置驱动的插件表"逼出来的，工具表在编译期就定死的 harness 从来不需要它。
omp 自己的文档承认了这个格子的缺失 上面那句话在 omp 上不用我推，extensions.md 直接写着 "Extensions run in-process with no isolation"。它接着把失败路径说得很具体：一个裸 setInterval / setTimeout 或者游离 promise 的回调里抛出去的东西，落在 handler dispatch 的 try/catch 之外，浮成进程级 uncaughtException，全局 postmortem handler 按 fatal 处理，于是 "the whole session is torn down"，不只是出事的那个扩展。同一篇文档给的对策是让扩展改用 ctx.setInterval，把回调放回和 handler dispatch 一样的隔离里，同步抛出和 rejected promise 在那里会被记到扩展错误通道，会话继续跑；坚持用裸的那一对，隔离就归你自己包。 这一格正是 FAILED 加事务回滚要接的球：同样一个抛出，dsh 那边的结果是它自己进 FAILED、半途收集到的 disposer 排空、依赖方退回 PENDING，兄弟插件不知道刚才发生过什么。这是 fiber 模型在这一章里赢得最干净的一次。

诚实地说清楚：这不是沙箱 这一章造出来的容纳全部是生命周期意义上的：一个插件的注册可以被完整回收， 它的 teardown 通知失败会被逐个 observer 隔离（真实实现是 vendor/cordis/src/fiber.ts 的 emitPluginDisposed()， 函数头写着 "Notify plugin teardown without allowing one observer to break ownership cleanup"）。 但普通插件没有任何安全沙箱：它和整个 harness 跑在同一个进程、同一个 realm 里， 可以 while(true) 占死事件循环、可以改全局对象、可以拿到别人的 ctx。 dsh-scope 的 README 写着： "Scopes route trusted same-process plugins; they are not sandboxes or authority boundaries." 真正的隔离边界在子进程和权限系统那边，不在 fiber 上。

§3.7回到真实的 dsh

本章的正本是 vendor/cordis/src/fiber.ts（754 行）和 vendor/cordis/src/registry.ts。effect() 的真实签名有两个重载， 因为同步 effect 的 disposer 是普通函数，异步 effect 的 disposer 还能被 await：

vendor/cordis/src/fiber.ts · 真实签名（节选）
effect(execute: () => SyncEffect, label?: string): Disposable<Promise<void>>
effect(execute: () => Effect, label?: string): AsyncDisposable<Promise<void>>

我们刻意省掉的东西，按"省掉之后你会撞上什么"排序：

  • 异步 effect body 与 async iterable。真实的 _execute 还要在每次 await iter.next() 之后重新比对 runner.epoch，中途被作废就停止收集。 我们的 driveEffect 只认同步形状。
  • effectInertia 这个 WeakMap。公开的 disposer 要保持"单次生效"的上游语义， 而结构性 owner 和外层 effect 必须能加入别人已经开始的那次回收。
  • provide() 的 disposer 会等依赖方收敛。reflect.ts 删掉实现、notify() 一圈之后，还要 await Promise.allSettled(fibers.map(fiber => fiber.await()))，最后才删自己 store 里的那一份，注释是 "ensure self access before dependencies cleanup"。
  • 服务隔离与 intercept。inject 不只是名字列表，还能带 intercept config； ctx.isolate() 能让子树看到同名但不同实现的服务，epoch 里的 uid 就是它的可观测面。 这个设计我觉得是对的，但每次读 isolate 那段还是得想三遍。
  • internal/plugin 的发布时序。真实构造函数在 dispose 赋值完成之后 才 emit，因为同步 observer 可能立刻把这个 fiber（或它的父亲）dispose 掉。

还有一件要说清楚的事：这份 vendor 不是原样的上游。 vendor/README.md 有一份逐条穷举的 "Local modifications" 日志， 第 6 条整条在讲 fiber.ts 的生命周期加固，堵的是"卸载过程中又有人来注册或卸载"这类重入洞。 本章的 mini 版本按那一条的结论写的：wrapper 先上 owner list、同步失败回滚、UNLOADING 期间拒绝创建 effect、过 checkpoint 重新比对 epoch。所以 demo 里的顺序和真实实现一致。 这些结论的来源是别人踩过的 bug，不是谁推导出来的。
