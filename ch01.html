第 01 章

最小的 agent loop

剥掉插件系统、剥掉会话日志、剥掉沙箱，一个 agent harness 的内核是二十行 while 循环。 本章先把它跑起来。剩下大半篇幅在啃一个更麻烦的问题：循环什么时候停，停的时候往日志里写什么。

本章造出 miniLoop()3 个 demo · 1 处先猜再跑约 20 分钟

§1.1harness 就是一个循环

把营销词去掉，一个编码 agent 做的事只有这些：把用户的话和一堆工具描述发给模型， 模型回一段文字外加若干个工具调用，你执行这些工具，把结果塞回消息列表，再发一次。 直到模型不再调用工具。

模型是脚本化的假模型，每次返回写死的东西，所以你可以反复运行、逐行对照。 工具是三个玩具实现：bash、read、edit，各自吐一句固定字符串。

§1.2缺口一：turn 和 step 不是一回事

上面的循环只有一层，一次迭代等于一次模型请求。真实产品里有两个边界，混成一个就会出事。 dsh 的定义抄下来就能直接用：

定义 step 是一次模型请求，加上这次请求触发的所有工具调用。
turn 是零个或多个 step：它在第一份输入被认领之前打开，在不再欠任何东西之后关闭。

turn 为什么可以包含零个 step。因为「用户发了一句话，然后被策略拦在模型前面」也是一件必须记录的事。 turn 不存在的话，这次交互就凭空消失，日志里查不到。dsh 的做法是给被拒绝的输入照样开一个 turn、照样关掉， 里面一个 step 都没有。

反过来，一个 turn 里可以塞很多 step。模型调了工具，工具结果回来了，模型欠一次新的请求， 这是同一个 turn 的第二个 step。用户没有再说话，回合就没结束。

turn/start ├── step 0 请求 → assistant 文本 + 2 个 tool_call → 2 个 tool_result ├── step 1 请求 → assistant 文本 + 1 个 tool_call → 1 个 tool_result └── step 2 请求 → assistant 文本，没有 tool_call turn/end reason = completed
换成别的 harness 这个循环谁都有。Pi、Claude Code、Codex、OpenCode 跑的都是发请求、执行工具调用、再发一次。差别在两处。

一是循环本身能不能换掉。dsh 的 packages/core/agent-loop/README.md 开头写得很直白： 这是整个 harness 里唯一含具体循环逻辑的包，对外只是 AgentFactory 契约的一个实现， 而且以插件形式列在配置树里（--dump-default-config 能看到 name: '@deepseek-ai/dsh-agent-loop' 那一行）。 内核固定的 harness 里，循环编译在主包里，你能往它身上挂 hook，挂不掉的是它本身。

二是边界的粒度。Codex 的 app-server 在一个回合收尾时推 turn/completed，回合这一层是有的； step 这一层协议里没有对应物。粒度只有一层的时候，「输入被挡在模型前面」这件事没有地方落： 没有 turn 可以打开，也就没有 reason 字段可以填。
HN 上的反驳 上面这一段讲的是结构，结构说明不了效果。开源当天 HN 那条主线程（item 49285244，545 分 234 条评论）里 排在最前面的一条评论来自用户 217，全文八个词：「if it's not better than omp im not trying it」。 这话对本书这种逐机制对照是有效的：turn/step 两层边界、循环可替换，都能翻源码验证； 换成 dsh 之后模型答得更好没有，本章任何内容都不构成证据。 同一条线程里 flaburgan 要的正是缺的那块：同模型、同 prompt 的 harness 横向评测，他说目前没人做。 本书也没做。

§1.3缺口二：终止条件不止一种

朴素循环用 toolCalls.length === 0 判停。真实世界里的停法要多几种，而且必须分开记， 因为 UI 要显示的东西不一样，重试策略也不一样。dsh 把它们做成一个可合并扩展的和类型 TurnEndReasonMap，内置六个：

reason触发产品含义
completed模型没有调用任何工具正常结束，等用户下一句
max-tokens某个 step 撞上输出 token 上限回答被截断，通常要提示用户继续
blocked输入在进入模型前被策略拒绝零 step 的 turn，日志留痕
aborted用户点了停止，带上取消原因不是错误，不该报红
error模型调用失败或工具炸了要能区分「可重试」和「不可重试」
interrupted进程崩了，重启后持久化层给孤儿 turn 补的封口循环自己从不发这一个

最后那行有点反直觉，我贴一下源码注释：The loop never emits this marker。 崩溃之前写下的事件都还在，只是那个 turn 缺一个结尾，重新加载的时候由 persistence backend 补上。 所以你在 agent.ts 里搜 interrupted 是搜不到的。

还有一种停法不在这张表里：工具自己宣布回合结束。一个「向用户提问」的工具执行完之后不该让模型接着跑， 控制权得交回人类。dsh 里这是工具结果上的一个标志位，叫 concludesTurn。 它不产生新的 reason，最后仍然记成 completed，因为从循环的角度看， 没人再欠它任何东西了。

Demo 1.2turn 怎么收尾
注意 blocked 这一档 选 blocked 跑一次，turn/start 和 turn/end 中间什么都没有。 dsh 的测试里把这个形状钉住了： expect(log.some(e => e.type === 'step/start')).toBe(false)， 同时 reasons 必须等于 [{ kind: 'blocked' }]。零 step 的 turn 照样是一条完整记录。 很多 harness 在这种情况下干脆什么都不写，于是「我明明发过一句话，为什么历史里没有」就成了无法排查的 bug。

§1.4缺口三：输入得排队

朴素循环把用户输入当函数参数传进去。单轮对话里没问题，一旦有并发就崩。考虑这些同时发生的事：

  • 模型正在跑第 3 个 step，用户又发了一句「等下，先看看测试」
  • 一个后台子 agent 干完了，运行时要把「你的子任务完成了」注入进来
  • 一个后台 bash 任务退出了，要通知模型
  • 防循环守卫检测到模型连续三次调同一个工具，要塞一句提醒

这四件事都得变成模型下一次请求里能看到的东西，同时一件都不能打断正在进行的 step： 一个 step 的消息列表在请求发出的瞬间就冻结了。所以输入需要一个待着的地方，这个地方是信箱。

外部输入 ──┐ 子agent回报 ─┤ 后台任务 ─┼──► inbox ──► step 边界处 claim() ──► 下一次模型请求 守卫提醒 ─┘ (step 进行中不打断)

dsh 的信箱有两条队列。next-step 里的东西在最近一个 step 边界被整批拿走； next-turn 里的东西一次只走一条，因为一条 followup 就是它自己的一个回合。 这两条队列的分法我读了三遍才顺过来：claim(target, turn) 的参数叫 target， 可它并不表示「从哪条队列取」，next-step 无论如何都清空，target 只决定 要不要顺手从 next-turn 头上再取一条。名字和行为差半格。

另一个容易忽略的区别：有些消息会唤醒空闲的 agent，有些不会。 用户说话该立刻唤醒；注入的上下文（比如守卫提醒）不该自己触发一次模型调用， 它应该躺在信箱里，等下一条真正的消息把它一起带走。dsh 原话是 "Some messages wake it immediately; injected context waits in the inbox until another message does."

换成别的 harness 把用户输入写成函数参数（run(prompt)、query(prompt) 这种形状）的 harness， 多出来的输入源就得另找入口。后台子 agent 干完活想在回合中间报一句「我完成了」，函数参数那条路已经用掉了， 剩下两个选择：拼进下一次请求前的 prompt 文本里，或者等回合结束、当成新一轮用户输入。 前者绕过了日志，事后查不到这句话是谁塞的；后者压着子 agent 的结果等一整个回合。

OpenCode 走的是另一个方向：服务端拥有会话，开一个 OpenAPI 3.1 端点， 让 CLI、桌面端、网页、脚本同时连同一个会话。这解决的是「谁能投」。 「什么时候取」是另一件事，得由循环这一侧定，也就是下面这个 demo 里那些 claim 时刻。

Demo 1.3信箱与认领边界

跑起来之后立刻点两次「注入 context」，它们会静静躺在 next-step 里； 再点一次「插话」，三条会在同一个 step 边界一起被认领。 「同时投递 5 条」是同一件事的放大版：五条一起进 next-step，一次 claim 全部拿走， 不会摊成五个 step 慢慢消化。

§1.6回到真实的 dsh

本章对应的真实实现在 packages/core/agent-loop/，驱动类叫 ReactLoopAgent。 方法签名基本就是我们刚才写的东西的严肃版本：

packages/core/agent-loop/src/agent.ts · 真实签名（节选）
// 主循环：只要 turn() 还返回 true 就继续开新回合
kick(): Promise<void>

// 一个回合的边界，内部跑 step 循环
turn(): Promise<boolean>

// 认领信箱输入 -> 组装系统提示 -> 投影运行时上下文 -> 跑 agent/pre-step 瀑布
preStep(target: InboxTarget, position: { turn: number; step: number }): Promise<PreparedStep>

// 渲染提示 -> 构造冻结的 GenerateOptions -> 流式接收 -> 交给工具调度
step(assembly: PromptAssembly): Promise<StepEndReason | null>

// 按执行模式（并行池 / 独占屏障）调度工具，把 additionalContexts 送进下一个 step 的信箱
executeToolCalls(...): Promise<{ concluded: boolean }>

注意 StepEndReason 的定义： Extract<TurnEndReason, { kind: 'completed' | 'max-tokens' }>。 一个 step 只可能以这两种方式收尾，另外四种是回合层的事。这一行类型把 §1.2 那个区分钉死在编译器里了。

几个真实细节，mini 版本刻意省了：

  • 工具调度有两种模式：并发安全的工具进并行池，会改状态的工具走独占屏障，按提交顺序执行。
  • GenerateOptions 是冻结对象。请求一旦构造完成就不可变，这是「模型可见即已记录」能成立的前提。
  • 每个 turn 有独立的 AbortController。回合结束后重新分配，中断一个回合不会污染下一个。
  • agent/pre-step 是个瀑布事件，插件可以在这里改写、或者直接拒绝被认领的消息。这是第 4 章的内容。
