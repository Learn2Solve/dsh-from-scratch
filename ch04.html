第 04 章

事件的五种模式

第 3 章的 fiber 已经能把插件挂上来、再干净地卸下去。可是插件之间只有一个方向的能力：加东西。 permission 插件没法拦住一次 write，因为工具注册表根本不知道 permission 存在。 本章补上这一刀：五种派发模式，以及其中真正当扩展点用的那一种，waterfall。

本章造出 MiniEvents（五模式 dispatcher）3 个 demo约 26 分钟

§4.1一个 dispatcher，五种语义

第 3 章结束时我们有了 ctx.effect()：每次注册都返回 disposer，插件卸载时反序回收。 问题是注册这个动作只能往里加东西。工具注册表跑一次工具调用的时候， 没有任何机制让别人插进这个过程的中间。 唯一的土办法是让 ctx.tools 自己去认识每一个可能想干预它的插件：

没有事件总线：干预方必须被写进被干预方 ctx.tools.execute(call) ├── if (!permissions.check(call)) return deny <- tools 要 import permissions ├── call = sandbox.rewrite(call) <- tools 要 import sandbox ├── audit.record(call) <- tools 要 import audit └── dispatchToolBody(call) 有 waterfall 之后：被干预方只留一个缝 ctx.tools.execute(call) └── ctx.waterfall('tools/pre-execute', exec, () => dispatchToolBody(exec)) ▲ permission / sandbox / audit 各自 ctx.on() 挂进来。 tools 不知道它们存在，它们之间也不知道彼此存在。

Cordis 的事件总线一共五种派发模式。它们的差别在于谁能否决谁，跟性能没关系。 这五种是封闭的一组，源码里就是一个联合类型：

vendor/cordis/src/events.ts:32 · 原文
export type DispatchMode = 'emit' | 'parallel' | 'serial' | 'bail' | 'waterfall'
模式调用是否 await返回值否决能力
emitctx.emit(name, ...args)不等无没有。返回值和返回的 promise 一律丢弃
parallelawait ctx.parallel(...)等全部 settle无没有。失败聚合成 AggregateError
serialawait ctx.serial(...)逐个 await第一个 bail 值先注册的能截断后面的
bailctx.bail(...)不等（listener 必须同步）第一个 bail 值同上，同步版
waterfallctx.waterfall(..., next)不等（返回值通常是 promise）最外层 listener 的返回值不调 next() 就短路整条链，连内建默认行为一起

整张表里只有 "bail 值" 这一个词需要记住，而它比直觉宽得多：

vendor/cordis/src/events.ts:13-15 · 原文
export function isBailed(value: any) {
  return value !== null && value !== false && value !== undefined
}
两个立刻会咬人的推论 0 和 '' 都是 bail 值：一个返回 0 的计数 listener 会把整条 serial 链掐掉。
更隐蔽的是 async function。它返回的是 Promise，而 Promise 也是 bail 值。 把一个 async listener 挂到 bail 事件上，它在第一个人身上就 bail 了， bail 出去的还是个 promise。Demo 4.1 里能看到这一幕。

resolve() 做两件事：先把这次派发上报给 internal/dispatch（诊断钩子）， 然后返回 listener 的快照。快照的意思是，派发进行中新注册或被卸载的 listener 不影响本次派发。 另外有个怪癖我照抄了 cordis：parallel 上报的 mode 字符串是 'emit' 而不是 'parallel'（events.ts:184），所以从 internal/dispatch 是分不出这两者的。

on() 那一行是第 3 章和本章的接缝。listener 并没有躺在某个全局数组里， 它是通过 fiber.effect() 注册的一个副作用。插件卸载，listener 自己就消失了， 没有任何 removeListener 的记账。

Demo 4.1同一组 listener，五种派发

读一遍输出，四个事实：

  • emit 在 async listener 还没跑完就返回了。它们的日志落在 emit() 已返回 之后。 L2 给出的决定被无声丢弃。
  • parallel 等到所有人 settle 才返回，一个 listener 抛异常不影响其他人跑完 （Promise.allSettled），最后聚合成 AggregateError。
  • serial 里 L2 一 bail，L3 从来没有被调用。这是设计好的语义： "第一个非 null/false/undefined 的返回值胜出并终止其余"。
  • bail 里 L1 那个 async listener 直接把 promise 当 bail 值返回了。 换成同步三人组再跑一次才是正常语义。
模式是契约 Demo 里三个 listener 写成 (payload, next) 的形状，只为了让同一份代码在五种模式下都能跑， 这是教学取巧。真实 dsh 里一个事件的模式是它公开契约的一部分，用 @mode JSDoc 标签声明， 生成器会拿它去校验派发点（docs/cordis-primer.md:26）。 listener 只按一种模式来写。

§4.2waterfall 才是扩展点的本体

前四种模式里，listener 之间的关系是排队。waterfall 换成了套娃： 每个 listener 拿到的最后一个实参是 next，它包住的是剩下的整条链， 链的最底部是调用方传进来的内建默认行为。八行代码：

mini-dsh v0.4 · MiniEvents.prototype.waterfall

这八行里有三个容易看漏的设计：

  • inner 是从 args 尾部 pop() 出来的。内建默认行为只是链条最后一环， 在派发器眼里它跟 listener 没有区别。
  • next 是一个被所有 listener 共享的闭包，靠 queue.shift() 推进。 所以一个 listener 调两次 next()，第二次会跑到再下一个 listener，而不是重跑同一个。 这条我每次重读都还得在纸上画一遍才敢确认。
  • args.push(next) 之后 args 数组不再变。payload 对象是同一个引用被一路传下去， 这就是"协作型 listener 通常直接改这个共享对象然后 delegate"的物理基础 （docs/cordis-primer.md:32）。

关键结论只有一句，它同时是本仓库的一条硬规则：

Waterfall listeners MUST call next() to delegate; returning without it short-circuits the chain.
AGENTS.md:106

"短路整条链"里的"整条"把内建默认行为也算了进去。permission 插件能工作，全部原因就在这里： 它 return 一个 deny 决定而不调 next()，于是 ctx.tools 自己那句 "默认放行"根本不会执行，工具也就没有跑。ctx.tools 里没有一行代码提到权限。

Demo 4.2 是本章的中心。三个 listener 按注册顺序从外到内套着： logging（最外）、permission、sandbox（最内）， 最底下是 ctx.tools 的内建默认行为。 每个 listener 前面有一个 checkbox 控制它是否调用 next()。 把任意一个取消勾选，它下游的一切会整片消失，工具真正的执行也在里面。

按这个顺序跑几次，差别最说明问题：

  1. 三个全勾，选 read src/agent.ts：链一路走到底，内建默认给出 { kind: 'allow' }，然后在回程上被 sandbox 加了标记、被 permission 透传、被 logging 记录。 工具真的执行了。这是 around-middleware 完整的一圈。
  2. 三个全勾，选 write /etc/hosts：permission 靠数据判断出这是工作区外的写， 不调 next()，直接返回 deny。sandbox 和内建默认都没跑，工具没执行。 权限插件否决一次工具调用，全过程就是这样，而工具注册表对此一无所知。
  3. 取消 logging 的勾选：一个只想记个日志的 listener 忘了 delegate。 waterfall 返回 undefined，调用方拿到一个非法的 decision，工具静默地没有执行。 那条仓库规则就是为这个存在的：忘记 next() 不会报错，它会无声地吞掉所有人的默认行为。
  4. 勾上"外部命令"，把上面三种再跑一遍。忘记 delegate 这个 bug 消失了，因为根本没有 next() 可以忘。 同时消失的还有整条回程，以及每次调用多出来的那几十毫秒。
真实实现里的一条额外约束 Demo 里 sandbox 只在回程给决定加标记，没有改 exec.args。这是刻意的： 真实 tools/pre-execute 明确禁止改写参数，原话是 "Arguments cannot be rewritten because history, audit, UI, and execution must agree." （docs/subsystems/tools.md:402）。 一个允许在这里改参数的 harness，日志里记的调用和实际执行的调用会对不上。
换成别的 harness Claude Code 的扩展点是一张固定的事件名单（PreToolUse、PostToolUse、 SessionStart、Stop 等等），在 JSON 配置里把事件名接到一条 shell 命令上。 这条命令从 stdin 收一份 JSON，用 exit code 和 stdout 回话：exit 2 算 block，stderr 当理由； exit 0 的时候可以在 stdout 里放一段结构化 JSON，里面的 permissionDecision 才是 allow / deny / ask。 它确实能让一次工具调用被拒绝，但它拒绝的方式是把一个决定交回给调用点， 而不像 waterfall 那样自己站在调用点和内建行为中间。于是它包不住注册表自己的默认行为， 也没有回程可以用来改下游的产出。另外它每被调用一次就要起一个进程。

dsh 里有一个包专门吃这份配置：packages/hooks/hooks-claude-code。 它把 type: 'command' 的 hook 映射到本章这些 waterfall 上， PreToolUse 落在 tools/pre-execute，UserPromptSubmit 落在 agent/pre-step，Stop 落在 agent/turn-stopping。 一份现成的 hooks.json 大体上能原样跑起来。桥自己的 README 把边界写得很坦白： Claude Code 当前 30 个 hook 事件里有 23 个不支持；PreToolUse 的 deny 和 ask 生效，allow 不做预批准，updatedInput 只会被记一条 warning 然后丢掉；只有 shell 形态的 command hook 会跑， http / mcp_tool / prompt / agent 一律跳过； 配置在加载时读一次，Claude Code 那套项目／用户／插件／策略的分层发现和热重载都没有。
维度 dsh 的 waterfall Claude Code 的 command hook 同一份 hooks.json 走 dsh 的桥
执行位置 进程内，同一个 JS 调用栈 进程外，每个 hook 一条 shell 命令 进程外，走 ctx.shell，spawn 一次都省不掉
能否否决内建行为 有。不调 next()，内建那一环就不会执行 部分。只能把 deny 交回调用点，包不住注册表自己的默认 部分。deny / ask 映射成 PreToolDecision，allow 不预批准

桥这条路我到现在也没想清楚该怎么评价。它自己的 README 第 7 行就写着， 一个原生 cordis 插件能把它做的事全做了，返回值还是类型化的，中间也没有序列化这道墙， 所以桥"只作为已映射的那个 command hook 子集的兼容路径存在"。这话说得很实在。 那么剩下的理由就只有一条：你不用重写手上那份 hooks.json。 够不够，取决于那份文件有多长。

HN 上的一条质疑 开源当天的 HN 主线程里（item 49285244，2026-08-13），用户 lxdlam 读完 Cordis 那篇论文之后写道： "found it may be useful, but not that useful... it adds hot-reload and dynamic enable/dispose capabilities to a plugin system, like the one in Pi agents, though they push the boundaries further, to the UI components"。 这条值得对着本章看。热重载和动态 enable/dispose 是第 3 章的东西， Pi 的 TypeScript extension 也能在不 fork 的前提下加工具、加命令、加 hook， 所以"进程内、类型化的扩展点"本身算不上 dsh 的新东西。 本章这套机制里真正走得更远的是两点：派发语义被收成一个封闭的五元联合， 每个事件用 @mode 声明模式并由生成器校验派发点；waterfall 这种带回程、 能连内建默认行为一起否决的形状被当成了全仓库的默认扩展方式，六十多个事件里要干预的一律走它。 lxdlam 说的 UI 那一头也确有其事，扩展点一直铺到客户端， 跑起来的 Web UI 会去取 37 个客户端插件 bundle。 另一个方向上 dsh 没有推进：它的多 provider 适配层 packages/llm/llm-pi-ai 直接依赖 @earendil-works/pi-ai@^0.82.1，模型层是从 Pi 拿来的。 至于"更远"值不值这份复杂度，lxdlam 给的答案是 not that useful，我手上没有反驳他的材料。

拦截的另一半：改写

否决是 waterfall 的一半，另一半是改写，而且它有两个方向。 去程上改的是输入（payload 是共享对象，直接改）， 回程上改的是下游的产出（await next() 拿到结果，返回一个替换值）。 真实 agent/request 的 JSDoc 把回程这一半写得很清楚： "await next() yields the config the machine would use" （packages/core/agent/src/runtime-types.ts:233-234）。

Demo 4.3 用一个和 agent/request 同形的事件演示这一圈。三个 listener： trace 两侧都动（去程打标记，回程加 header）、 pin-model 只在回程动（整体替换掉下游给的 config）、 redact 只在回程动（把 config 里的密钥抹掉）。

为什么 serial 这么少 agent/turn-stopping 的 JSDoc 解释了原因。它是 serial，但它的 listener 不靠返回值否决：反对关闭回合的人去调 agent.steer(...)， 然后 loop 重读信箱，有新的 steering 就再跑一个 step，没有就关掉回合。 原话是 "Data decides, so listener order cannot change the outcome." （docs/subsystems/core.md:996）。 Claude Code 的 Stop hook 被桥接过来时走的就是这条 serial： 一个 blocking 的 Stop hook 自己够不着 agent 对象， 桥读出它的 reason，代它喂进 steer() （packages/hooks/hooks-claude-code/README.md:43）。

§4.4三个事件域：加一个事件之前先选域

上面那张表混着三类完全不同的东西。要把它们分清楚，是因为选错域会丢数据。

┌─ session 事件 ────────────────────────────────────────────┐ │ turn/start · user/message · assistant/message │ │ tool/call · tool/result · step/start · compaction/* │ │ 载体：只追加的会话日志，可持久化、可重放、可 fork │ │ 判据：会改变模型看到的内容 -> 必须在这里留痕 │ └──────────────────────────────────────────────────────────┘ ┌─ agent 事件 ──────────────────────────────────────────────┐ │ agent/pre-step · agent/request · agent/turn-stopping │ │ agent/status · agent/inbox/* │ │ 载体：进程内活着的 Agent handle，不持久化 │ │ 判据：只影响"这一次运行"的调度与策略 │ └──────────────────────────────────────────────────────────┘ ┌─ capability 事件 ─────────────────────────────────────────┐ │ tools/* · fs/* · llm/stream · approval/request │ │ 载体：拥有这个能力的那个 service │ │ 判据：属于某条能力流水线，换 provider 就换一整套行为 │ └──────────────────────────────────────────────────────────┘

session 事件：持久事实

session 事件跟 cordis 事件是两码事。它们的载体是日志里的一行。 这个 build 认识的全部类型是一个生成出来的集合，44 个，从 turn/start 到 compaction/summary （packages/core/session/src/known-event-types.ts:19）。 它们被 append 之后，cordis 侧才用一个 emit 事件 session/event 把"日志长了一行"这件事广播出去。

选这个域的判据是仓库里另一条硬规则：

Model-visible ⟺ logged: anything that reaches a model request must be reconstructable from the session log; a new model-visible input requires a session event.
AGENTS.md:107

反过来说：如果你的新行为会往模型请求里加任何东西，那就没得选， 必须先有一个 session 事件。否则会话重放出来的历史和当时模型真正看到的对不上， 而这正是第 5 章那套压缩机制能成立的前提。

agent 事件：活的句柄

agent/* 的 payload 里带着一个活的 Agent 对象， 你能在 listener 里直接调 agent.steer()、agent.inject()、agent.cancel() （packages/core/agent/src/runtime-types.ts:64-144）。 这类事件不持久，进程重启就没了。所以它适合放调度和策略， 不适合放"这次交互发生了什么"。agent/pre-step 拒绝一次输入是 agent 事件， 但"这次输入被拒绝了"这件事得进日志，就是第 1 章那个零 step 的 turn。

换成别的 harness payload 里带一个活对象这件事，只有进程内的扩展点做得到。 一个从进程外接上来的扩展点，无论它是读 stdin 的 shell hook， 还是通过 JSON-RPC 或 HTTP 连过来的客户端（Codex 的 codex app-server --stdio、 OpenCode 那个拥有执行生命周期、对外开 OpenAPI 端点的 Go server，都属于这一类）， 收到的只能是序列化过的数据，能回的也只能是序列化过的数据。 想让它调 steer()，就得有人在进程内代它调，上一节 Stop hook 那个例子就是这么处理的。 这里没有高下之分，只有边界画在哪里之后的必然结果： 跨进程换来的是语言无关和崩溃隔离，代价是句柄传不过去。

capability 事件：挂在拥有它的那个 service 上

第三类的归属规则很直白，primer 里一句话给完了： "a tool pipeline event belongs to ctx.tools, model streaming belongs to ctx.llm, and live agent coordination belongs to ctx.agents" （docs/cordis-primer.md:42）。 同一句话的后半段还给了事件和方法的分工： "Prefer events for interception and policy; prefer service methods for direct capability calls."

要加一个新的干预点，按这个顺序问：

你要加的行为 ... ├─ 会改变模型看到的内容？ ───► 必须先有 session 事件（durable），再谈拦截 ├─ 只影响这一次运行的调度／策略？ ───► agent/* 事件，payload 带活的 Agent └─ 属于某条能力流水线？ ───► 那个 service 自己的 capability 事件 需要否决或改写 -> waterfall 只是观察 -> emit

§4.6回到真实的 dsh

真实实现是 vendor/cordis/src/events.ts 里的 EventsService，它作为 ctx.events 装上去，并把五个派发方法混入每一个 context。 waterfall 的原文只有十行，和我们写的几乎一样：

vendor/cordis/src/events.ts:234-243 · 原文
waterfall(...args: any[]) {
  const cbs = this.dispatch('waterfall', args)
  const inner = args.pop()
  const next = () => {
    const cb = cbs.shift() ?? inner
    return cb(...args)
  }
  args.push(next)
  return next()
}

几个真实细节，我们的 mini 版本刻意省掉了：

  • thisArg 与 context filter。真实 dispatch() （events.ts:165-175）先判断第一个实参是不是对象，是就把它当 thisArg 取出来，然后用 thisArg[Context.filter] 过滤 hook，只有 global: true 的 listener 无条件收到。上面 tools/pre-execute 那个 carrier 就是这么用的， 它是 dsh scope 过滤（agent-scoped listener 只收到自己那个 agent 的事件）的底座。
  • listener 会被服务反射重新绑定：on() 里有一句 listener = this.ctx.reflect.bind(listener)（events.ts:295）， 让 listener 体内的 this.someService 走第 2 章那套 Proxy 反射。
  • internal/listener 是个 bail 事件，而且能改道注册。 on() 会先 bail() 一次它，非空结果直接替代整个注册流程 （events.ts:296-297）。cordis 自己就用这一招把 internal/update 的 listener 挪进 fiber 私有列表（events.ts:140-146）。
  • session/flush 并不真的走 ctx.parallel。SessionStore 自己用 Promise.allSettled 实现（packages/core/session/src/index.ts:1022-1039）， 抛的是第一个失败而不是 AggregateError，并且注释明确写了必须走这个入口、 不许裸调 ctx.parallel('session/flush', …)。SessionStore 是这条路唯一的入口。
  • waterfall 不一定是异步的。ctx.waterfall 本身是同步函数， 返回值类型完全由事件契约决定：session-telemetry/record 是同步瀑布 （packages/session/session-telemetry/src/index.ts:43）， llm/stream 的 next() 返回 AsyncIterable （packages/llm/llm/src/index.ts:64）。
