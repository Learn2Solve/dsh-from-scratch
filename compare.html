前面九章都在讲 dsh 自己怎么想。这一页把它放回同行里，逐个机制对一遍， 看哪些地方它真的换了结构，哪些地方只是换了个名字。最后一节说清这页比的是什么、不比什么。

§A.1先说结论

开源当天 HN 那条主线程里，票数最高的一条追问是 rco8786 写的： 「But like, what is it? Odd that this reached #1 on HN.」他抱怨 README 除了安装步骤 和一个指向 Cordis 的链接（那个链接后面写着「A Meta-Framework of Spatiotemporal Composability」） 之外几乎什么都没说。这一页存在的理由就是这个问题。

我能给出的答案是这样。Claude Code、Codex、OpenCode 三家的扩展都在进程外面： MCP 服务器、hooks 脚本、OpenAPI 客户端，你能往旁边挂东西，碰不到循环，也改不了那张内置工具表。 Pi 和它的下游 fork omp 走另一条路：进程内的 TypeScript 扩展加工具、加命令、加 hooks，不用 fork 主仓。 dsh 把这条路推到底：循环、工具表、模型层、会话存储在它这里全是插件， 一棵 YAML 组合树决定这次进程里装什么，每个会话还能挂自己的插件子树。

所以它的新颖之处是程度，不是种类。同一条 HN 线程里 lxdlam 读了 Cordis 那篇论文之后 说得很直接：「found it may be useful, but not that useful... it adds hot-reload and dynamic enable/dispose capabilities to a plugin system, like the one in Pi agents, though they push the boundaries further, to the UI components」。热重载和动态卸载 Pi 已经有了， omp 继承了同一套，dsh 把边界推到了 UI 组件那一层。这句评价我认为是准确的， 它也让「dsh 重新定义了 harness」这类说法站不住。 这笔复杂度的账划不划算，我读完九章也没有确定答案，只能把账单列清楚给你看。

§A.2六个 harness 的一句话画像

下面这六段只写我能指到出处的东西。Pi、Claude Code、Codex、OpenCode 四家我读的是它们的公开介绍， 以及 dsh 仓库里那两个把它们当子进程驱动的 provider 实测出来的协议细节。 omp 那一段来自它自己那套第一方文档。

harness一句话
Pi 终端里的极简 harness，MIT 许可，作者 Mario Zechner，2026 年 4 月挪到 Earendil 名下。 内置工具只有 read / write / edit / bash 四个，别的能力靠 TypeScript 扩展加进来，不用 fork 主仓。 模型层是单独一个包 @earendil-works/pi-ai，统一了 15 家以上的 provider，会话中途能换模型。 四种跑法：交互 CLI、print/JSON、RPC、SDK。它以 token 开销低、系统提示短出名。
omp pi-mono 的下游 fork，仓库 can1357/oh-my-pi。同步锚点 b21b42d（2026-03-22），之后分岔到 Bun 运行时、Rust natives、 bun:sqlite 凭据库。默认界面是差分渲染的 TUI，31 个内置工具， 会话是只追加的 JSONL entry 树，默认压缩策略把历史画成 PNG 帧。 扩展形态跟 Pi 同一套：一个默认导出函数的 TS 模块。
Claude Code Anthropic 的闭源产品，走 npm 分发，终端 TUI 优先。内置工具是固定的一套，大约 15 个。 扩展面有五六种：MCP 服务器、hooks、Agent Skills（一个 SKILL.md 加 YAML frontmatter）、 subagents、slash commands、CLAUDE.md。程序化调用走 Claude Agent SDK。
Codex CLI OpenAI 的开源实现，Rust 写的，终端优先。对外开一个 codex app-server --stdio，说 JSON-RPC。 支持 MCP、审批模式、沙箱、config profiles、AGENTS.md。
OpenCode 开源，客户端和服务端是拆开的。Go 写的服务持有执行生命周期，对外暴露一个 OpenAPI 3.1 端点， 所以 CLI、桌面端、网页、脚本能挂到同一个会话上。TUI 用 Bubble Tea 写。跨 provider，模型无关。 opencode serve 可以无头跑着，多个客户端同时连。
dsh DeepSeek 在 2026-08-13 开源的那一坨。一个 Cordis 依赖注入内核撑起两百多个包， 一棵可以打补丁的 YAML 组合树决定这次进程里装什么，界面是浏览器里的 React 客户端。 循环、工具、模型、会话存储在它这里都是插件。

换成别的 harness 「压缩是否破坏原始记录」这一行还剩四个 ?，看着像偷懒，其实是我不敢替它们回答。 但有一句关于结构的话是安全的：只要一个 harness 的会话状态就是那个消息数组本身， 压缩就必然是重写数组。摘要顶掉原文，原文从状态里消失，除非它另外写了一份完整日志文件。 dsh 和 omp 都敢说「不破坏」，前提相同：状态压根就不是那个数组。 往下一层机制就分岔了。dsh 的状态是一串只追加的事件，数组每次现算，折叠靠一条 surfaceOp 事件；omp 的状态是一行行只追加的 JSONL，压缩往尾巴上追加一条 CompactionEntry，靠里面的 firstKeptEntryId 指出边界， 指针左边的 entry 不再进 LLM 上下文，但一条都没有从磁盘上消失，重开会话也还在。 这也是第 5 章要花那么长篇幅的原因。

§A.4一张家谱

矩阵里有一格我一开始填错了。我以为 dsh 的多 provider 模型层是自己写的， 毕竟两百多个包了，再写一个 provider 适配器听起来很符合它的作风。

packages/llm/llm-pi-ai/README.md · 第一句，原文
Generic multi-provider adapter for the harness LLM seam backed by
`@earendil-works/pi-ai`. One plugin instance owns a dict of provider
profiles keyed by route; every request selects a profile with
`GenerateOptions.provider` and resolves `GenerateOptions.model`
against that route's configured catalog.
packages/llm/llm-pi-ai/package.json · dependencies
"@earendil-works/pi-ai": "^0.82.1"

那个极简 harness 的模型层，被这个最大主义 harness 直接 npm 装进来了。 dsh 的适配器在它外面套了一圈自己的东西：路由字典、按 route 的 catalog 覆盖、 凭据引用（apiKeyEnv 只存变量名，密钥不进配置文件）、per-model 的 reasoning 档位映射、 把 SDK 的 maxRetries 强行按到零好让重试预算归 agent 层管。 但拨号、流式解析、十几家 provider 的方言差异，是 pi-ai 在做。

那一格填错之后我把六家的来历都查了一遍。结果不是六个平行的项目，是一棵有分叉的树， 六家里三家能连到同一个上游。

Mario Zechner · pi-mono （对外叫 Pi，MIT，2026-04 挪到 Earendil 名下） │ ┌───────────────────┴────────────────────┐ fork 下游 npm 装一个包 │ │ omp dsh can1357/oh-my-pi DeepSeek，219 个包 锚点 b21b42d，2026-03-22 @earendil-works/pi-ai@^0.82.1 已分岔：Bun 运行时 / Rust natives 只借模型层，别的自己写 / 凭据进 bun:sqlite 的 agent.db Claude Code Codex CLI OpenCode （闭源） （Rust） （Go 服务） 这三家跟这棵树没有血缘关系，是各自长出来的

omp 是 pi-mono 的下游 fork，它自己那篇移植文档把同步锚点写得很死： commit b21b42d032919de2f2e6920a76fa9a37c3920c0a，2026-03-22， 包 scope 从 @mariozechner/pi-* 和 @earendil-works/pi-* 映射成 @oh-my-pi/pi-*。同一篇文档还列着它主动分岔的地方： 运行时换成 Bun，主 CLI 不留 Node 入口；jiti 换成 Bun 原生的 import()； 凭据从 auth.json 挪进 agent.db（bun:sqlite）并且支持多凭据轮询； 性能路径整体下沉到 Rust。fork 之后它没有停在原地，这是同一份代码分头往下走出来的两个东西。

这棵树解释了矩阵里几个看着巧合的格子。omp 和 Pi 的扩展形态是同一套： 一个默认导出函数的 TS 模块，进程内跑，加工具加命令加 hook。 dsh 借的只是模型层那一个包，它的插件内核跟 Pi 没有关系，是 Cordis 自己一套。 所以三家同源，同的地方各不相同：omp 继承的是整个进程模型，dsh 继承的是拨号那一层。

插件内核那一半，官方文档没写来路。开源第一天 X 上有几个中文开发者顺着代码的味道往回找， 落点是同一个地方：聊天机器人框架 Koishi。@heipiao233 说得最直白， 「这篇论文几乎可以说是给 Cordis 写的…它是给聊天机器人框架 Koishi.js 写的」。 @lihaoze24141442 是从 RAII 和 IoC 的味道认出来的， 「找到了 Cordis 原作者在 koishi 文档中对相关思想的介绍」，他贴的是 koishi.chat 上那篇 disposable。 @Daiiors 是老用户：「这个 koishi 框架就是 cordis 框架。 去年我做的量化交易系统也是基于这个框架。」同在 X 上的 @teortaxesTex 反应是懵的： 「not once does it mention DeepSeek or the DS harness. No evals, no nothing.」 这四条都是社交媒体上的个人说法，我按原话引，没替他们担保。

能核的那一半我核了：cordiverse/paper 的 README 自陈是 preprint， 全文一次都没有出现 DeepSeek，也没有附任何 eval。一篇不提 dsh 的论文被当成 dsh 的架构说明挂在 README 上， §A.1 里 rco8786 那句「what is it」有一半是这么来的。

Koishi · 聊天机器人框架（koishi.chat） 插件引擎：可撤销的副作用 + 声明式依赖 │ 抽出来单独成包 │ Cordis cordiverse/cordis · 论文 cordiverse/paper 论文是 preprint，不提 DeepSeek，也没有 eval │ dsh 插件内核直接用它，连 agent loop 都做成插件 这条线来自社区指认；论文那一条是我自己核过的

所以这棵家谱朝下有两条边：模型层是从 Pi 家 npm 装进来的， 插件内核是一个跑了几年的聊天机器人框架换了个场合。dsh 自己写的，是夹在中间的那一层。

另一个方向也通。dsh 仓库里躺着 subagent-claude-code 和 subagent-codex： 前者调官方 Claude Agent SDK（钉在 @anthropic-ai/claude-agent-sdk@0.3.220）， 解析 claude 可执行文件的真实路径，起一个 persistSession: false 的 query； 后者 spawn codex app-server --stdio，走 initialize 到 initialized 到 thread/start { cwd, ephemeral: true } 的握手，等那条权威的 turn/completed。 两个 provider 都只把最终答案捞回来，子 agent 的推理、中间消息、工具流水、stderr、 工作区 diff 一概不进父会话的上下文。 omp 这一头没有对应的东西：它的子 agent 全是进程内的子 AgentSession， 内置七种 agent 类型，但文档里明说它不 spawn 外部的 claude 或 codex 二进制。 所以「把别的 harness 当工人使唤」这一轴上，六家里还是只有 dsh 一个。

把这两个方向摆在一起看，dsh 在争的位置就清楚了：它在这些工具的上面一层。 下面借 Pi 的模型层，上面把 Claude Code 和 Codex 当工人使唤。 这个位置的名字叫编排层，它跟另外五家不在同一个格子里竞争， 所以「dsh 比 Claude Code 好用吗」这个问题本身问得不对。

换成别的 harness 反过来问：Claude Code 能不能把 dsh 当子 agent 调？能，dsh 那个 ACP 服务端就是给这个用的。 Codex 能不能？也能，同一个口。omp 也有 RPC 和 ACP 两个口，别人调它没问题， 它调别人没有现成的路。互相当子 agent 这件事在协议层早就通了， 没通的是「谁来当那个总调度」。dsh 是目前唯一一个把这件事写进包结构里的。 它值不值这个位置，取决于它的调度到底比人手工串一串脚本好多少。这一点没有数据，见 §A.7。

§A.5同一个任务，六种走法

矩阵是静态的，看不出代价。下面这个 demo 换个角度：给一个具体任务， 把六家各自要走的路排在一起，数往返次数，数进上下文的东西，数人要动手做的事。

先把话说清楚。dsh 那一栏是我在仓库里读到并跑过的。omp 那一栏来自它自己那套文档， 机制我读到了，东西我没装过。剩下四栏是架构推演： 按它们公开描述的结构，这个任务只能这么走。每一栏都标着来源。

Demo A.2六种走法并排

第一个任务跑完，dsh 那一栏的往返次数最少，进上下文的东西也最少。 这不是它聪明，是 Code Mode 把五次工具调用塞进了一段程序里。 omp 的 eval 能走同一条路，它默认那条路走的是原生 ast_edit， 先出预览再落盘，多一次往返。第二个任务是三个里最有意思的： 五家都要为压缩付一次模型请求，omp 付零次。

这两个开关的含义 「拆掉 Code Mode」等于取消 run_code，让模型回到一次工具调用一次往返。 「关掉 surfaceOp」等于让压缩直接重写消息数组，也就是矩阵里那四个 ? 和 omp 之外几家最可能的样子。 两个开关都拆掉之后，dsh 剩下的还有插件化的工具表和运行时自我改造， 但它在前两个任务上的优势就没有了。

§A.6dsh 输在哪里

上面那张表把 dsh 那一列涂成了高亮色，读起来像一份推荐。这一节把力气花在反面。 分四组：第一组是我自己在源码里查到的；第二组是开源当天 HN 主线程上别人说的； 第三组是 omp 具体压过 dsh 的地方，来自它自己那套文档； 第四组是三份独立的安全披露，它们钉的 commit 跟本书对照的是同一个。 第二组里有几条比第一组更值得你花时间想。第四组最要紧的是它把这个项目切成了两半， 一半评价很高，一半还没开始做。

§A.6.1 源码里能查到的

  • 没有 TUI。packages/client/ 底下四十来个 ui-* 包全是 React， 界面只有浏览器一条路。你 ssh 进一台服务器想跑 agent，得先起 web 服务再做端口转发。 另外五家都是终端优先，Claude Code 和 Codex 干脆只有终端。omp 的 TUI 还是差分渲染的。
  • SESSION_FORMAT_VERSION = 0，而且它明说不做迁移。 packages/core/session/src/types.ts 里那行常量就是 0， 注释里的规则是：写入端的语义一变就 bump，读取端遇到别的版本号直接抛。 完整的 upgrade-step 链条只存在于一篇 Agent Note 里。现阶段你今天存下的会话，明天可能读不回来。
  • 两百多个包。find packages -name package.json 数出来 219 个。 想改一个行为，你得先知道它属于哪个 seam、由哪个 provider 实现、在哪一层 patch 里被挂上。 Pi 的卖点之一是心智负担轻，dsh 在这一项上是反面典型。
  • 配置文件里能写代码。YAML 里的 !!js 标签会被求值， 官方例子就长这样：ANTHROPIC_API_KEY: !!js process.env.ANTHROPIC_API_KEY。 它确实好用，条件挂载、读注入服务、拼字符串都靠它。它同时意味着， 任何能写你 cordis.yml 的人都能在你的进程里执行任意代码。 一份从网上抄来的 profile 是一段没人审过的脚本。
  • 插件没有安全沙箱。沙箱那几个包管的是工具执行（bash、文件写），不管插件本身。 一个 Cordis 插件跑在主进程里，拿得到 ctx，也就拿得到所有服务。 cordis_run 让模型现场挂插件这条路更直接：第 9 章那个 demo 好玩， 代价是模型写的代码和你的 harness 同进程同权限。
  • 它 64 天大。第一个 commit 是 2026-06-10，最后一个是 2026-08-13，中间 12293 个 commit。 这个密度说明它是高强度冲出来的，也说明没人在生产环境里用它跑过一天。 开源当天 43437 个 star、3404 个 fork，两天后大约 97000 个 star、9100 个 fork，而 origin/master 从那天起一个 commit 都没动， npm 上还是 0.1.0-rc.6。动的全是读者。
  • 它自己的文档在漂。tool-cordis 实际注册 7 个工具， 它的 README 写 5 个，仓库里还有一篇 Agent Note 按旧名字描述 3 个。 两百多个包各带一份中英 README 是很壮观的工程，维护它们是另一回事。

§A.6.2 HN 上的批评

  • rco8786（高票）问的是定位：「But like, what is it? Odd that this reached #1 on HN. Every product relying on community plugins works fine the 6 first months, then it's a nightmare of incompatible, deprecated plugins, with no consistency and no governance.」 dsh 的每一项优势都建在插件系统上，所以这条批评打的是它的根。 它现在还在头六个月里，第七个月的样子没人见过。
  • bdcravens 讲的是同一件事的另一半：「Most vendors that create a plugin-based system end up creating a large library of plugins to kickstart the ecosystem, which many users end up trusting more because they're "official", so they essentially created a mono-vendor ecosystem with extra steps.」 219 个包里绝大多数都是官方的。你要真去换掉哪个 provider，换进来的东西没有官方那份的测试和文档。 「一切皆插件」到目前为止的实际效果，可能就是他说的那句：带额外步骤的单厂商生态。

  • yipinwong：「Good idea, ugly landing page」。 这条放在最后不是因为它不重要。一个只有 web 界面、没有 TUI 的 harness， 第一印象全压在那个页面上。

§A.6.3 omp 具体压过 dsh 的地方

§A.6.1 写的是 dsh 自己的软肋。这一小节换个角度：同一轴上 omp 已经做得更彻底的几项。 出处都在它自己的文档里，我没有跑过。

  • snapcompact。默认压缩策略不调模型：把要丢掉的历史序列化，用像素字体画成 PNG 帧， 交给视觉模型当图像读。字形和帧尺寸按各家图像计费公式挑（Claude 用 11on16-bw， Gemini / GPT 用 8on22-bw，Kimi / GLM 用 8on16-bw）， 不需要 API key，也不联网。dsh 的压缩要跑一次摘要模型。
  • Rust natives。grep / fd / glob / AST 改写 / 结构化 diff / token 计数 / 文本排版 全走 @oh-my-pi/pi-natives。dsh 是纯 TypeScript。
  • 会话树 + rewind / checkpoint。会话是一棵只追加的 entry 树， checkpoint 打内存标记，rewind 在检查点处 append 一条 branch_summary 并把 leaf 移回去，被放弃的探索分支还躺在 JSONL 里。 dsh 有 fork，没有树内导航和探索分支回滚。
  • 30 多家 provider + 多凭据轮询。外加 11 种 toolconv 方言转换器， 其中有专门处理 DeepSeek 全角 token 泄漏的那一套。dsh 的多 provider 层借的是 pi-ai， 凭据轮询和 toolconv 这两层它没有对等的东西。
  • 持久跨会话记忆。四种后端可选，默认关；打开之后有本地 SQLite 加向量召回 （mnemopi）和远程向量服务（hindsight）。 dsh 只有 session_search 一类的日志检索。
  • skills 发现根目录覆盖六个生态。 .omp、.claude/skills、.agent/skills、 .codex/skills、.config/opencode/skills、.github/skills 都会扫。dsh 只扫两个。
  • 有真正的 TUI。差分渲染，append-only 原生 scrollback，支持 Kitty / iTerm2 / Sixel。 这一条 §A.6.1 已经写过，放在这里是为了把账单凑齐。

§A.6.4 插件信任模型（三份独立审计）

前面三小节是我自己读出来的，这一小节不是。开源当天和第二天， 有两个人各自把插件这条路走了一遍，出了两份审计，彼此独立，落点重合。 第三天又多了一份，钉的是 web 控制面。 对本书来说要紧的是它们钉的版本：第一份钉在 commit 47f9438， 活体验证跑的是 npm 上的 0.1.0-rc.6，跟这本书从头到尾对照的是同一个东西。

第一份出自 Fz0x00（Discussion #454）， 规模是 40 条攻击路径、96 条带 file:line 的源码证据、13 个可复现 demo。 它把这个项目切成两条轴，这个切法比「有没有沙箱」那种问法准确得多。

  • 轴 A，面向模型和 agent 行为：审计给的定性是 production-grade。 工具执行管线、fail-closed 的审批、进程沙箱、文件观察策略、凭据引用模型、 只追加的审计日志，还有浏览器那道 confusion-deputy 围栏（403/415 是对活实例验的）。 第 5 章和第 6 章写的就是这一半，审计没有推翻其中任何一条。
  • 轴 B，面向插件代码：审计的原话是「目前没有安全设计」。 插件在宿主进程里跑，拿宿主权限；install、update、篡改、持久化、热重载这几条路上， 签名、完整性、来源、确认闸门一个都没有。

轴 B 具体长什么样，两份审计各自给了可复现的路径。下面几条按它们的原文列， 括号里是审计仓库那些 demo 目录的真名。

  • YAML 里的 !!js 就是加载期的宿主级 RCE （demo-01-js-config-rce，活体标记文件 PWNED-BY-LIVE-JS）。 §A.6.1 那条只说了它「意味着」什么，审计做的是把它跑出来。
  • dsh plugin add <pkg> 字面上就是 pnpm add <pkg>， 这是第二份审计（xiejin77，Discussion #587）的原话。 恶意 bundle 在 install 那一刻就在宿主进程里执行，审计给的证据是 payload 的 pid 等于 host 的 pid。
  • 插件能在 boot 期改写整棵配置树，时点在任何运行时防护激活之前： approval.policy 改成 never， sandbox-policy.mode 改成 danger-full-access。 换句话说，轴 A 那一整套的参数，是由轴 B 在它启动之前决定的。
  • dsh plugin remove 不会移除已经持久化的 !!js 后门。 装完之后再改文件也是零校验加载，用户 patch 的热重载大约 15 秒生效，不用重启进程。 热重载在第 3 章是这个内核最漂亮的地方，在这里它是攻击面的一段。
  • 第三份（OracleNep，Discussion #853）钉的是另一条面： dsh web 的控制面是裸 node:http，无 token、无 cookie、无 TLS。 Host / Origin 围栏源码自己写明「不是认证层」。PoC 是未认证 session.create，再执行 /permission danger-full-access，再 session.prompt 驱动 bash。作者给的分级是默认 loopback 为 High， 绑到非回环为 Critical。这不是轴 B 的插件安装，是 web 面把轴 A 的审批拨盘露了出来。
这几条要跟上面一起读 插件那条路要受害者自己敲 dsh plugin add，第二份审计的作者把边界写在最前面： 不是零点击的远程 RCE。出厂的 web 界面里，agent-instructions 那一路默认关着。 #853 另起一条：只要 dsh web 在跑，本机任意进程就能走未认证控制面， 不必先 plugin add。两份插件审计也都列了 dsh 已经做对的地方：pnpm 的 registry integrity、 0600 / 0700 的文件权限、.env 的 bootstrap guard、 特权 RPC 只绑 loopback，第一份审计给这些的定性是 real mitigations。 它的立场也写得很明白：防御性披露，「插件即可信」是这个项目的设计取舍，报告只陈述事实和风险。

所以这一小节的标题不叫「dsh 不安全」。审计自己的二分比那句话准得多： 同一个仓库里，面向模型的那半边被一份外部审计评为 production-grade， 面向插件的那半边还没开始做。这两半在架构上本来就是分开的， packages/sandbox/ 管的是 bash 和文件写， 管不到加载它自己的那棵配置树。

第二份审计还留了一句横向的话，我把它加成了 §A.3 矩阵里的一行： Codex、Claude Code、Gemini CLI 这一路的共识是让核心进程只吃声明式或者纯文本的指令， 可执行的扩展一律放到进程外面去跑。六家在这一轴上三比三分开， dsh 这一边的另外两个是 Pi 和 omp。这一行是前面九章那些能力的前提， 也是这一小节所有问题的前提。

§A.7这里比的是架构，不是效果

读到这里你手上有一张 17 行的矩阵、三个任务的六种走法、一份带出处的批评清单。 有一样东西这页给不了你：这六个东西干活谁干得好。

HN 上 flaburgan 要的正是这个。他想看 harness 之间的横向质量评测， 并且指出目前根本没有人做同模型、同 prompt 的对比。他说得对。

把话说完整。本附录比的是结构：谁的什么东西能在运行时换掉，会话状态长什么形状， 压缩之后原文还在不在，谁能把谁当子 agent 调。能指到源码的地方我指了，指不到的留了 ?。 它一个字都没有说 dsh 改代码改得比 Claude Code 好，也没有说 Codex 的补丁质量高于 Pi。 那种对比要固定模型、固定任务集、固定 prompt，跑足够多次数看方差， 还要公开评分口径好让别人复现。这项工作我没有做，据我所知也没有别人做过。

所以 217 那句置顶短评是有道理的。他要的是效果证据， 这页只有结构证据。两者不能互相顶替。

§A.8怎么选

不排名。按你实际想干什么对：

你想要的去看
今天就要一个能干活的编码 agent，装完就用 Claude Code 或 Codex CLI。dsh 的第一步是读那棵 YAML 组合树。
想在终端里跑，token 账单要压得住，系统提示要看得懂 Pi。四个内置工具，扩展是 TypeScript 文件。
想在终端里跑，但要 30 多家 provider、会话树、压缩不调模型 omp。Pi 的下游 fork，TUI 是默认界面，默认压缩是 snapcompact。
要多个前端（CLI、桌面、网页）连同一个会话 OpenCode。它的服务端本来就是为这个拆出来的；dsh 的 ACP 是自动化专用，不做 UI。
要把 Claude Code 和 Codex 当工人，上面套一层自己的调度 dsh。六家里这一项只有它写进了包结构。omp 不 spawn 外部 harness 二进制。
压缩之后还要能查到原文，或者要做审计 dsh 的只追加事件日志，或者 omp 的 JSONL entry 树。别的方案要么自己另存一份，要么接受原文丢失。
同一个进程里跑多个会话，每个会话工具集不同 dsh 的插件子树，或者 omp 的每会话私有工具注册表。
想读一份架构，把里面的想法搬到自己的项目里 dsh，读第 5 章和第 6 章就够了。事件日志加表面投影、能力接缝这两招， 在一个只有五千行的 harness 里也能用。
怕插件生态半年后烂掉，或者不接受配置文件能执行代码 别选 dsh。invaliduser 和 bdcravens 那两条批评现在没有反驳材料。
要在生产环境跑，要向别人保证不出事 这六个里没有一个我敢推荐。dsh 尤其不行，理由在 §A.6.1。
想知道哪个改代码改得最好 这页答不了，见 §A.7。目前谁都答不了。
