第 05 章

会话日志与表面投影

每个 harness 最终都要压缩上下文，而压缩的第一版几乎都长这样： history.splice(0, 20, summary)。二十条原始消息从此不存在于进程里。 dsh 把消息数组降级成一个投影，事实来源换成一条只追加的事件日志。 压缩于是成了一次 append。原始事件一条不动，只是不再出现在投影里。

本章造出 SessionLog / foldSurface() / deriveMessages()4 个 demo · 1 处先猜再跑约 32 分钟

§5.1可变消息数组的三个致命伤

第 1 章的 miniLoop 里有这么一行：deps.history.push(...)。 那个数组就是全部上下文，它同时扮演三个角色：模型请求的输入、UI 的数据源、会话的历史记录。 一个可变数组扛不住这三件事。下面三个失败跟审美无关，它们会在真实事故里咬人。

一：审计链丢失

翻开 history，你看到一条 { role: 'user', content: '跳过测试，直接提交' }。 这句话可能来自真人，也可能是防循环守卫注入的提醒、一个子 agent 干完活的回报， 或者某个插件在组装请求时临时拼进去的一段字符串。数组区分不了，它只有 role 和 content。 事故复盘时你问模型为什么会认为可以跳过测试，答案已经被结构本身抹掉了。

二：UI 无法重放

消息数组里没有流式 chunk，没有工具卡片的展开状态，也没有 todo 列表、 被策略拒掉的那次输入、用户中断掉的那个 turn。产品于是维护第二份状态来画界面， 两份状态迟早不一致。表现通常是刷新页面之后 UI 少了一半东西，而模型那边什么都没少。

三：压缩摧毁证据

上下文满了要压缩。最直接的写法是把前 20 条换成一条摘要：

几乎每个 harness 的第一版压缩
const summary = await summarize(history.slice(0, 20));
history.splice(0, 20, { role: 'user', content: summary });  // 20 条消息就此消失

摘要是模型写的，模型会写错。半小时后 agent 基于摘要里的一个错误结论做了危险操作， 你想回去看原始材料，没有了。连"摘要到底漏掉了什么"都答不上来，因为对照物已经被 splice 掉。 这个操作还不可重放：同一份记录喂给 UI，永远画不出压缩发生前的那个界面。

The session log is the source of the context the model sees. deriveMessages() projects model history from it, and raw assistant/chunk events preserve replay and UI fidelity. Fork, resume, transcripts, telemetry, and persistence all derive from this stream.
docs/architecture.md · Session log

三伤有同一个根：消息数组被当成了事实来源。本章把它降级成一个从日志算出来的函数值， 大约 120 行，页面上跑的就是这些行。

§5.2事件信封

日志的原子单位是一个 SessionEvent。它是一个以 type 为判别式的联合类型， 字段少得有点反直觉：

packages/core/session/src/types.ts · SessionEvent（真实定义，节选）
export type SessionEvent<T extends SessionEventType = SessionEventType> = {
  [K in SessionEventType]: {
    type: K
    /** Monotonic sequence number within the session. */
    seq: number
    /** Unix epoch milliseconds. */
    time: number
    data: SessionEventMap[K]
    /** 读者不认识 type 时可以安全跳过的标记；缺省表示"必须理解" */
    ignorable?: true
  } & (K extends SurfaceEventType ? {
    /** 这条事件引用了哪些更早的事件作为来源 */
    sourceEventSeqs?: number[]
    /** 它是怎么进入 surface 的；非 surface 事件上不存在 */
    surfaceOp?: SurfaceOp
  } : object)
}[T]

逐个字段说清楚，每一个都在偿还 §5.1 的某个失败：

字段约定
seq会话内单调递增且连续，包括原始 chunk。契约是 seq === log.length，所以持久化层可以逐字存储整份日志，不需要重编号。
timeUnix 毫秒。它是元数据，不参与任何投影。
data必须是无损 JSON。Session.append 用 snapshotJsonValue 递归读一遍并同时拷贝，所以有状态的 getter 没法"给校验一个值、给存储另一个值"。BigInt、函数、Map、Date、稀疏数组、负零全部当场拒绝。
ignorable?默认是必须理解。读者遇到不认识且没有这个标记的 type，得拒绝重建整个会话，不能悄悄跳过。
sourceEventSeqs?只存在于三类 surface 事件上。这是 §5.1 第一伤的答案：一条消息的来源写在事件里。
surfaceOp?同上，只存在于 surface 事件上。它是本章的主角，§5.4 展开。
为什么默认"必须理解" 一个不认识的必需事件可能改变后面整份日志的解释方式。 比如一个新版本引入的 surface 操作：跳过它，后面所有 replace 的坐标就全错了， 但日志依然"parse 成功"。
写者只在纯信息性的记录上标 ignorable: true。 忘标一次的后果是过度拒绝（麻烦），漏判一次的后果是静默恢复一个被掏空的会话（灾难）。 dsh 选了会麻烦的那一边。

SESSION_FORMAT_VERSION = 0，且刻意不提供兼容

packages/core/session/src/types.ts · 版本号的真实注释（节选）
// While the harness is unreleased it is pinned at `0`: no compatibility is
// implied, incompatible logs are rejected, and no migration is provided.
//
// The version is a single monotonic integer with no major/minor split. Whether
// a bump is needed is decided by what the WRITER emits, never by what a newer
// reader can accept ...
// ("parses without error" is not correctness - silently skipping content that
// shapes reconstruction is a wrong read.)
export const SESSION_FORMAT_VERSION = 0

这里有三个判断值得抄走。版本是一个整数，没有 major/minor：兼容性不是二维的， 你要么能正确读，要么不能。该不该 bump 由写者决定，跟"新一点的读者能不能容忍"无关。 够格 bump 的只有结构性变化：header 形状、事件信封、核心事件语义，以及 surface 机制本身 （SurfaceEventType 集合与 SurfaceOp 变体）。新增一个普通事件类型不 bump， 词汇表的增长由每条事件上的 ignorable 兜住。拿不准就 bump。 一次近似恒等的升级步骤几乎免费，漏一次 bump 会让旧运行时静默读错新日志。

§5.3只有三类事件是模型可见的

这个 build 的事件词汇表里有 44 个类型 （known-event-types.ts 里的 KNOWN_SESSION_EVENT_TYPES， 由脚本从各插件的 SessionEventMap 声明合并生成）。能进入模型请求的只有 3 个：

packages/core/session/src/types.ts
export type SurfaceEventType =
  | 'user/message'
  | 'assistant/message'
  | 'tool/result'

其余 41 个全是 log-only。挑几个容易被误认为模型可见的：

事件为什么不给模型看
tool/call最反直觉的一个。assistant/message 的 content 里已经带了 tool-call block，模型自己产生的东西不需要再喂回去一遍。tool/call 存在只为了 trace 和配对校验。
assistant/chunktoken 级重放保真度。UI 靠它复现打字机效果，模型只需要组装好的那条 assistant/message。
turn/* step/*边界标记。回合结构是给日志读者的，不是给模型的。
todo/write整份列表快照，重放时最后一次写入胜出。UI 从事件渲染，不进派生历史。
plan/modelog-only、非 surface、整值替换。foldPlanMode 折叠出当前状态，一份没有该事件的日志折叠为 inactive。
request/header下一次请求的完整 header 快照。最新那条就能重建请求配置，所以它不需要出现在消息里。
approval/asked approval/decided审批过程。模型看到的只有工具结果，不该看到人类怎么点的那两下。
换成别的 harness plan/mode 这种状态在 dsh 里根本不经过模型：foldPlanMode(events) 取最后一条，resume、fork、压缩都从日志直接恢复。todo/write 的账更值得算一遍。 todo_write 是个模型可见的工具，所以调用本身在 transcript 里， 那是模型自己产生的东西；但它的结果只有一行 Updated todo list: 2 pending, 1 in progress, 0 completed.， 整份列表快照落在 log-only 的 todo/write 事件上，交给 UI 和重放去读。

换成一个以消息列表为状态的 harness，这份列表没有别的地方可待。同样改十次， 两边都会留下十次调用，差别在结果这一侧：dsh 给模型十行确认，全表快照走事件； 而列表本身必须以消息形式存在时，每次改动都把整张表再写进 transcript 一遍， 之后永久占位。plan/mode 那一类就更明显，它在 dsh 里连一次调用都不占。

注意这段话的前提是"以消息列表为状态"。omp 的会话不是那个形态（§5.5 有它的形态）， 它的 todo 具体落在哪一类 entry 上我没查，所以这一段不覆盖 omp。

所以"投影"这件事的核心规则，是一个每节点执行一次的纯函数。 下面这段是我们的 mini 版本，逐条对着真实的 deriveEventMessage 写的：

mini-dsh · deriveEventMessage() · 页面上运行的就是这段
两个刻意为之的细节 逐字投影，不加框。user/message 直接返回 event.data， 不在这里补 <context> 之类的包装。要框的人自己把框烘进 content （agent-instructions 就是这么写 <system-reminder> 的）。 投影必须是纯粹的 pass-through，否则它就不再是"日志能重建请求"的那个函数了。

空内容的 assistant/message 返回 null。 一个撞上 max-tokens 的 step 会留下一条只承载 usage 的空消息， 它必须被记录（否则 token 账目丢了），但绝不能给 provider 的对话里塞一个没内容的 assistant 回合。

§5.4surfaceOp 折叠

只有三类事件可见，那直接 events.filter(e => SURFACE_TYPES.has(e.type)) 行不行。 不行，因为压缩产生的摘要检查点自己也是一条 user/message， 光看类型区分不出"追加到尾部"和"覆盖掉中间一段"。

dsh 的做法是让写入方在 append 的那一刻就把意图记下来，于是重放变成一次纯折叠：

packages/core/session/src/types.ts · SurfaceOp
export type SurfaceOp =
  | 'append'
  | { op: 'replace'; start: number; end: number }

start 和 end 是 seq 值，而且必须是当前 surface 上 真实存在的节点，两端都含。start === end 就是替换单个节点。 被覆盖掉的每一个节点，都必须出现在这条事件的 sourceEventSeqs 里。

两个把关函数，它们的错误信息就是这套契约的完整定义：

mini-dsh · 准入校验

然后折叠本身只有二十来行：

mini-dsh · foldSurface() 与 deriveMessages()
日志（只追加，永不改写） surface（模型可见顺序） seq 2 user/message append ──► [2] seq 6 assistant/message append ──► [2, 6] seq 8 tool/result append ──► [2, 6, 8] seq 9 step/end log-only 不动 seq 12 assistant/message append ──► [2, 6, 8, 12] seq 40 user/message replace 2..12 ──► [40] 一次 splice：4 个节点变 1 个 replaceGeneration += 1 deriveMessages() = nodes.map(seq => deriveEventMessage(log[seq])).filter(非 null)
一个容易踩的细节 nodes 是 surface 顺序，不是 seq 顺序。 一次 replace 会把新事件那个很大的 seq 用 splice 塞回旧位置， 所以折叠之后 nodes 完全可能是 [40, 24, 27, 29, 33] 这种非单调的样子。 任何假设"surface 按 seq 排序"的代码都会在第一次压缩后出错。

replaceGeneration 是位置替换的计数器。真实 Session.deriveMessages() 缓存每个节点的投影结果（每个节点只投影一次，一次调用的成本是 O(新增节点)）， 而 generation 变化就是把缓存整体推倒重建的信号：append 只会让缓存变长，replace 会让它失效。

§5.5压缩是一次追加，不是一次删除

现在可以回答 §5.1 第三伤了。dsh 的压缩事务一共五步，其中四次 append、零次删除：

1. appends compaction/start (log-only) — acquires the lock,
2. summarizes the range,
3. appends compaction/summary (log-only) with the summary, range, shadowed seqs, token count, and provider/model call envelope,
4. appends a single user/message with surfaceOp: { op: 'replace', start, end } carrying the summary — the only surface mutation in this operation,
5. appends compaction/end (log-only) — releases the lock.
packages/compaction/compaction/README.md

第 4 步是整个事务里唯一触碰 surface 的动作，而它是一次 append。 原始事件一条都没动，只是不再出现在派生历史里。 顺带说一句我读了三遍才接受的地方：这对锁标记只表示"谁在压缩"，不表示"这中间不许别人写"。 摘要还在生成的时候，一个空闲的 inject() 可以往日志里塞不相关的上下文， 所以手动压缩在提交前只重新校验自己选中的那一段，不要求整个 surface 没变过； 自动压缩因为跑在自己的 turn 里，才要求整个 surface 相等。

为什么锁的两端是两条日志事件

compaction/start 在摘要开始之前同步落进日志， compaction/end 是整个事务的最后一条。 所以 surface 变更严格发生在锁内，锁绝不会在变更落地前释放。 在这中间崩溃，留下的是一个可检测的孤儿锁： 一条没有配对 compaction/end 的 compaction/start。 反过来的设计（先改 surface 再记 end）会留下一条谎称"压缩完成了"的记录，而 surface 其实从未被遮蔽。

检查点事件的 sourceEventSeqs 是一条完整的因果链， 真实实现里它长这样（compaction-basic/src/region.ts）：

packages/compaction/compaction-basic/src/region.ts · commitCompactionBody()
session.append('user/message', checkpointMessage, {
  surfaceOp: { op: 'replace', start, end },
  sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs],
})

一条引用同时指向：哪个事务干的、原始摘要文本在哪、以及被遮蔽的每一个节点。 拿着这条检查点，你可以在任何时候把被折叠的六条消息原样翻出来做对照。 落地的替换消息用 <compacted-summary> 标签框住已确立的检查点上下文， 未加框的原始摘要留在 compaction/summary 事件上， 后续的自动压缩周期会把上一个检查点合并进新的摘要。

切在哪：selectCompactableRange

范围选择是头部锚定的：从尾部往前累加 token，直到攒够 retainTokens 的"近期尾巴"， 剩下的头部就是压缩对象。然后有一条硬约束： 绝不切开一个 assistant 的 tool-call 和它对应的 tool/result。 真实实现的写法是把切点往前挪，直到 toolPairingBalancedBefore() 成立； 挪到 0 就返回 null，什么都不做。切开的后果是给模型一个悬空的 tool-call， 大部分 provider 会直接报 400。

换成别的 harness 这一步的分歧落在动词上：splice、移一个指针、还是 append 一条折叠指令。 第一类是把消息列表当状态的：Claude Code、Codex CLI、OpenCode 在模型这一层持有一个可变的 Message[]，压缩作用在那个列表上就是原地替换，换掉的回合不再出现在工作记录里。 它们各自落盘留不留原文，本章没测，能确认的只是模型这一层的形态。 Pi 的落盘格式我也没查，所以它先不进这一格。

omp 不在这一类里。本章原先那句"压缩是破坏性的"对它不成立，这里改过来。 omp 的会话物理上是一份 append-only 的 JSONL，逻辑上索引成一棵 entry 树， 压缩是 append 一条 CompactionEntry：带 firstKeptEntryId 这个边界指针、 带 summary 和 tokensBefore，磁盘上所有原始 entry 原样保留。 它的文档写得很直白：「Only the LLM context resets at the compaction boundary; the scrollback above the divider stays intact, including across session resume.」 TUI 把压缩点画成一条细分隔线，上面标着 compacted 和 ctrl+o，按下去展开摘要。

dsh 这边是 append 一条带 surfaceOp: { op: 'replace', start, end } 的 user/message，原始事件留在原来的 seq 上。 所以"压缩不删原文"不是 dsh 一家的性质，两边都做到了。区别在机制，下面并排放一遍。

边界指针与折叠

两种写法都只往文件尾部加东西，读法不一样。omp 重建上下文时 （buildSessionContext）取活动路径上最后一条压缩 entry，把它变成一条 compactionSummary 消息，然后从 firstKeptEntryId 一路收到压缩点， 再接上后面的 entry。dsh 重建时把整份日志折叠一遍，每条 surface 事件按自己带的 surfaceOp 决定是追加到尾部还是覆盖掉中间一段，折叠完再逐节点投影成消息。

omp · 边界指针 dsh · surfaceOp 折叠 JSONL 里的 entry 全部留在文件里 日志里的事件全部留在日志里 append CompactionEntry append user/message firstKeptEntryId = 4 surfaceOp: replace 2..12 summary / tokensBefore sourceEventSeqs: [start, summary, 被遮蔽的每一个] 重建 = summary + entry 4 起的连续后缀 重建 = foldSurface(整份日志) 后逐节点投影 一次压缩一个切点 replace 可以落在 surface 中间任意一段 切点之前整段丢，之后整段留 nodes 因此可能非单调，例如 [40, 24, 27]

后果落在两个地方。边界指针每次压缩只留一个切点，切点之前整段丢、之后整段留， 重建出来的上下文永远是一段摘要加一条线性前缀；能出错的地方少，读日志的人不必知道折叠规则。 折叠这一侧，start 与 end 是 surface 上两个真实存在的节点， 所以替换可以落在中间任意一段（后面 pruneToolResults() 的头尾裁剪就是这么一次替换）， 而且同一份日志能被不同消费者按不同规则重算：转录稿走 isAppendSurfaceEvent()， 跟模型视图不是同一次折叠。dsh 能从一份日志派生出十几个投影，出处就在这里。

第一列按架构归类，不等于对某个产品的逐项测评：这几家在模型这一层都是消息列表， 所以落到同一格。各自具体怎么压缩、落盘留不留原文，得看各自的实现，本章没测。 flaburgan 在那条 HN 线程里提的正是这件事，同模型同 prompt 的横向质量对比目前没有人做， 本书也没有。omp 那一列不一样，它每一格都对着 omp 自己的文档写，出处在 §5.8 的清单里。

这一格 dsh 落后：snapcompact omp 的默认压缩策略不调模型。被丢弃的那段历史先序列化、压掉空白， 然后用内置的公版点阵字体打印到 PNG 帧上，让视觉模型当图片读回去。 字形和帧尺寸按当前模型的图像计费公式挑：Claude 是 8x13 字形走 11px 步进 （11on16-bw，Opus 4.7 以后的高分辨率线用 1932px 帧，压在 Anthropic 4784 视觉 token 的上限里）； Gemini 是同样字形走 22px 行距、帧宽 2048px，因为 Gemini 3.x 对任意尺寸的图片都按固定 1120 token 计费； GPT 和 Codex 用同一个字形但停在 1568px，它们按面积计费，帧再大换不来更多字符。

整条路径不碰模型，也不要 API key 和网络，所以上下文溢出恢复的时候它照样能跑。 条件是当前模型的 model.input 含 "image"， 不支持视觉就退回 context-full 并发一条警告。

dsh 的五步事务里第 2 步是 summarizes the range，一次真实的模型调用，会花钱也会写错。 这一格上 dsh 落后。确定性的本地渲染和一次摘要请求，成本结构不一样。
omp://compaction.md · Snapcompact strategy

顺着这条线还有一件 dsh 没有的事：omp 的日志里可以有分支。checkpoint 在当前 entry 上打一个标记，之后 rewind 在 turn 结束时调 branchWithSummary(checkpointEntryId, report)，在标记处 append 一条 branch_summary 并把 leaf 移回去。被放弃的那段探索留在同一个 JSONL 文件里， 只是离开了活动分支：下次重建上下文时它不进模型请求，而 /tree 还能导航回去。 dsh 这一侧有 fork 和 resume，一份日志内部没有分支指针，也没有树内导航。 omp 的这对工具默认是关的（checkpoint.enabled 默认 false）。

这条边界在 dsh 自己的依赖里 dsh 的多 provider 适配器 packages/llm/llm-pi-ai 依赖 @earendil-works/pi-ai，也就是 Pi 的模型层。toPiContext(options) 收到的 options.messages 正是 deriveMessages() 的输出， 它把这个数组翻译成 pi-ai 的 { systemPrompt, messages, tools }。 翻译里有两处能说明形态差异：pi-ai 的每条消息都带 timestamp， 而 dsh 的时间长在事件上，所以适配器一律填 timestamp: 0； pi-ai 的 role: 'toolResult' 要工具名，dsh 的 tool-result block 只有 toolCallId，适配器得回头扫前面的 assistant 消息把名字找回来。

这条线还连着 omp。omp 是 pi-mono 的下游 fork，上游同步锚点是 2026-03-22 的 commit b21b42d，包 scope 从 @mariozechner/pi-* 映射成 @oh-my-pi/pi-*。模型层这一块，dsh、omp、Pi 三家同源。

工具结果裁剪：不需要模型的那种压缩

在摘要压缩之前，还有一层更便宜的： packages/compaction/compaction-tool-result-pruner/。 它是确定性的、不调模型的，只做一件事：把超预算的工具结果换成 头部 + 标记 + 尾部。默认预算是：

compaction-tool-result-pruner/src/config.ts
export const PRUNE_MARKER = '\n\n[... tool result middle pruned ...]\n\n'

export const DEFAULTS: ResolvedConfig = deepFreeze({
  thresholdChars: 8192,
  headChars: 4096,
  tailChars: 1024,
})
// 配置校验保证 headChars + marker + tailChars <= thresholdChars，
// 否则"裁剪"可能反而变长。

三个不显眼但重要的实现选择：

  • 按 Unicode code point 切，不按 UTF-16 code unit。用 Array.from(text) 取代 text.slice()，所以保留边界不会劈开一个代理对。 源码里明说了 grapheme cluster 仍然可能被切开，这是写下来的已知取舍。
  • replace 只允许改 content。assertToolResultRewrite 把原事件和替换事件的 content 都置空，然后做结构化深比较：callId、isError、 meta 只要有一处不同就拒绝。裁剪不能顺手改掉工具结果的身份。
  • 影子定价协议。每个替换前面紧挨着一条 compaction/prune， 记下被遮蔽节点的 token 估价，这样纯函数式的消费者可以直接做减法，不必自己维护每节点状态。

§5.6铁律：Model-visible ⟺ logged

Model-visible means logged. Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it. This is why a new model-visible input requires a new session event: extend SessionEventMap and render from the log.
docs/architecture.md · Session log

这条规则有运行时断言撑着。 packages/core/agent-loop/src/invariant.ts 往 llm/stream 这个瀑布事件上挂了一个 listener，把每一个由 loop 构造的请求 和当时的日志对一遍：

packages/core/agent-loop/src/invariant.ts · 真实实现（节选）
// Prepend prevents a short-circuiting replay listener from silencing the check.
ctx.on('llm/stream', (options: GenerateOptions, next) => {
  if (!isAgentLoopRequest(options)) return next()
  if (!Object.isFrozen(options)) fail('a loop-built request must be frozen')
  if (options.sessionId === undefined) fail('a loop-built request must carry a session id')
  const session = ctx.sessions.get(options.sessionId)
  if (!Object.isFrozen(options.messages)) {
    fail('a loop-built request must carry a frozen messages array')
  }

  const events = session.events
  if (!events.some(event => event.type === 'step/start')) {
    return fail('a loop-built request with no step/start in its session log')
  }
  const header = foldRequestHeader(events)
  if (header === undefined) {
    return fail('a loop-built request with no request/header event in its session log')
  }
  const expected = session.deriveMessages()
  if (JSON.stringify(options.messages) !== JSON.stringify(expected)) {
    fail(`llm request for session "..." diverges from the dispatch-time durable
          derivation (log-reconstruction desync)`)
  }
  // ... 再比一遍 model / system / temperature / maxTokens / stop / tools
  return next()
}, { global: true, prepend: true })

注意那个 prepend: true。瀑布事件的 listener 可以不调 next() 直接短路整条链 （第 4 章的内容），所以校验必须挂在最前面，否则一个重放 listener 就能让不变量哑掉。

它带来的直接后果，是一条对日常开发很有约束力的规则：

每一个新的模型可见输入，都必须先有一个 session event 想给模型看一段 skill 内容、一条文件变更通知、一份子目录的 AGENTS.md、 一个子 agent 的回报、一次 cron 通知？ 不能在组装请求的时候临时拼一段字符串进去。 正确路径是：扩展 SessionEventMap，append 一条事件，然后让请求从日志渲染出来。 这也解释了为什么 user/message 的 payload 带一个 source 字段： 真人提示、agent.inject() 的合成上下文、目标续跑，三者的 content 都逐字投影，靠 source 区分。

反方向同样成立，而且同样重要：

The web layer is pure presentation. Nothing that is "how to draw" (tool-card views, queue states) enters the session log; the host computes such data per frame or pushes it live, and replay recomputes it.
packages/client/AGENTS.md

这个等价关系两边都不能松。左边松了，请求里会出现查不到来源的内容。 右边松了，日志会被 UI 状态污染，最后长成一个没人敢改的东西。

代价，一并写清 只追加的日志不是免费的，四笔账。

第一笔是字节。assistant/chunk 的量最大，所以默认后端 session-persistence-jsonl 的 DEFAULT_COMPRESSION 直接是 'zstd'。我第一次跑 dsh 就死在这上面：npx 拿到了 Homebrew 的 Node v23.6.0，那个版本没有 zlib.createZstdDecompress， zstd-private-decoder.ts 在顶层 import 就抛 SyntaxError， 栈埋在插件加载器里，看上去像是 dsh 自己写错了语法。发布的包没有声明 engines， npm 一句提示都没给。换到 Node v25.8.1 之后 474ms 启动。

第二笔是手续费。想让模型多看一段内容，你得先加一个事件类型：改 SessionEventMap， 可能还要配一个 invariant 和一个 projection。这条路堵得很死，是设计意图， 也是每次都要付的成本。

第三笔是词汇表。44 个类型里凡是没标 ignorable 的都是"必须理解"， 读者遇到不认识的就拒绝整个会话， 而词汇表由插件扩展，这个数字只会涨。SESSION_FORMAT_VERSION 还钉在 0， 不兼容的日志直接拒绝，不提供迁移。

第四笔是断言的强制力，它取决于组装。上面那段检查没有内建在 loop 里， 它是 @deepseek-ai/dsh-agent-loop/invariant 这个 companion 插件， 由 ctx.invariants 注册（服务默认 enabled: true）。 组装方不加载它，或者往 package_blocklist 里写一条正则，检查就消失， 而请求照样发得出去。

§5.7本章的产物

mini-dsh v0.5 的核心是一个只有 append 一个写方法的对象。 所有校验都堆在 append 处，理由和真实实现一样：日志是持久的事实来源， 坏事件得在写入点就炸，不能等到某个后端 flush 的时候才发现。

mini-dsh v0.5 · createSessionLog()

本章造出来的全部东西，以及它们分别对应 §5.1 的哪一伤：

函数作用偿还
createSessionLog()只追加日志，append 处做全部准入校验三伤全部
deriveEventMessage()单事件 → 消息，或 nullUI 重放
foldSurface()重放 surfaceOp，算出当前 surface 与替换史压缩摧毁证据

下一章预告 现在谁拿到 log 都能直接写 tool/result：没有权限、没有审批、没有并发模型。 第 6 章把工具执行做成一条流水线，tool/call 和 tool/result 只能由 ctx.tools.execute() 产生；同时 SessionLog 会从一个裸对象 变成 ctx.sessions 这个 Service，从而拿到 Service Definition / Provider / Consumer 这套能力接缝：换一个 provider，bash、PTY、LSP 一起换到远端沙箱里去。

§5.8回到真实的 dsh

真实实现的对应签名，逐个对照我们写的东西：

packages/core/session/src/index.ts · Session（真实签名，节选）
class Session {
  /** 下一条事件的 seq，永远等于日志长度（seq = log.length 契约） */
  get seq(): number

  /** 冻结的日志快照；surface 事件必须带 SurfaceIntent，非 surface 事件带了编译不过 */
  append<T extends SessionEventType>(
    type: T,
    data: SessionEventMap[T],
    ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent] : []
  ): SessionEvent<T>

  /** 增量维护的有序 surface 视图：nodes + replaceGeneration */
  readonly surface: SessionSurface

  /** 每个节点只投影一次；generation 变化则整体重建 */
  deriveMessages(): Message[]

  /** 最新 request/header 折叠出的请求配置 */
  requestHeader(): EpochHeader | undefined

  /** 构造 seed 结束的位置：这个位置之前的事件来自 resume / fork / replay */
  readonly firstLiveSeq: number
}

几个真实实现里存在、我们刻意省掉的东西：

  • SurfaceManager.validateNext(event) 是增量校验。我们的 append 每次把整份日志重折一遍（O(n²)，40 条事件无所谓）；真实实现先在不改状态的前提下 把这次转换"计划"出来（planSurfaceEvent），验证通过再原子提交 （applySurfacePlan）。一条坏事件因此留不下半个状态。
  • deriveMessages() 返回的数组每次都是新的，后来的 append 不会长进调用方 已经持有的那个数组。但里面的 Message 对象是共享且深冻结的， 它们复用日志里已经冻结的 event data，所以缓存不必做第二次深拷贝， 消费者也改不动日志。
  • chunk-rows.ts 的 packChunkRuns 把连续的 assistant/chunk 打包成行，因为它是数量最大的事件类型。 打包之后 seq 的连续性契约保持不变。
  • repair.ts 的 interruptedTurnClosers 为进程崩溃时没关掉的 turn 合成缺失的 step/end 与 turn/end， 并用 TOOL_NOT_STARTED / TOOL_OUTCOME_UNKNOWN 补上没有结果的工具调用。顺序有讲究：step 的边界必须在 turn 的边界之前合成。
  • @deepseek-ai/dsh-session/invariant 才检查 seq 单调、turn/step 闭合、 同 step 内 tool call/result 配对，加载时会重放已有会话。存储校验、快照、冻结、 被引用的源事件校验和 surface 准入，是根包永远开启的责任。 每个插件自己拥有它 merge 进来的事件的关系不变量：todo/write 的校验在 tool-todo/src/invariant.ts，plan/mode 的在 plan-mode/src/invariant.ts。
  • surface 之外还有 projection。todo 列表、plan 状态这类 UI 状态是从日志另外 折叠出来的单元（ctx.sessionProjections）：todo 的规则是"最新一次整表写入， 被下一个 turn/start 清空"，plan 的是"最后一条 plan/mode 胜出"。 这个 build 里一共注册了 13 个这样的单元，同一份日志，互不干扰。
