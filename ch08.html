第 08 章

Code Mode

一次工具调用换一次模型往返。一个五步的调查就要五次往返，而且每一份中间结果都会永久留在 context 里。 Code Mode 把这五次压成一次：模型不发工具调用了，它写一段 TypeScript 程序，程序在 harness 里跑， 只有它 return 或者打印出来的东西回到对话。

本章造出 run_code + 生成的 SDK4 个 demo约 26 分钟

§8.1往返次数就是延迟

第 1 章那个 miniLoop，一路到第 7 章都保持着同一个形状：一个 step = 一次模型请求 + 这次请求触发的工具调用。 代价就藏在形状里。模型只能在 step 边界上做决定，于是任何"看到 A 之后才知道要去看 B"的活儿， 都要多付一次完整的模型往返。

拿一个具体任务：一个 monorepo 里有若干 package，每个 package 的 package.json 用 docs 字段声明自己的文档路径，找出哪些文档缺少 ## Model Experience 段落。 依赖链是三层：目录列表 → 每个 package 的 manifest → manifest 指向的文档。

native mode code mode ┌─────────┐ ┌─────────┐ │ model │ ① bash ls packages │ model │ ① run_code(program) └─────────┘ └─────────┘ ↓ 结果全文进 context ↓ ┌─────────┐ ┌──────────────────────────┐ │ model │ ② 3× read package.json │ program（一次往返之内） │ └─────────┘ │ bash ls │ ↓ 三份结果全文进 context │ 3× read ─┐ 并发 │ ┌─────────┐ │ 3× read ─┘ │ │ model │ ③ 3× read README │ return { missing } │ └─────────┘ └──────────────────────────┘ ↓ 三份结果全文进 context ↓ 只有 return 的值进 context ┌─────────┐ ┌─────────┐ │ model │ ④ 最终答复 │ model │ ② 最终答复 └─────────┘ └─────────┘ 4 次模型请求 · 7 份工具结果进 context 2 次模型请求 · 1 份 curated 结果

左边为什么是 4 次而不是 7 次：native 模式下并行分发是有的，同一个 step 里的三个 read 会在池子里重叠跑。往返次数等于依赖链的深度，跟工具调用总数没关系。 并行分发省的是墙上时钟，省不了往返。dsh 自己的设计笔记把这两件事分得很清楚：

Parallel native dispatch in the loop. The other answer to round-trip cost at decision time; it was blocked on concurrency-safety metadata and offers no composition either way — it parallelizes calls the model already decided on in one step.

第二个代价更贵，而且不可逆。native 模式下每一份中间结果都会进入 context，然后一直留在那里。 上面那七次调用里有六份是文件全文，模型真正需要的只是"哪个文件缺段落"这一句话。 Code Mode 下过滤发生在程序里，模型只看到 { checked: 3, missing: ["packages/probe/README.md"] }。

下面这个 demo 把两种模式并排跑起来。两边用的是同一套 mini 工具、同一个 mini 仓库、同一个调度器， 唯一的差别是 presentation。跑之前先押一个数：

读数怎么看 墙上时钟只差不到两倍，因为工具本身的延迟两边一样，程序不会让磁盘变快。 被压下来的是另外两行：模型请求次数，和进入 context 的字符数。前者是延迟里最贵的一项， 一次请求几百毫秒到几秒；后者是永久成本，它跟着会话一路涨到压缩阈值。 右栏那几行 #n 工具 exc|par start→settle 是程序内部真实的 dispatch 时间线： bash 独占跑完，三个 read 才重叠进来。§8.4 解释这个分类是谁定的。
换成别的 harness 没有 code mode 的 harness 只能按左栏跑。一个"读五个文件、再 grep 一遍"的调查就是五次模型往返， 五份完整结果永久占着 context，一份都退不掉。上面 demo 里这个任务的依赖链是三层、七次调用， native 侧付掉 4 次请求和 2481 个字符，code 侧是 2 次和 623 个字符。 终端型 harness 走的是另一条省法：Pi 只带 read / write / edit / bash 四个内置工具， system prompt 压得很短，省的是每一次往返的单价。客户端-服务端分离的 harness （OpenCode 那种 Go server 持有执行生命周期、对外开一个 OpenAPI 端点的形状）换掉的是谁来驱动会话。 两条路都不动"一次工具调用换一次往返"这条账。omp 动这条账，它有一个叫 eval 的工具， 包装的选择跟 dsh 正好相反，下一节讲。

§8.2presentation 是一行 preset 配置

Code Mode 在 dsh 里没有全局开关。第 7 章把整个产品降维成一棵可打补丁的配置树， 每个 agent 挂载自己的插件子树；Code Mode 就是那棵子树上的一行：

apps/cli/config/agent-presets/code/agent.cordis.yml · 真实文件的最后七行
# ── presentation ────────────────────────────────────────────────────────────

# Code Mode for this agent alone. The row waits for the host's `codeRuntime`
# rather than assuming it: a deployment that composes no TypeScript runtime
# fails this preset at mount, naming this id, instead of at the first request.
- id: tool-presentation
  name: '@deepseek-ai/dsh-agent-tool-presentation'
  config:
    mode: code

code preset 和 standard preset 的全部差别就是这一行。为什么它是 preset 里的一行， 而不是一个新的 registry？registry 搬不下来：agent loop 要读它的 scheduler， apiproxy 要读它的 presenter 去渲染工具卡片，每个工具插件都往它里面注册。 一个 service 只有在它所有的消费者都跟着下移时才能下移。preset 能拥有的是这个 registry 的 presentation：

What a preset can own is the presentation of that registry. ctx.tools.presentAs() declares it for the mounting agent alone, so a Code Mode session runs beside native ones in one process, each seeing its own catalog.

"同一个进程里并排" 是字面意思。一个部署可以同时跑三种 agent：主 agent 走 native， 一个调查型 subagent 走 code，一个混合 agent 走 both。它们共享一个 registry 实例、一个沙箱、一份持久化， 各自看到的 catalog 不同而已。mode 没有默认值，必填，理由很干脆： 没写这一行的 preset 已经拿到部署默认值了，再给它一个可省略的值，等于让这一行白组合。 一个 composition 里出现第二次声明会被拒绝，不合并。"模型看到哪种形态"有两个答案，那是矛盾，不是覆盖。

换成别的 harness 让模型写程序去调工具这件事，dsh 不是首创，也不归它独有。Anthropic 出过一个跑代码的工具， Cloudflare 把 code mode 这个说法写成了模式文章，omp 有一个叫 eval 的工具。 少见的是收紧那一步。前两条路上，"这个 agent 面对的是一张工具表还是一份 SDK" 由工具作者或者部署决定，一个进程一种答案；omp 那边谁都不决定，两个入口一直摆着， 模型每一轮自己挑。dsh 把这个决定压成 per-agent preset 里的一行 mode: code， 于是一个 code mode 会话能和 native 会话在同一个进程里并排跑，共享同一个 registry 实例。 收紧也在同一行付掉：code 之下，registry 把直呼任何其他工具解析成 UNKNOWN_TOOL， 宣告的表面和可调用的表面因此没法分叉。
omp 的 eval omp 里对应的工具叫 eval，它和另外三十个内置工具并列站着，approval="exec"， 一个会话里 concurrency="exclusive"。它不收紧任何东西。一次调用是一个 cell， 状态活到下一次调用，py / js / rb / jl 四种语言各留一份自己的状态。工具触达靠 prelude 注入：tool.<name>(args)， 连同 display()、read()、write()、completion()、 agent()、parallel()、pipeline() 一起进运行时。 那边没有按工作区生成的静态 TypeScript SDK 文件，prelude 是运行时注入的， 所以也就没有 ToolOutputMap 这一半。 两边各自让掉了一样东西。omp 留着逃生口：模型只需要读一个文件的时候， 发一次普通的 read 就完事，不必先写程序；跨调用的持久 kernel 和四种语言也一起归它。 dsh 把入口收成一个，换到的是一段整会话不变的请求前缀，以及"宣告的表面等于可调用的表面" 这条由 executor 兜住的保证；付出的是那一行读文件也得包一层程序的开销。
这个决定写在哪工具层部署层omp：并列的一个工具dsh：preset 里一行
谁做决定工具作者运维、启动参数模型每一轮自己挑agent 的 preset 组合
同进程并存两种形态部分：两个入口都在，谁都没被收紧无：一个进程一种答案有：每个会话都同时有两个入口有：按 agent 各看各的 catalog
直呼其他工具会失败无部分：粒度到不了单个 agent无：三十个工具照常可调有：UNKNOWN_TOOL
SDK 带输出类型看工具看实现无：prelude 运行时注入，不生成声明文件有：output schema 必填，投影成 ToolOutputMap
持久 kernel看实现看实现有：一次调用一个 cell，状态留到下次无：每次运行开一个新 worker，程序的世界随它一起死

宣告的表面必须等于可调用的表面

这里有个容易做错的地方。假设你只改 prompt：把 native schema 换成 SDK 文本，registry 的执行入口没动。 模型偶尔还是会发一个原生的 read 调用，它见过太多这样的训练数据，而 registry 会老老实实执行。 这时候你有两个表面，宣告的那个只有 run_code，实际可调用的那个是全部。 两个表面对不上的系统没法推理。

dsh 让 presentation 同时决定能执行什么。判定函数只有一行，值得整段抄下来：

packages/core/tools/src/index.ts · 真实实现
private collapses(name: string, scope: ScopeKey | undefined, nested: boolean): boolean {
  return !nested && this.modeFor(scope) === 'code' && name !== RUN_CODE_NAME
}

// resolveExecution 在策略流水线之前就用它做决定：
// 视图（get）与 presentation 无关；collapse 归属于操作边界，也就是这里。
private resolveExecution(name, scope, nested): ToolDefinition | undefined {
  const tool = this.get(name, scope)
  if (tool === undefined) return undefined
  if (this.collapses(name, scope, nested)) return undefined
  return tool
}

三个连接词各有分工。!nested 放过程序内部发出的子调用，也就是下一节的主题。 mode === 'code' 让 both 模式下的原生调用照常执行；both 之下这条规则为假， 那条 prompt 规则也跟着渲染成空字符串。name !== RUN_CODE_NAME 留下唯一的入口。 被拒绝的调用返回 UNKNOWN_TOOL，和"这个工具根本没注册"是同一个错误码， 因为对模型来说这两件事的含义就该一样。

还有个细节：prompt 里那句"只有 run_code 能直接调"用的是和 executor 同一个谓词， 所以 prompt 不可能声明一条 registry 不执行的规则。它的真实文本是：

packages/core/tools/src/index.ts · CODE_ONLY_INSTRUCTION（section 顺序 99，排在所有 per-tool guidance 之前）
`run_code` is the only tool you can call directly — a tool call naming any other
tool fails. Reach every tool the SDK declares below from inside the program.

顺序 99 是刻意的。每个工具插件都注册自己的 guidance 段，顺序 100-199， 它们讲的都是"用 read 工具而不要 cat"这类事，谁都不会说明这个工具怎么触达。 collapse 规则要是排在它们后面，模型就会先读完一整册"该用这些工具"， 然后才读到"但你一个都不能直接调"。

KV cache presentation 在 agent 被组合的那一刻就定下来，整个会话生命周期内不变， 所以请求前缀是稳定的：这一行配置不制造任何 cache 失效。 这也是它必须落在 preset 组合期、不能做成运行时开关的另一个理由。 会话中途把 catalog 从 12 个 schema 换成 1 个，等于把整段前缀作废。

三处值得停下来看：

一、每个字段都带 JSDoc，而且是原始 description

参数的描述不是重新写的，它就是 JSON Schema 里那份 description，被搬到了 JSDoc 里。 所以 bash 的参数在 SDK 里长这样（真实快照第 44-59 行的一部分）：

system-prompt.expected.md · 节选
  bash: {
    /** The bash command to execute. */
    command: string;
    /** Clear, concise description of what this command does in active voice, 5-10 words
        (shown in the UI). Examples: "ls" → "List files in current directory"; ... */
    description: string;
    /** Timeout in milliseconds. The executor applies its configured default and cap,
        and kills the command on expiry. */
    timeoutMs?: number;
    ...
  } & Record<string, JsonValue>;

末尾那个 & Record<string, JsonValue> 不是装饰。参数 schema 没有声明 additionalProperties: false（工具自己做校验），所以渲染器诚实地把它渲染成开放对象； 而输出 schema 声明了 additionalProperties: false，所以输出侧没有这个交叉类型。 类型文本忠实反映 schema，不做美化。

二、输出侧被完整类型化了

大部分 code mode 实现会跳过这一半。给参数生成类型很容易，JSON Schema 本来就在那里。 给返回值生成类型，要求每个工具都声明一份规范输出 schema，这是工具作者要付的税。 dsh 收了这笔税：ToolDefinition 的 output { schema, render } 是必填的。 回报是 ToolOutputMap 里那些具体到 { kind: "background"; jobId: string } | { kind: "foreground"; exitCode: number | null; ... } 的联合类型。模型写 result.stdout.text 的时候知道自己在写什么，不用对着 any 猜。

顺带一个不对称：原生 schema 投影里没有 output，模型看到的只有 name / description / parameters，只有 SDK 投影带上它。 "输出有类型"这件事只有 SDK 这个投影给得出来。

三、ToolCallError 携带 toolName

程序里的一次失败必须能被程序自己处理，否则整段程序白跑。所以失败以异常形态出现， 并且带上是哪个工具失败了。真实链路：host 端把工具的错误结果变成绑定层的 rejection， worker 端把它包装成一个真正的 ToolCallError 实例，只附加工具名。 原生的 content 和内部错误元数据不进入程序可见的失败契约。这个 class 是运行时按请求数据现场物化的：

Binding rejection classes are request data — an optional namespace descriptor names the constructor global and the own property that receives the failed member name. The worker materializes and injects that real class, so instanceof works without hardcoding tools or ToolCallError.

换句话说，code-runtime 这个 seam 完全不知道"工具"是什么。 Code Mode 交给它的是 { global: 'tools', functions, errorClass: { name: 'ToolCallError', memberNameProperty: 'toolName' } }， 运行时照着造。第 6 章那套能力接缝的又一次应用。

§8.4嵌套调用不是后门

最容易想错的一件事：程序能直接拿到工具函数，那它是不是绕过了权限、沙箱、审批、超时？没有。 collapses 里的 !nested 只放过入口检查，放过之后调用照样从头走一遍 第 6 章那条完整的守卫流水线。

程序里的一次 await tools.read(...) │ ├─ jsonNormalizeArgs 参数必须是无损 JSON（undefined / BigInt / 循环 → 这一次调用被拒） ├─ 排入 per-run 调度器 按提交顺序，classify 为 parallel / exclusive ├─ prepare pre-execute 守卫：权限、沙箱、审批 ← 有序阶段 ├─ dispatch 工具主体 + 超时 ← 只有这一段并发 ├─ finalize post-execute、additionalContexts、concludesTurn ← 有序阶段 └─ settle tool/code-dispatch 事件写进会话日志

这条链和 native 调用走的是同一个 registry、同一批 pre-execute 监听器、同一个沙箱后端。 dsh 自己的说法是 "Code Mode uses the same tools/pre-execute policy gate as bash"。 一个越界的写入在程序里被拒绝，和它在 native 调用里被拒绝，是完全一样的拒绝。

并发遵守原生规则，不遵守 Promise.all

另一个容易想错的地方。Promise.all 只表达"我不在乎顺序"，它不授予并发权限。 能不能重叠由工具自己声明：

分类条件调度
parallelisConcurrencySafe(args) 恰好返回 true与相邻的 parallel 调用重叠，上限 maxParallelSubCalls（默认 10）
exclusive未声明、返回非 true、参数无效、分类器抛异常先排空池子，独占运行，直到 commit 完成 才放开屏障

真实 dsh 里 read 声明了 isConcurrencySafe: () => true，注释写得很清楚： "Observation races fail closed because guarded mutations re-check the version in-lock"。 web_search / web_fetch / subagent 和 session-query 那几个也声明了。 bash 没有声明，write / edit 也没有。所以一段 Promise.all([tools.bash(a), tools.bash(b)]) 在真实 dsh 里是串行跑的，一个接一个，按提交顺序。 模型大概会对这一点期望过高，dsh 自己把它列成了已知风险：

Sub-dispatch overlap is bounded by tool safety claims, not by the caller. A program's Promise.all or asyncio.gather buys wall-clock parallelism only across calls the tool itself classifies concurrency-safe; a run of exclusive calls still costs its round-trips in sequence, and models may over-expect.

启动严格按提交顺序，结果也按提交顺序 commit，一个 head-of-line 游标。 分类在每次启动前重新读一遍，因为一个调用排队期间 registry 可能被改动，把它翻成 exclusive； 读不到就 fail-closed 判 exclusive。这些规则不是 Code Mode 新发明的，它复用的是 agent loop 里那套原生调度契约。

下面这个 demo 真的在执行你输入的程序，没有 setTimeout 表演。 程序体被交给一个 AsyncFunction，参数是注入的 tools / console / ToolCallError， 真实 worker 里也是这么做的，每一次 await tools.x(...) 都真的排进上面那个调度器。 两个预设按钮会把程序填进编辑框，填进去之后随便改：把 Promise.all 换成 for 循环， 看时间线怎么变；把某个路径写错，看 ToolCallError 怎么被 catch 住； 或者把 console.log 那一行删掉，看模型的视野少了什么。

"填一段越界写入" 那段程序试着写 /etc/hosts。沙箱守卫在 pre-execute 阶段拒绝， 拒绝变成程序里的一个 ToolCallError，程序 catch 住继续跑。 "嵌套调用不是后门"的完整含义就是这个：能力没有变宽，变的只有触达路径。

§8.5代价

这些收益是要付钱的。四项代价，前三项在真实 dsh 里也没有被消掉。

一、炸在中途，副作用留在原地

native 模式下每一次工具调用都是独立的、被完整记录的、原子的事件。模型看到第 3 次成功、第 4 次失败， 它精确知道世界处在什么状态。程序不这样。一段程序写了三个文件然后在第四步炸掉， 模型收到的是 code run failed (exception): ... 加上程序打印过的东西， 那三个文件到底改了没有，得它自己推断。

点一下上面 demo 的"写一段会炸的程序"：文件系统里真的多了三个文件，模型的结果里只有一条失败信息， 加上程序自己 console.log 出来的三行。demo 把这两边逐个对了一遍， 告诉你哪几个副作用落在模型视野里。然后把那行 console.log 删掉再跑一次，对账会翻面。 可见的副作用只有程序打印过的那些。

dsh 在这里做了一件缓解：每一次子调用都单独写一条 tool/code-dispatch 事件进会话日志， 带上参数、结果、是否失败，所以回放和排查是可能的，第 5 章那本只追加日志在这里付了利息。 但那是给人和给工具看的，不进模型 context。

二、错误处理的责任转移给了模型

native 模式下一次工具失败会作为一条 tool_result 回到模型面前，模型下一个 step 自然就看到了， 重试逻辑是循环免费给的。Code Mode 下失败是程序里的一个 rejection，模型必须在写程序的时候就想好要不要 try/catch。没 catch，整段程序死掉，前面所有成功调用的结果一起丢失，它们从没进过 context。 SDK 说明里那一条被写成大写的 A FAILED tool call rejects with ToolCallError，就是为这个。

三、排查比一串工具调用难

一条 native 工具调用轨迹是自解释的：谁调了什么，返回了什么，一行一条。 一段程序的失败是一个 stack trace，行号指向模型自己写的代码。 dsh 为此保证 type-strip 是位置保持的（"position-preserving, so runtime error line numbers match the model's source"），这样 stack trace 里的行号还能对上模型写的那一版源码。 不小的工程量，只为了让报错可读。

四、common case 会被抽税

这条是 dsh 明确拒绝走 Cloudflare 原教旨路线的理由。一个编码 agent 大量的工作是"读一个文件"、"改一行"、 "跑一次测试"，这些本来就是理想的单次原生调用。强迫每一次 edit 都包一层程序， 是给最常见的情况加税：

Always-exclusive (Cloudflare-faithful, no mode). Rejected for this SDK's primary consumer: a coding agent's bread-and-butter single calls (bash, read, edit) are already ideal as native calls, and forcing every edit through a program taxes the common case. The mode config keeps the faithful form ('code') one line away without imposing it.

所以 mode 有三个值。both 存在的意义就在这儿：常见动作走原生， 需要组合、循环、分支、join 的时候写程序。代价是模型多了一个"该走哪条路"的决定要做。

omp 把这条论证走到了尽头：那边没有 mode 这个东西，eval 永远只是一个工具， 常见动作永远是原生调用。"该走哪条路"的决定它也一直在付，付得不显眼而已， 因为两个入口从来没有一个被关掉过。

加到 mini-dsh 上的东西有三块：一个 presentation 选择器（wireSchemas + collapses）、 一个 SDK 生成器（renderToolsSdk，上面 §8.3 已经列过）、 一个 run_code transport 加它自己的有序调度车道。核心是后者：

我们的 mini 版本刻意省掉的东西：

  • 没有隔离。我们的 AsyncFunction 和页面共享一个 realm，能看到 window。 真实实现每次运行开一个全新的 worker_threads.Worker：env: {}、execArgv: []、 resourceLimits 堆上限、不池化，"a program's world dies with its worker"。 官方说得很直白，这是 containment，不构成 security boundary，信任姿态和 bash 工具等价。
  • 没有 type stripping。真实实现在 host 侧用 node:module 的 stripTypeScriptTypes 剥类型（erasable syntax only，enum 和 namespace 直接被拒绝并 作为程序 exception 返回），我们的 demo 把程序体当纯 JS 解析，所以写了类型标注会语法错误。
  • 没有预算。真实实现有三道独立预算：computeMs 计的是 worker 的 实测忙碌时间（用 eventLoopUtilization() 每 25ms 采样，所以死循环藏不到一个 pending 的诱饵调用后面， 而等一个慢工具不计费）、maxWallMs 兜住忙碌时间看不见的东西（等一个没人 resolve 的 promise）、 maxOutputBytes（默认 64 MiB）只管外层输出。
  • 没有敌意对端假设。真实实现把程序当敌对方：message port 上每一条入站消息都被 形状校验并重建，绑定名只按 own property 解析（伪造的 constructor 走不到原型链上）， worker 侧的命名空间对象是 null-prototype 加 defineProperty 建的， 所以一个叫 __proto__ 的工具是普通的 own key，碰不到原型 setter。
  • read 的返回不一样。真实 read 返回带行号的文本，程序要自己剥行号； 我们的 mini read 直接给原文，为了让 demo 里 JSON.parse(m.text) 能读。
  • 没有 Python flavor。真实实现的 run_code schema 文本是按语言解析的 （RUN_CODE_FLAVORS，读的是已挂载 runtime 的 language）， 两张 per-language 表都用 satisfies 对着 CodeSdkLanguage 检查， 只加一张表会在 typecheck 时炸，而不是等到运行时。
HN 上的一条质疑 发布当天那条 HN 主线程（item 49285244，当天 545 分 234 条评论，两天后 720 分 298 条）里，syntaxing 问了一句很短的话： "Is there a reason why so many of these agent harness are written in node.js?" 放在这一章它有具体的着力点。Code Mode 要跑一段模型现场写的程序，而 dsh 交出来的隔离是 worker_threads，同一个进程里的一条线程，官方文档自己写明这是 containment，不是 security boundary， 信任姿态和 bash 工具一样。CodeRuntime 的 isolation 是个纯描述字符串， well-known 值列了三个（worker-thread / process / container）， 紧跟着一句 "not a security claim"；而 packages/code-runtime/ 下发出来的 provider 只有 worker thread 那一个，language 也只有 typescript 有已发布的后端。 想要一道真边界，自己写 provider。
