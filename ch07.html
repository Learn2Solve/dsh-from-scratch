第 07 章

YAML 组合：profile、bundle、patch、preset

前六章造的东西全是在 JavaScript 里手工接线的。谁先挂、挂什么配置、哪个不要，都写在代码里。 本章把这些接线搬进 YAML，让它变成一份能被逐层打补丁的数据， 再给每个会话挂一棵属于它自己的子树。

本章造出 composeLayers() / mountPreset()3 个 demo · 1 次预测约 26 分钟

§7.1一行配置就是一个插件实例

我们手上现在有 miniLoop、Context 与 Service、 Fiber 与 ctx.effect()、五种事件模式、SessionLog、ctx.tools。 都能跑。但要改变产品形态，你得改 JS：注释掉一个 ctx.plugin(...)， 把一个常量从 'native' 改成 'code'，给某个插件多传一个字段。

真实 dsh 里这些动作全部发生在 YAML 里。一个正在运行的 dsh 就是一棵插件树， 树上每个节点是一行配置，Loader 把它变成一个活着的插件实例。这一行的类型是 EntryOptions，字段少得可以背下来：

字段类型含义
idstring在所属 entry tree 里稳定的标识。补丁按它寻址
namestringentry tree 要 import 的 module specifier
configany传给插件的配置。group 行的 config 是子行列表
groupboolean \| null标记这一行是嵌套 group
disabledboolean \| null阻止这一行及其后代运行
injectInject \| null这一行需要的 service，或 service intercept 配置

另外两个字段由 isolate.ts 用 declare module 挂到同一个接口上， 因为它们是 Loader 的可选能力，不算 entry 的固有属性： intercept?: Dict | null 和 isolate?: Dict<true | string> | null。 isolate 是 §7.4 的主角。

下面是 packages/bundle/base/cordis.patch.yml 里真实的一行：

packages/bundle/base/cordis.patch.yml · 沙箱策略那一行
- id: sandbox-policy
  name: '@deepseek-ai/dsh-sandbox-policy'
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()

这一行说了四件事。它的 id 是 sandbox-policy，所以别的层能按这个名字找到它； 它挂 @deepseek-ai/dsh-sandbox-policy；沙箱模式读环境变量，没设就是 workspace-write；工作区根取进程 cwd。接线本身没有一行 JavaScript。

Entry.update() 的两条路 改一行配置不一定意味着重启插件。Entry.update() 先算出新旧 options 的 diff，然后判断 const replace = diff.some(key => key === 'name' || key === 'inject' || key === 'group')。 只有这三个键变了才重新 import 模块、销毁旧 fiber、启动新 fiber； 只改 config 走的是 _patchContext() 里的 fiber.update(this.options.config, true)， 插件原地收到新配置。apply 失败还会尝试回滚到旧配置，回滚也失败才抛 AggregateError。
group 行永远不 disabled Entry._disabled() 的第一行是 if (options.group) return false， 注释写着 // group is always enabled。 但给一个 group 写 disabled: true 依然能关掉整个子树： 子行判断自己是否 disabled 时会沿 parent.ctx.fiber.entry 往上走， 逐级调用 disabledOf(entry.options)。group 自己那个 fiber 是活的， 里面的东西一个都不跑。

§7.2层叠补丁

一棵树如果只能从一个文件读出来，"官方发行版 + 用户改两行"这件事就没法表达。 用户要么 fork 整个文件，升级时自己解冲突；要么什么都改不了。 dsh 给的是补丁层：起点是一个空的 entry list，每一层往上面叠。

docs/architecture.md 的原话是：

Layers apply to an empty entry list in this order: each bundle in the profile's listed order, then the profile's cordis.patch.yml, then the home-level one, then any --patch overlay. A patch targets a row by id and replaces its whole config, or inserts new rows.
[] <- 空 entry list │ ├─ bundle 1 dsh-base/cordis.patch.yml 一整条 insert：约 60 行 ├─ bundle 2 dsh-web-app/cordis.patch.yml 按 id 覆盖，再 insert 浏览器那一半 │ （bundle 顺序 = profile package.json 的 dsh.profile.bundles 顺序） ├─ profile $DSH_HOME/profiles/web/cordis.patch.yml ├─ home $DSH_HOME/cordis.patch.yml 机器级偏好，所以压过 profile 层 └─ overlay --patch ./a.yml --patch ./b.yml 按 argv 顺序 │ ▼ composed tree ──► Loader 挂载

两个概念要分清。profile 是 Harness home 下的一个命名组合，位置在 $DSH_HOME/profiles/<name>/，里面一个 package.json（它的 dsh.profile.bundles 列出有序的 bundle 层，dependencies 装它自己的外部插件） 加一个用户自己的 cordis.patch.yml。bundle 是一个 npm 包， manifest 里写 "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }。 它分发的是"配置行 + 这些行要挂的代码"，插进来之后依然能被上面的层继续打补丁。

换成别的 harness 每个 harness 都有配置文件，区别在于配置描述的是什么。Claude Code 的 settings.json、 Codex CLI 的 config.toml、还有 CLAUDE.md / AGENTS.md 这类 prose 层， 配的是一个结构在编译期就定好的程序：哪些键可以填、填了会影响什么，由那个程序说了算。 假设你想改内建文件工具的行为，你能做的是加一个 hook 在调用前拦一下、挂一个 MCP server 提供另一个名字的工具、或者在 CLAUDE.md 里写一段话让模型少用它。 配置的词汇表里没有"这个工具由哪个模块实现"这一项，因为那不是配置层能表达的东西。 omp 也在这一类里。它有 settings、models.yml、extensions 和 marketplace； settings 的 config.yml 还能叠内置默认、全局、项目、可重复的 --config overlay 与运行时 flag。对象深合并，数组整块替换。 这些入口不少，叠出来的仍然是那个程序的一张固定键表。 cordis.yml 是另一回事，它就是程序本身。dsh 用户换掉文件工具，写的是 - id: tool-fs 加一行 name: ./my-fs-tools.js， Entry.update() 看到 name 变了就销毁旧 fiber、import 新模块、起新 fiber。 连 agent 主循环也一样：它在 base bundle 里就是一行 id: agent-loop （我这份 clone 里是第 436 行），和 tools、system-prompt 挨着，谁都能打它。

这套设计的代价，HN 第一条高票就问了 发布当天 HN 主线程（item 49285244，当天 545 分 234 条评论，两天后 720 分 298 条，2026-08-13）里票最高的疑问来自 rco8786："But like, what is it? Odd that this reached #1 on HN. The README is pretty bare outside of installation instructions and a link to 'Cordis', which is 'A Meta-Framework of Spatiotemporal Composability.'" 这条质疑和上面那张表是同一件事的两面。能力全在配置里，README 就没什么可写的： 它不能说"我有这十五个工具"，因为工具是哪些取决于你叠了哪几层； 也不能说"我的循环这样跑"，因为循环是一行可以被打掉的配置。 想知道这东西是什么，你得读 cordis.patch.yml，或者跑一次 --dump-config。 新人手上没有那两样东西，落地页上又只有一个抽象名词等着他。

补丁语义只有一个函数，vendor/include/src/index.ts 的 applyEntryPatches()。它的注释开头就写着这是 "THE patch semantics of this include"， 挂载和离线工具（dsh --dump-config）共用同一个实现，所以 dump 出来的树不可能和实际启动的树漂移。 规则逐条列出来：

  • 输入永不被改，输出永远是脱开的。函数第一行是 data = structuredClone(data)， 即使没有任何补丁也照样克隆。原因写在注释里：补丁或挂载共享的 entry 对象会把早先的值烙进缓存的解析结果， 于是配置热重载时"删掉一条补丁"永远无法还原。
  • 寻址表递归建立。buildMap() 收集每一行的 id， 并对 entry.group && Array.isArray(entry.config) 的行递归下去。group 里的行也能被外面按 id 打到。
  • insert 不带 id 就追加到根；带 id 就追加到那个 group 的 config 里。 目标不存在 warn patch insert: entry %C not found，目标不是 group 则 warn patch insert: entry %C is not a group。
  • 插进来的行立刻被索引。insert 分支末尾有一句 buildMap(insert)， 注释说明理由：补丁列表一层一个来源，后面的层必须能配置或关掉前面的层刚插入的行， 否则 "inserted rows were silently unpatchable"。
  • 非 insert 补丁必须有 id。带了 name 而且和目标不符，整条跳过并 warn name mismatch。这道栓拦的是这种情况：你以为在改 A，其实那个 id 已经被别人占了。
  • 覆盖是按键赋值：target[key] = value。而 config 就是一个键， 所以"打一行 config"等于整块替换，不做深合并，要保留的字段必须重写一遍。 dsh-base 的注释把这条约束反推成了组织原则： "a row whose value differs by mode does NOT live here"。
  • 打不中的补丁只 warn，不炸。一次 profile 启动会打几十条补丁， 让一条过时的补丁拖垮整个进程是错的产品行为。

§7.3!!js 与延迟求值

纯数据配置有一个硬伤：有些值要到运行时才知道。端口看命令行，沙箱模式看环境变量， 会话目录看 Harness home 装在哪，而 tool-bash 在 Windows 上根本不该存在。 把这些挪进插件内部，读配置的人就看不出实际值从哪来了；做成模板字符串，又要养一套 DSL。

dsh 走的是第三条路：给 YAML 加一个标签，让标量变成表达式节点。 整个方言就是这一个 yaml.Type：

vendor/include/src/index.ts · 方言的全部
const JsExpr = new yaml.Type('tag:yaml.org,2002:js', {
  kind: 'scalar',
  resolve: (data) => typeof data === 'string',
  construct: (data) => ({ __jsExpr: data }),
  predicate: isJsExpr,
  represent: (data) => data['__jsExpr'],
})

export const entryListSchema = yaml.JSON_SCHEMA.extend(JsExpr)

基底是 JSON_SCHEMA，不是默认 schema，也就是说 YAML 那些花活（yes/no、 时间戳、八进制）都不认，只认 JSON 的类型集合，外加这一个标签。 construct 把 !!js expr 变成 { __jsExpr: 'expr' }， represent 又能把它写回原样。这是能往回写的前提。 Loader 会在它认为配置变了的时候把整棵树写回源文件， 如果表达式在解析时就被求值成了字面量，写回去的文件就把当时那次求值的结果烙死了。

求值发生在什么时候

求值是惰性的、按行的，而且只发生在两个位置。第一个是插件 config， 在 Loader 装的 internal/config 钩子里：

vendor/loader/src/index.ts · 谁的表达式在谁的 fiber 里求值
ctx.on('internal/config', function (this: Fiber, _config, next) {
  const config = next()
  if (!this.entry || this.parent.fiber?.entry === this.entry) return config
  // Tree carriers (Group, Include) keep their configs literal: their
  // entry and patch lists hold other rows' configs, whose `!!js`
  // expressions belong to those rows' own fibers.
  const plugin = this.runtime?.callback as Record<PropertyKey, unknown> | undefined
  if (plugin?.[EntryGroup.key]) return config
  return interpolate(this.ctx, config)
}, { global: true })

两处细节。求值的作用域是这一行自己的 fiber context（this.ctx），不是根 context， 所以 inject: [webStartup] 的行可以写 !!js ctx.webStartup.host ?? '127.0.0.1'，Loader 会等那个 service 存在之后再解析它的表达式。 而 tree carrier（Group、Include）的 config 保持字面量： 它们的 config 装的是别人的 config，那些表达式属于别人的 fiber。

第二个位置是 disabled，它不走 interpolate，走 Entry.disabledOf()：

vendor/loader/src/config/{entry,utils}.ts
// Entry：每次读 entry.disabled 都重新求值，原始节点留在 options 里
private disabledOf(options: EntryOptions): boolean {
  return isJsExpr(options.disabled)
    ? Boolean(this.evaluate(options.disabled.__jsExpr))
    : Boolean(options.disabled)
}

// utils：求值器本体，一共九行
export const evaluate = new Function('ctx', 'expr', `
  with (ctx) {
    return eval(expr)
  }
`) as ((ctx: object, expr: string) => any)

with (ctx) { return eval(expr) } 解释了配置里那些写法为什么都成立。 with 把 context 的成员摊平成裸名字，所以 dshHomePath('sessions') 能直接调 （boot() 把它挂在根 context 上）；而求值器的第一个形参就叫 ctx， 所以 ctx.webStartup.host 也能写。两种风格在真实文件里并存，不是笔误。

这条标签不是藏在实现里的细节，官方教程正面教它。 docs/cordis-tutorial/05-config.md 的原话是 "The loader used in this repo supports a !!js tag for config values that must be computed at load time"， 紧跟的例子就是 greeting: !!js process.env.DEMO_GREETING ?? 'Hello'。 同一页把适用范围也划了出来：!!js 只在 config 里和一个条目的 disabled 字段里生效。后面那一处的分量更重些： disabled 的表达式在每次挂载决策时都会对 loader context 重新求值一遍。

诚实地说清这件事 这是配置求值期的任意代码执行。eval 拿到的是宿主进程的全部权限： 一份 cordis.patch.yml 和一段 JS 脚本的危险性完全相同。 dsh 没有假装它是沙箱，packages/preset/agent-presets/README.md 的 Trust 一节把这个立场写死了："a preset is exactly as privileged as the plugins it names. A user preset — authored by a person or by an agent — carries the same trust as shell access"。 Demo 7.1 上面那个 求值 !!js 按钮跑的就是同一个 new Function('ctx','expr','with (ctx) { return eval(expr) }')， 只不过喂给它的是一个假的 ctx（process.platform = 'darwin'、 dshHomePath() 指向 /Users/you/.dsh/）。

这个立场在发布之后被人当成攻击面认真检了一遍。检出来的东西不推翻上面那段话， 它做的是把上面那段话的后果摆到台面上。

下载来的一份 profile 是没人审过的脚本 一份从别处取来的 profile、或者一个 add 进来的 bundle， 里面的 !!js 会在 load 期跑在你的宿主进程里，权限和你自己敲一行 node 完全一样。 Fz0x00 的插件安全审计把这条路径做成了可复现的 demo： demo-01-js-config-rce 落下一个标记文件，内容是 PWNED-BY-LIVE-JS。 那份报告钉在 commit 47f9438，正是本书对照的这个快照，活体验证跑在 @deepseek-ai/dsh@0.1.0-rc.6 上。它另外记了两件周边的事： dsh plugin add 字面上就是一次没有签名的 pnpm add， 而 dsh plugin remove 不会移除一个已经写进配置里的 !!js 后门。 前提也得说清楚：这条路要你自己去 add 那份 profile 或 bundle，不是零点击的远程 RCE。

读这份审计得连着它自己的分轴一起读，不然容易读成"dsh 不安全"。它把仓库切成两半。 面向模型和 agent 的那一半，原话是 "Axis A (model/agent behavior) is production-grade"， 点名的东西是工具执行管线、fail-closed 审批、进程沙箱、凭据引用模型、append-only 审计， 还有浏览器那道 confusion-deputy 围栏（对活实例验过 403/415）。 面向插件代码的那一半，原话是 "Axis B (plugin code) currently has no security design"： 插件在宿主进程内以宿主权限运行，install、update、篡改、持久化、热重载这几条路径上 没有签名、完整性、来源或者确认闸门。!!js 落在后一半。 报告也自陈了几条真实存在的缓解：pnpm 的 registry integrity、0600/0700 权限、 .env 的 bootstrap guard、特权 RPC 的 loopback pinning。

§7.4host 平面 vs agent 平面

补丁层解决了"这台机器跑什么"，没解决"这个会话跑什么"。 Web 界面里两个标签页可能一个是全功能编码 agent，一个是只有两个工具的极简模式； 它们在同一个进程里，共用同一份持久化、同一个沙箱策略、同一条模型路由。 所以插件树被切成了两个平面。

host 平面agent 平面（一个 preset）

挂几次每进程一次每 preset 一次；每个点名它的会话按 scope 父子关系加入
拥有什么registry 本体、沙箱与审批栈、持久化、模型路由只拥有"一个会话可以不一样"的那部分：工具、persona、prompt section
典型行tools、fs-sandbox、approval、llm-deepseek、session-persistence-jsonltool-fs、tool-web、persona、plan-mode

划线的标准不靠语感。出厂 preset 的注释里有几条可以机械判定的关系，讲得比架构文档清楚，直接引用：

The task REGISTRY stays on the host plane: its producers sit outside any realm this file could put it in — tool-bash above resolves it with ctx.get, and an entry-local realm here is invisible to every sibling row, so run_in_background would answer "background jobs unavailable" while these controls sat in the catalog. tokenMeter is deliberately NOT in this realm: [...] it owns the context-meter projection units the browser reads for every session — behind a realm those units would come and go with whichever presets happen to be mounted. What a preset chooses is whether its agent compacts at all, which is compaction-basic below.

三段注释说的是同一件事。被 preset 外面读的东西留在 host，只被 preset 里面读的东西可以下沉。 preset 拿到的选择权停在"这个 agent 有没有这个能力"这一层，不到"这个能力怎么实现"那一层。 下沉也有完全正当的案例，standard 的 planning group 注释： "Plan state is per-agent by nature, so an entry-local realm is not a workaround here — it is the correct lifetime."

realm 规则：一条硬约束

preset 里任何发布 service 的行必须待在一个带 isolate 的 group 里。 standard 的文件头把理由和机制一起写了：

A service row here MUST sit inside a group carrying an isolate realm. Without one it publishes into the root realm, where it is process-global — another preset publishing the same name collides, and a host reader would resolve one preset's instance for every session; dsh-agent-presets rejects that at mount. true means an entry-local realm: this standing mount's own private instance, apart from every other preset's. (A shared label does NOT pool instances — provide() throws on the second registration under the same realm symbol; labels join REALMS, and are not what this file needs.)

检查在 mountPreset() 里，靠 leakedServices() 实现： 遍历 service store 的所有 own symbol，凡是实现属于这次挂载的 fiber、 且 rootIsolate[impl.name] === key（也就是它占的正是根 realm 给这个名字的槽位）的， 就是漏出去的。返回值按 localeCompare 排序，所以诊断信息里名字的顺序和文件里的顺序无关。

这个设计我认为是对的。但上面那段引文我每次重读还是要想三遍：true 开一个 entry-local realm， 字符串是 label，label 加入 REALMS，而同名 label 并不池化实例，第二次 provide() 直接抛。 三件事各自都清楚，凑在一起就是要慢慢过。

minimal：三行，两个工具

minimal 值得单独看，它是四个里唯一一个"不是产品"的组合。整个文件三行顶层： 一个 persona、一个装持久 shell 的 group、一个装文件系统的 group。

apps/cli/config/agent-presets/minimal/agent.cordis.yml · 第一行与文件头注释
# The persona is the complete system prompt, so global identity, Web orientation,
# tool guidance, and later assembly listeners cannot add prompt text. Runtime
# context snapshots are suppressed for this preset, and the model composes only
# persistent `bash` and `str_replace_editor`. Context compaction is absent.

- id: persona
  name: '@deepseek-ai/dsh-persona'
  config:
    text: You are a helpful software engineer assistant.
    complete: true
    includeRuntimeContext: false

complete: true 的意思是这就是完整的 system prompt。全局身份、Web 环境说明、工具指引、 后续任何 assembly listener，都加不进一个字。加上 includeRuntimeContext: false 和完全没有 compaction，你得到的是一个提示词固定、工具固定、上下文不被任何策略动过的 agent。

出厂就带着的那个 benchmark agent 两个工具，一句写死的 system prompt（You are a helpful software engineer assistant.）， 没有 compaction，没有运行时上下文快照。这就是当年那批 SWE-bench agent 的形状： 一个 shell，一个编辑器，一句话提示词。DeepSeek 没把它藏起来， 它和另外三个产品级 preset 并排躺在 apps/cli/config/agent-presets/ 里， 在界面下拉框里叫"极简模式"，order 是 3。 官方对这个模式的说明是"用于最小环境基准测试"， 和这一节从文件里读出来的形状是同一件事。 standard 那边是 25 个工具、plan mode、goal、子 agent、workflow、skills、compaction， 每一样都在给模型多一份可以出错的自由度。两者共用同一个 host、同一份日志、同一条模型路由。
换成别的 harness 同一个进程、同一时刻，一个会话是两个工具的评测 agent，另一个会话是三十二个工具的产品 agent。 这件事 omp 也做得到。它的每个 AgentSession 各自持有一份隔离的工具注册表， 创建时能传 toolNames / restrictToolNames / customTools， 跑起来之后 pi.setActiveTools(names) 也只改当前这一个会话。 区别在于每会话变的是什么。omp 变的是一张工具名单， dsh 变的是一整棵插件子树，工具只是那棵子树上的若干行。 所以 preset 能动的不止名单。minimal 的 persona 带 complete: true， 后面任何 assembly listener 都加不进一个字，它也完全没有 compaction。 code 比 standard 只多一行 tool-presentation: { mode: code }， 整张工具面就塌成一个 run_code。这些都不在名单那一层。 还有一根轴容易和它混掉，所以说明白：OpenCode 的 Go server 加 OpenAPI 3.1 端点解决的是 "一个会话，很多客户端"，CLI、桌面端、网页、脚本可以同时接到同一个 session 上。 dsh 在那根轴上也有东西（跑起来的 Web UI 会去拉 37 个 client plugin bundle）， 但和 preset 无关。preset 管的是"一个进程，很多形状不同的 agent"。

几个真实实现里的东西，我们刻意省掉了：

  • 补丁层其实不止四层。apps/cli/src/profile-boot.ts 在所有用户层之上还压了一层 telemetry 开关：非空的 DSH_TELEMETRY_DISABLED 会把 session-telemetry-otel 打成 disabled。base 的注释解释了为什么必须是补丁： "the launchers patch the row disabled; config cannot disable a row"。
  • 用户补丁层是热的。watchUserPatches 盯住精确路径（文件和父目录都不存在也照样盯）， 把突发变更串行化，并在调用方给定的层序里重新组合。读/解析/候选任一步失败都保留上一棵好树， 同时广播 hmr/config-update-failed(filename, Error)。
  • preset 子树把 write() 覆盖成 no-op。Loader 一旦认为配置变了就会把树写回源文件， 而"某一行自己 dispose 了 fiber"就足以让它这么认为。继承这个行为等于把一个会话的运行时状态 烙进所有会话共享的文件里，还会在 setTimeout 里对只读的出厂 preset 发起 writeFile。preset 文件是输入，不是持久化目标。
  • mount 拒绝三件事，我们只实现了两件。第三件是"一直没变成可用状态的行"： 模块 import 失败或插件抛异常由 Loader 自己拒，剩下的是还在等一个这份组合从未提供的 service 的行， 由 inactiveRows(tree) 点名。code preset 的 tool-presentation 就靠这条：它等 host 的 codeRuntime， 于是"没有 TypeScript runtime 的部署"在挂载时就失败并报出这个 id，而不是拖到第一次请求。
  • isolate 还有 label 形式。true 是 entry-local realm（LocalRealm）， 写字符串则是 GlobalRealm：同名 label 的 entry 加入同一个 realm。 注意 label 不会把实例池化，第二次 provide() 在同一个 realm symbol 下会直接抛。
