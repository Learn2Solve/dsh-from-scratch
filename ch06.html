§6.1能力接缝的三个角色

第 2 章让服务能挂到 ctx 上。挂一个服务是机制，怎么切是设计。 dsh 把切法写进了词汇表，当成硬规则：

A capability seam comprises Service Definition / Service Provider / Consumer roles. The seam is the complete capability, never one role.

所以「shell 接缝」这个说法指的是三样东西加起来，不是那个抽象类。 我第一次读到这条规则觉得是在玩文字游戏，把 packages/shell/ 下面那十个包 全翻完才明白它在防什么：一旦你把 seam 理解成「那个抽象类」，你就会开始往抽象类上加东西， 而该加东西的地方在 provider 里。三个角色各管一件事：

角色拥有什么shell 接缝里是谁
Service Definition 那个 ctx.<key> 和全套词汇类型。必须是 Cordis 的 Service，抽象类或具体注册表，绝不能是 TypeScript interface packages/shell/shell/
abstract class ShellExecutor
Service Provider 一份实现。可以有多个，但一个 context 里只能挂一个 packages/shell/bash-local/
packages/shell/bash-sandbox/
Consumer 注入并使用这个服务。它不知道哪个 provider 在下面 packages/shell/tool-bash/

Definition 必须是 class，因为 interface 编译完就没了，运行时没有任何东西可以被 inject、被重复注册检测、被 ctx.get() 查到。 ShellExecutor 的构造函数只有一行 super(ctx, 'shell')， 这一行把 shell 这个 key 的所有权钉在了这个包上，第二个 provider 想挂同一个 key 会直接抛。

Service Definition packages/shell/shell/src/index.ts abstract class ShellExecutor extends Service { constructor(ctx) { super(ctx, 'shell') } // 拥有 ctx.shell 这个 key abstract resolve(request): ShellExecSpec // 补默认值和上限 abstract run(spec): Promise<ShellRunResult> // 前台 abstract start(spec): ShellProcess // 后台 } ▲ ▲ 实现 │ │ 实现 Service Provider packages/shell/bash-local/ packages/shell/bash-sandbox/ class LocalBashExecutor class SandboxBashExecutor bash -c，进程组，超时归类 extends LocalBashExecutor inject: ['subprocess'] inject: ['subprocess', 'sandbox', 'sandboxPolicy'] ▲ 注入 │ inject: ['tools', 'shell', 'systemPrompt', 'shellEnv'] Consumer packages/shell/tool-bash/src/index.ts ctx.shell.run(ctx.shell.resolve(request)) 整个文件里没有 "local" 也没有 "sandbox" 这两个词

图里最后那行值得停一下。tool-bash 的 execute 体里，前台执行只有一句：

packages/shell/tool-bash/src/index.ts:380 · 真实代码
const result = await ctx.shell.run(ctx.shell.resolve({
  ...request,
  signal: exec.signal,
}))

resolve() 让 provider 自己补默认值和上限，run() 执行。 Consumer 既不选 provider，也不知道命令最终在本机跑、在 Seatbelt 里跑，还是在一台远端虚拟机里跑。 读到这里它听起来还只是依赖注入的教科书用法，下一节是它的产品后果。

角色可以合并，但不能只有一个 角色通常各占一个包，因为它们独立演化。但当它们本来就是一件事时，一个包可以拥有多个角色： dsh-llm 同时拥有自己的 Service Definition 和 Consumer。 规则约束的是「seam 指整体」这个用法，不是包的数量。

§6.2换一个 provider，整个产品换世界

文件系统接缝的结构和 shell 一模一样：packages/fs/fs/ 是 abstract class FileSystem（Service Definition，拥有 ctx.fs）， packages/fs/fs-local/ 和 packages/e2b/fs-e2b/ 是两个 provider， packages/fs/tool-fs/ 里的 read / write / edit 是 Consumer。

Definition 里有三个方法看起来不起眼，这一整节都靠它们：

packages/fs/fs/src/index.ts · 真实签名（节选）
// 返回一个 subprocess 在【这个 filesystem 的 execution world 里】能打开的绝对路径
abstract processPath(target: FsTarget): string

// 返回该 target 在这个 execution world 里的 file: URI（编码由 backend 拥有，
// 因为宿主平台可能和执行平台不是一个平台）
abstract fileUrl(target: FsTarget): string

// 不暴露、不解析 target 内部结构地测试包含关系
abstract contains(parent: FsTarget, child: FsTarget): boolean

execution world 是个术语，指一组共享同一份路径语义的 provider。 文件系统 provider 和 subprocess provider 属于同一个执行世界： processPath() 交出来的路径，这个世界里的 subprocess 能直接 open。 docs/architecture.md 里那句话就是这个意思：

Seams are why one provider swap changes the whole product. Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves Bash, PTY, and LSP with them, with no provider forks.

展开来说：bash 工具通过 ctx.shell 拿到命令执行能力， LSP 客户端在 lsp-stdio/src/host.ts:57 用 fs.fileUrl(target) 告诉语言服务器打开哪个文件，终端用 processPath 决定在哪个目录起 PTY。 把 ctx.fs 和 ctx.subprocess 一起指向一台远端沙箱，这几个包都不用改。 packages/e2b/README.md 直接点了名：dsh-bash-local、 dsh-terminal-bash、dsh-lsp-stdio 都不需要 E2B 专用分叉。

同一份 README 也给了这句口号的边界，我觉得这段比口号本身有用。整个 packages/e2b/ 家族被它自己标成 experimental provider-composition POC，而且搬走的只有可变工作。 harness 进程、Cordis 对象、模型调用、agent 与会话状态、会话持久化、skill，全都留在本地。 所谓「整个产品换一个世界」，换的是文件和进程那一层的世界。

Demo 6.1provider 热切换

点「三个 provider 依次热切换」：同一个 read 工具、同一批参数， 在 fs-local 下读到本地内容，在 fs-workspace 下 /etc/passwd 被围栏拒绝， 在 fs-e2b 下读到的是远端沙箱里的另一份文件，processPath 也变成了 /home/user/...。同一个 execution world 里的 bash 工具拿到的就是这个路径。

路径那个输入框是可以改的。填 ../../etc/passwd 再选 fs-workspace 跑一次， 围栏会放它过去，因为这个 demo 的 contains() 是字符串前缀比对。 真实 Definition 的签名收的是两个 FsTarget，注释写的是 canonical containment， 比的是 provider 自己规范化过的 target，不是我们这里的裸字符串。 把围栏做在没规范化的路径上，是这类漏洞最常见的长法。

「接缝证据」按钮做三个可验证的检查：fs-workspace 的 readText 是不是和 fs-local 的同一个函数对象（继承来的，没重写）； read 工具的源码里有没有出现过任何 provider 的名字；ctx.fs 这次解析到了谁。

「换成一个会骗人的 provider」是第四个 provider。它不违反任何一条规则， 路径合法、行数合法、输出通过工具自己声明的 output schema，只有内容是编的。 流水线全绿，模型拿到的是假话。接缝除了是替换点，也是信任边界： 谁能往 ctx.fs 上挂东西，谁就决定了模型看见什么。 真实 dsh 里换 provider 是配置树上的一行改动，而配置树谁能写，是第 7 章的问题。

这里和真实 dsh 有一处刻意的偏差 真实的 packages/fs/fs-sandbox/ 只 override 了两个 mutation （writeText、editText），读操作原样透传，因为 every mode permits reading。 demo 里的 fs-workspace 连 read 也拦，纯粹是为了让同一次调用产生可见差异。 真实实现里那段注释值得读一遍：那道围栏是受信任代码里对模型控制路径的策略检查，不是内核边界； 隔离不受信任代码是 ctx.shell 的活（dsh-bash-sandbox）。

另外注意 SandboxedFileSystem extends LocalFileSystem： resolve、stat、read、原子写、read-match-write 的临界区全部原封不动继承， 这个包只加了逐调用的策略围栏。provider 之间共享实现是常态， 接缝并不要求每个 provider 从零写一遍。

§6.3工具执行流水线

上一节的 tools.execute() 有个缺口，它直接调用了工具体。 于是「这次调用要不要人批准」和「这个工具超时了怎么办」这两件事没有地方放， 唯一的去处是往工具体里塞 if，而 dsh 有二十一个 tool-* 包。

dsh 的答案是把 execute() 拆成一条流水线，每一段都是第 4 章的瀑布事件：

assistant 消息里出现 tool-call 块 │ ├─► session 事件 tool/call 先记录，再执行；UI 用 presentCall(args) 画待执行卡片 │ ├─► 参数校验 / 工具不存在 走同一条结果路径，但【不经过策略，也不进工具体】 │ ├─► tools/pre-execute waterfall hooks、权限策略、沙箱解析 │ allow ──┐ deny ──────┐ ask ──► ctx.approval 一次性询问 │ │ │ allowed-once ──┐ │ ▼ │ rejected / cancelled / 接缝缺席 ──► deny ├─► 单调守卫 guards │ ◄──────────────────┘ │ 只能 deny 或弃权 │ 没有 allow 结果，所以顺序无法把拒绝翻回允许 │ deny ──────────────────┤ │ │ │ ├─► tools/execute waterfall │ 环绕分发：超时、重试、指标 │ └─► 工具体 execute() │ 只能替换 exec.signal，不能改调用身份 │ │ ▼ ├─► tools/post-execute waterfall accept / block / 替换 value / 附加 additionalContexts │ │ 被拒绝的调用也会走到这里 ├─► finalizeContent 定义自己拥有的最后一道 content 不变式，同步、必须总函数 ├─► tools/result 冻结、无损 JSON、只能观测 └─► session 事件 tool/result 模型看到的唯一结果

流水线的每一段都在补一个具体的洞，逐条对一遍：

  • tool/call 先记录再执行。反过来的话，进程在工具跑一半时死掉，日志里就没有这次调用。
  • 参数不合法不进策略。一个必然失败的调用不该让权限插件观测到，更不该让人类去批准它。 真实实现里这条路径连 finalizeContent 都会按规则丢弃。
  • pre-execute 是瀑布，guards 是单调的。瀑布可重排，一个后注册并 prepend 的监听器 可以强行返回 allow。所以不能被绕过的拥有方策略要注册成 ctx.tools.guard()， 它跑在整条瀑布之后，只有 deny 和弃权两种返回。没有 allow 结果，就没有「顺序不同结论不同」。 整个仓库里只有一处真的用了它，subagent-in-process-driver/src/structured.ts:109： 结构化输出一旦记下来，这个子 agent 后面的任何工具调用一律拒绝。
  • ask 在 guards 之前解析。先问人，再过守卫。反过来会出现「人批准了但守卫仍然拒绝」， 然后还要回去撤销那次批准。approval 接缝缺席时 ask 退化成拒绝。
  • 被拒绝的调用照样走 post-execute。防循环守卫要数它：一个模型反复捶一个被拒绝的调用， 正好是最该打断的循环（§6.5）。
  • tools/result 是 emit，不是 waterfall。到这一步结果已经冻结，要改就得在 post-execute 改。最终结果必须有一个所有观测者都同意的版本。
换成别的 harness 这条流水线最实用的性质是策略不住在工具里。审批、沙箱模式、计划模式，都是 tools/pre-execute 上的普通监听器，工具体里没有一行代码知道有「策略」这个东西。 换成一种把权限检查写成每个工具内部分支的 harness，加一条新规则要挨个改工具， 而漏改一个的后果是那个工具悄悄不受约束。dsh 把这条路走到了什么程度可以量一下： Claude Code 的 PreToolUse / PostToolUse hook 协议在 dsh 里就是两个监听器， packages/hooks/hooks-claude-code/src/index.ts:238 把 hook 返回的 deny / ask 翻译成一个 PreToolDecision 就完事了。 别人的扩展协议在这里成了自己的一个插件，hooks-codex/ 是同样的写法。
这条线还没画完 packages/shell/tool-bash/src/index.ts 的模块注释第六行写着 TODO(permissions): deployment policy belongs in tools/pre-execute and sandboxing executors。 这个工具自己知道它还 import 着 dsh-sandbox 的 approveEscalation 和 SandboxExecutionPolicy，策略有一截还长在工具体里。 我更愿意看到这种 TODO，而不是一篇声称已经做到了的架构文档，但读的时候要记得， 「策略全在工具外面」目前是目标，不是现状。

§6.4参数校验与渲染意图

自带一个 JSON Schema 子集

模型生成的参数是不可信的字符串。dsh 没有引入 ajv 之类的完整实现，只在 packages/core/tools/src/json-schema.ts（656 行）里定义并强制执行一个子集：

The subset accepts any JSON root, an annotation-only schema for unconstrained JSON, one scalar type, object properties/required/boolean additionalProperties, array items, type-correct scalar enum/const, and exact-one oneOf. Unsupported or misplaced keywords reject rather than being accepted without enforcement.

最后半句是这里最该学的一条：不支持的关键字直接报错，而不是被接受下来却没人执行。 一个写了 pattern 却没人执行的 schema，比没写更危险，因为工具作者会以为自己已经防住了。

这个子集有几个不太常见的选择：

  • 白名单窄到可以写进错误消息里。报错原文是 is not a supported keyword (subset: type/oneOf/properties/required/additionalProperties/items/enum/const + annotations)。 pattern、minimum、minLength、format 一个都不能写。 想要正则约束就自己在工具体里检查，这是这个子集要付的钱。
  • required 里的每个名字都必须在 properties 里声明过， 否则 json-schema.ts:217 会报 required names "x" which is not in properties。标准 JSON Schema 不管这件事。
  • 校验器不用 JavaScript 调用栈递归，而是显式的帧栈（SchemaWalkTask 走 schema， ValueFrame 走值）。模型可以生成任意深的嵌套，递归实现会被一个深度 10 万的数组爆栈。
  • 违规全部收集再一起抛，不是遇到第一个就停。给模型的错误消息里列出全部问题，它一次就能改对。

同一个校验器有两个用处：校验模型给的参数，以及校验工具自己返回的规范值。

HN 上的一条评价，一半夸一半骂 发布当天的 HN 主线程（item 49285244，545 分 234 条评论，2026-08-13）里， JonChesterfield 写道「I really like the json schemas around the tool calls. Much stricter validation than in codex.」夸的正是这一节。 同一条评论紧接着给了一个具体的缺点：「git is behind bash and that means hope or sandboxing」， 他认为 git 该是个顶层工具。这一条我核过，是真的：packages/ 下面 二十一个 tool-* 包里没有 git，模型想提交代码只能走 tool-bash。 于是校验器管得住 bash 的参数是一个字符串，管不住那个字符串是 git commit 还是 git push --force。 §6.4 的严格只覆盖参数这一层，命令内部的语义要靠 §6.1 那个 ctx.shell 接缝换成沙箱 provider， 也就是他说的 hope or sandboxing 里的后半句。

渲染意图必须是纯函数

每个工具都要提前声明「我这次调用在 UI 里长什么样」。 dsh 把这个词汇表放在 packages/core/tools/src/presentation.ts， 是 provider-neutral 的 tagged union，UI 桥不需要对工具名做特判：

card用来渲染真实使用者
generic带标题的默认行，可选图标类别、salient 原始输入、follow-along 文件位置所有非终端非 diff 的调用；glob / grep 的待执行卡片
terminal一条真的 shell 命令 + 工作目录，结果带输出体和退出码tool-bash/src/index.ts:113
diff内联 diff 卡片tool-fs/src/edit.ts:153、write.ts:134
search搜索结果，用 shape 区分 matches（按文件分组）和 paths（平铺）tool-fs-search/src/presentation.ts:197
read带行号、可高亮的文件读取窗口tool-fs/src/read.ts:183
webweb_search 的可引用来源列表 / web_fetch 的 URL 和 HTTP 状态presentation.ts 的 WebResultView

注意 kind（read / edit / delete / move / search / execute / fetch / other）和 card 是两个正交维度： card 决定用哪种版式，kind 决定图标。read_image 就是 card: 'generic' 配 kind: 'read'。

关键约束在两个方法的文档注释里，一字不改地抄过来：

packages/core/tools/src/index.ts:275 Pure and side-effect-free: a UI may call it during live streaming AND a session-log replay, so it must depend only on args.

这句话解释了第 5 章那套日志为什么能成立。会话日志只记录 args 和结果的无损 JSON 投影， 渲染出来的界面不进日志。重开一个会话时，UI 拿日志里的 args 重新调一遍 presentCall(args)，必须画出和当时一模一样的卡片。 如果 presentResult 偷偷读了一下 ctx.fs，或者用了 Date.now()， 或者依赖了某个内存里的缓存，那么 replay 出来的历史就和当时不一样， 而这种不一致在实时使用中永远不会暴露。

纯函数还有第二个后果：presenter 允许在旧 schema 的 args 上被调用。 所以真实实现里 defineTool 对 presentation 是软校验： 「Presentation is display-only and may run on REPLAY of arbitrary logged args (possibly from an older schema), so it must never throw.」

Demo 6.2 的最后一行做了这个检查：拿结果的 JSON 副本（模拟从日志里读回来） 重新算一次 presentResult，和实时算出来的那份逐字节比对。

§6.5防护栏

流水线搭好之后，防护栏就是普通插件，不需要内核里的特殊代码。 dsh 里两个最典型的例子分别挂在两个不同的阶段上，各自解决一类问题。

超时：一个 tools/execute 包装层

工具在定义里声明 timeoutMs， packages/guard/timeout-policy/ 把它变成一个环绕包装层。 这个包只有 81 行，里面有四个容易做错的决定：

  • timeoutMs 绝不发给模型。schemas() 只白名单 name / description / parameters 三个字段。让模型知道预算，它就会开始编造「我需要更长时间」。
  • 不 race，不丢弃 promise。包装层把一个派生的 deadline signal 换到 exec.signal 上， 然后照常 await。工具自己观测到 abort、自己收敛到 quiescence。 Promise.race 会让一个还在写文件的工具变成孤儿。 声明 timeoutMs 等于承诺「我会转发 signal」。
  • 只有自己的计时器响了才替换结果。timeoutOf(d.signal, TOOL_TIMEOUT) 按 code 判定归属： 外层还有一个 deadline 先响了的话，这里读到 undefined， 于是它被当成普通的上游取消，而不是冒领成本插件的超时。
  • finally 里恢复上游 signal。否则 post-execute 的监听器会看到一个已经 abort 的 signal， 以为整次调用被取消了。

防循环：一个 tools/post-execute 的观测者

模型卡住的典型形态是反复调用完全相同的工具和参数。 packages/guard/repeat-tool-reminder/ 的处理方式很值得注意： 它不否决，只注入一条建议。

默认阈值是 [3, 5, 8]。第一档（thresholds[0]）给一句温和的提醒， 后面的档给详细版，点名工具、连续次数和规范化后的参数。几个细节：

  • 先数，再 await next()，最后把提醒折到下游决定上。 顺序是刻意的：计数必须无条件推进，而且下游插件仍然可以 block 或替换结果。 additionalContexts 在 accept 和 block 两种决定上都能搭车， 所以一个被 block 的调用也拿得到这句提醒。
  • 参数要 canonicalize。{a:1,b:2} 和 {b:2,a:1} 是同一次调用。做法是深度 key 排序后 JSON.stringify。
  • 提醒的文本有长度上限，检测没有。 chain key 永远用完整的规范字符串比对，只有塞给模型的那段被截断（默认 500 字符）。 否则一个 write 的大 body 会在循环场景里被无界地带进下一次请求。
  • 用户插话会清空 chain。挂在 agent/pre-step 上：只要认领的消息里有一条是用户来的， 链子就断。上下文变了，重复就不算循环。
  • 提醒必须带 {kind:'plugin'} 来源。源码注释写得很直白：「the label is load-bearing (an unlabeled context would render as a user prompt in derived history)」。 没有标签，这句提醒在历史里会被当成用户说的话。

§6.6本章的产物

miniLoop 里那个 tools.execute(call, signal) 现在有了真身： 一个注册表、一条五段流水线、一个可换的 fs 接缝。

mini-dsh v0.6 · ctx.tools 与结果收尾

和第 1 章那个 TOOLS 字典对比一下差别在哪：那时候「执行一个工具」是 impl(args)；现在它是一条有五个扩展点的流水线， 而且工具能力本身（读文件、跑命令）已经被推到接缝的另一边去了。 工具体只剩下把参数翻译成一次能力调用，再把结果翻译成规范 JSON。

下一章预告 本章切 provider 用的是我们自己写的 ctx.swap('fs', ...)，这是作弊。 真实 dsh 里没人在代码里换 provider：fs-local 换成 fs-e2b 是配置树上的一行改动，而且要连带把 ctx.subprocess 一起换掉，还得保证加载顺序正确。 第 7 章把整个产品降维成一棵可打补丁的 YAML 树：profile、bundle、patch、preset， 以及每个会话挂载自己插件子树的能力。上一段那个会骗人的 provider 也要在那一章才有答案， 因为「谁能改配置树」才是它真正的边界。

几个真实实现里的东西，我们的 mini 版本刻意省掉了：

  • scope 与遮蔽。注册表是分层的（ToolLayer / ScopedLayers）。 一个 agent 可以有自己的同名工具变体遮蔽全局那份，也可以用 restrict() 过滤全局工具集（多个掩码取交集）。被过滤掉的全局工具「从 prompt 里消失并且拒绝执行， 和不存在的工具无法区分」。守卫和监听器同样分层，全局层优先，然后是 scope 链，最远的先跑。
  • cancellation 的两个错误码。ABORTED_BEFORE_DISPATCH 表示工具体还没被调用就取消了， ABORTED 表示已经进过工具体。注册表用一个 bodyInvoked 标志位来选。区分这两者的原因很实际：前者可以安全重试，后者可能已经改了磁盘。
  • signal 融合。tools/execute 的包装层可以替换 exec.signal，但注册表会在进入工具体前 把调用方的原始 signal 重新融合回去（fuseToolSignals）， 所以替换永远不可能切断调用方的取消能力。而且这个融合是 dispatch 作用域的， 工作收敛后监听器会被摘掉，不会泄漏。
  • 无损 JSON 与冻结。参数进流水线时 snapshotJsonValue + deepFreeze； 结果在 tools/result 之前 materializeFinalResult 独立快照并冻结。 投影函数（render、presentationMeta）抛异常会被归一成 ToolOutputError，而不是把整条流水线炸掉。
  • Code Mode 的嵌套执行。parent 是一个 ToolExecutionToken （不是执行对象）。mode: 'code' 下只有带 parent 的调用才能执行原生工具名； 模型直接调用一个原生工具会在策略流水线之前就被折叠拒绝， 而且拒绝消息里带着「从 run_code 程序里调用它」这条出路。这是第 8 章。
  • 不变式检查。每个包都有一个 invariant.ts。 tools/src/invariant.ts 会在开发期断言「一个 execution 不能重复跑 pre-execute」、 「tools/execute 必须跟在 tools/pre-execute 之后」这类阶段顺序。
