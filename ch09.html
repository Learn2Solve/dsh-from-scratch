第 09 章

自我改造：让 agent 修改自己的运行时

前八章造的东西，这一章会同时用上：服务注册表、fiber 的反序回收、瀑布事件、会话日志、工具流水线。 模型现场写一段插件，挂进正在运行的进程，然后在同一个 turn 里调用它自己刚注册的工具。 这件事能不能做，取决于工具表是一张可写的注册表，还是一个启动时读一次的常量。 dsh 选了可写，代价记在 §9.6。

本章造出 cordis_define / cordis_run / cordis_stop3 个 demo · 1 个预测题约 30 分钟

§9.1为什么这件事在别的 harness 里做不到

"让模型给自己加一个工具"听起来像一个 feature，落到实现上是一道结构题。它同时要求四样东西， 而这四样恰好是第 2 到第 6 章各自的产物：

需要什么来自哪一章缺了会怎样
运行时可写的服务注册表第 2 章 Context / Service新插件无处发布自己的能力，只能改源码重启
卸载时反序回收副作用的 fiber第 3 章 Fiber / ctx.effect()停不掉。长会话里堆满孤儿监听器和幽灵工具
能被外部代码挂钩的事件第 4 章 ctx.on() / waterfall动态插件只能加工具，改不了已有行为
接受运行时注册的工具表第 6 章 ctx.tools / capability seam最致命的一条。工具表若是启动时冻结的数组，这一章的一切都不存在

最后一条值得展开，也值得先削掉一点。工具集写成模块顶层的 const TOOLS = [...]、 启动时读一次拼进 system prompt 就再也不变，这样的 harness 确实存在。在那种结构里， "运行中新增一个工具"没有落点：没有 owner，没有作用域，没人负责在它消失时把它摘掉， schema 变了也没人知道该重发请求。

这条界线并不把 dsh 单独圈出来。omp 的扩展用 pi.registerTool(...) 注册工具， 运行中可以 pi.setActiveTools(names) 换掉当前会话的活动集， MCP 那一侧还能 /mcp reload 做一次断开加重新发现的热重绑。工具表可写，它做到了。

剩下的差别在作者和来源。omp 那条路上的工具来自一段人写的代码，装进发现目录，进程起来时被 import 执行； 它进入工具表的时刻晚，出生的时刻早。本章要挂的东西没有这段前史， cordis_define 收下的是模型在这次会话里写出来的函数体， cordis_run 求值它，挂成 cordis-dynamic 组下的一个子 fiber。

焊住这件事的是注册的返回值。dsh 的 ctx.tools.register() 不往数组里 push， 它返回一个 disposer，而这个 disposer 本身就是调用方 fiber 上的一个 effect：

packages/core/tools/src/index.ts · ToolRuntime.register 的最后一句
return this.layers.effect(
  this.ctx,
  layer => layer.tools.insert(name, definition),
  { label: 'tools.register()' },
)

注册和生命周期就此焊在一起。谁注册的，谁的 fiber 死了就自动注销。 cordis-host-runner 的 lifecycle.ts 因此可以在模块注释里写得这么轻松， 停止一个动态包不需要任何专门的清理代码：

Stopping needs no helper — a host half unwinds through an ordinary awaited fiber.dispose(), because everything the plugin registered is an effect on its fiber.
换成别的 harness 工具表冻在编译期的 harness，没有地方安放一个下午三点才被造出来的工具。 第一条替代路是 MCP：Claude Code、Codex 和 dsh 都支持它，一个外部进程可以把自己的工具挂进模型看得见的目录。 dsh 自己的 packages/mcp/mcp-client 就是这么干的， 按 cordis.yml 里的一条配置连上一台 server，把它的工具注册成 mcp__<server>__<name>。 第二条是 omp 的扩展：一个默认导出 (pi: ExtensionAPI) => void 的 TS 模块，跑在 harness 自己的进程里， 用 pi.registerTool(...) 加工具，也能挂事件、slash 命令、快捷键和消息渲染器。 它的工具表同样是活的，写那段代码的人是你。 三条路的时间点不一样。MCP server 是你事先写好、事先配好的另一个程序； omp 扩展是你事先写好、放进 .omp/extensions 这类发现目录的一个模块； cordis 动态包是模型在这次会话里写的一段函数体，挂进当前进程，带着一个 disposer。 前两条换来的东西也是真的。MCP 有独立进程、可以用任何语言写、同一台 server 能被几个 harness 复用， 隔离性比 §9.6 那个沙箱结实得多；omp 扩展在挂载之前被一个人读过一遍、装过一次， 它更安全的理由和它更不动态的理由是同一个。
先把这话的分量说清 这套机制不是 dsh 发明的。开源当天 HN 那条帖子里，lxdlam 读完 cordiverse/paper （不是 DeepSeek 自己的 harness 论文）给出的结论是 「found it may be useful, but not that useful... it adds hot-reload and dynamic enable/dispose capabilities to a plugin system, like the one in Pi agents, though they push the boundaries further, to the UI components」（HN item 49285244，2026-08-13）。 这话没说错。热重载和 dispose 在插件系统里是旧东西，Pi 的 TypeScript extension 也能加工具、命令和 hook。 dsh 推进的是范围：写这段代码的是模型而不是你，落点包括浏览器里的 UI slot， 代码跑在 harness 自己的进程里。最后这一句要付什么代价，§9.6 会算清。
第 2 章 第 3 章 第 4 章 第 6 章 Service 注册表 Fiber / effect ctx.on 瀑布 ctx.tools.register │ │ │ │ └──────────────────┴────────┬─────────┴──────────────────┘ ▼ cordis_define → cordis_run ▼ 模型写的 plugin 成为一个活的子 fiber ▼ 它注册的工具立刻出现在下一次请求里

§9.2七个工具，两两成对的动词

先说一件容易踩坑的事：这套工具的名字在仓库里有四个版本，只有一个是真的。 读文档会读到三种说法，而运行时真正发生的只有 packages/extensions/tool-cordis/src/index.ts 里那句 ctx.tools.register(defineTool({ name: … }))：

出处它说的名字可信度
tool-cordis/src/index.ts下面那 7 个唯一权威
docs/tool-catalog.md（生成物）同样的 7 个一致
tool-cordis/README.md5 个：cordis_inspect 一个顶三个已过时
Agent Note 2026-07-08-self-referential-cordis-toolset.md3 个：cordis_mount / cordis_unmount上一代设计

生成的目录跟着源码走，手写的散文跟不上。任何"用文档描述行为"的地方都会这样，这个仓库并不特别糟。 dsh 的应对是把能生成的东西全部生成，再用 verify-* 脚本闸住新鲜度（§9.9 还会提一次）。 读源码是唯一不会骗你的路径。真实注册的七个是：

工具参数做什么
cordis_inspect_list无列出所有 Inspect Provider（host 侧本地的 + 从浏览器同步来的 manifest），每个带平台、只读方法、输入输出 schema
cordis_inspect_queryplatform provider method input?跑一次 Provider 显式声明的只读查询。名字必须来自 list，不许猜。它不能调用业务服务，也不能改运行时
cordis_inspect_selfpluginId? packageId?看当前会话自己的动态对象。三档细节：不给 id 只列 plugin 摘要；给 pluginId 出版本指针与所有 package 摘要；两个都给才返回那个不可变 package 的源码与诊断。packageId 不能单独出现
cordis_defineplugin name purpose code.host? code.client?登记一个不可变的 Package。只校验参数与语法、记录源码：不申请批准、不执行 apply、不改 currentPackageId
cordis_runpluginId packageId mode激活某一个精确的 Package。mode:"run" 首次启动 / 重启 / 回滚，mode:"update" 从 current 切到另一个 package
cordis_stoppluginId停掉当前 Run，取消未完成的批准请求。定义、所有 package、授权、版本指针全部保留，重复 stop 幂等成功
cordis_undefinepluginId永久删除。必要时先 stop，然后删掉每个 package、每份授权和版本指针
成对的动词 define ↔ undefine 管存在，run ↔ stop 管活着。两条轴正交， 于是"停掉但保留版本以便回滚"和"彻底删除"是两个不同的意图，模型不必用一个动词表达两件事。 第三类是只读的 inspect，它不参与任何一对。一个只读动词没有反义词，这也是它可以被无脑调用的原因。

还有一条设计选择藏在 define 的参数里：plugin 是一个 oneOf， 要么 { kind: 'new', idPrefix }（给 3 到 6 个小写字母，host 补数字后缀）， 要么 { kind: 'existing', pluginId }。后者追加一个新 package，旧的原地留着。 于是"改一版"天然是 append-only：Plugin 是一条版本线，Package 是线上的不可变节点， currentPackageId 只是一个指针。回滚就是把指针指回去，再 cordis_run mode:"run"。

§9.3host 半与 browser 半

一个动态 package 可以同时带两半：code.host 跑在 Node 进程里，code.client 跑在浏览器里。 两边都是一段返回 cordis plugin 的普通 JavaScript 函数体，没有 JSX、没有 TypeScript、没有 import 变换。 第二半的含义比第一半激进：模型可以把 UI 写进正在运行的 web client。

浏览器那半的落点不是 innerHTML，而是一份编译期生成的 slot 目录（tool-cordis/src/client-catalog.ts）： 每个 slot 的 key、注册选项、组件能收到的 props、谁已经占着这个座位。 生成器宁可失败也不输出模型无法据以行动的条目。

两半的启动顺序和授权由 host 的 run() 决定，而这里有本章最重要的一道人类闸门：

packages/extensions/cordis-host-runner/src/index.ts · run() 的两条分支（节选）
// 没有 browser 半：host 自己直接激活，不问任何人
if (plan.definition.clientCode === undefined) {
  const started = await this.activate(plan, undefined, false, attempt)
  if (started.ok) return this.runResponse(plan.plugin, started)
  this.failAttempt(plan.plugin, attempt, 'host-load', started)
  return { ...started, reason: 'host-half-failed' }
}

// 有 browser 半：先看这个 Package 是否已被授权
const requestId = ApprovalRequestId(this.registry.mintApprovalRequestId())
const requiresApproval = !plan.plugin.clientVersionUpdatesApproved
  && !plan.plugin.approvedClientPackages.has(packageId)
attempt.status = requiresApproval ? 'awaiting-approval' : 'starting-host'
this.ctx.emit('cordis/request-run', { requestId, agentId: agent.id, pluginId, packageId, /* … */ requiresApproval })

读法：host 半不需要批准，browser 半需要，而且只需要一次。 用户点"批准"时可以顺带勾上 approveFutureVersions，之后这个 Plugin 的后续版本直接放行 （clientVersionUpdatesApproved）；不勾，授权就按 Package 记（approvedClientPackages）。 被批准的对象是页面上会出现的东西，不是代码本身。host 半早就以 bash 级别的权限跑起来了， 再给它加一道确认框只是安慰剂。

谁来驱动这次 run host 通过 cordis/request-run 事件问所有打开的页面"这个定义要不要跑"。 第一个应答的页面负责按顺序驱动：先 host 半，再取源码，再 browser 半，最后回一份说明发生了什么的 resolution。 用户在页面上自己按"运行"也走同一条编排，只是没有什么要问的。整段编排在 packages/extensions/cordis-client-runner/，它把 guarded plugin 塞进模块表、 用 loader.create 挂载，所以动态包和静态包共享同一套激活门禁、fiber effect 清理和状态投影。 本地跑起来的那个 Web UI 会去取 37 个 client plugin bundle，模型写的那半用的就是同一条加载路径。

§9.4检查活的运行时

模型要给运行时写插件，第一件事是知道运行时长什么样。这里有个值得偷的设计： inspect 的数据来自两个性质不同的源头，然后求交集。

  • 能做什么：一份编译期生成的 API catalog（tool-cordis/src/api-catalog.ts）， 与 docs/subsystems 出自同一次 AST 扫描，含渲染后的方法签名、原始 JSDoc、事件的分发模式。 它讲的是仓库在编译期的事实，用 verify-cordis-api 闸住新鲜度。
  • 正在跑什么：live service store，也就是进程里此刻真实存在的服务和它们的 owner fiber。

关键在这两者不匹配的时候怎么办。tool-cordis/src/inspect.ts 的选择是：

packages/extensions/tool-cordis/src/inspect.ts · liveServices()
/**
 * Every service this process provides, joined with the generated catalog: what is
 * RUNNING comes from the store, what each service CAN DO comes from the catalog,
 * and a live service the catalog does not cover stays in the list as reachable
 * with no signatures rather than being dropped.
 */
function liveServices(ctx, api) {
  const catalogued = new Map(api.map(entry => [entry.key, entry]))
  return liveImpls(ctx).map((impl) => {
    const entry = catalogued.get(impl.name)
    return {
      name: impl.name,
      owner: impl.fiber.name,
      state: STATE_LABELS[impl.fiber.state],
      summary: entry === undefined ? '' : plainSummary(entry.summary),
      catalogued: entry !== undefined,
      methods: entry === undefined ? [] : entry.methods.map(method => method.signature),
    }
  }).sort(/* … */)
}

一个活着但目录里没有的服务，被报成可达，但没有签名，留在列表里。 这条规则是自我改造能力的必需品，不只是健壮性好看：动态包 provide 出来的服务，按定义就不可能出现在编译期目录里。 inspect 若只信目录，模型永远看不见自己上一步造出来的东西，package 之间也无法通过 provide / inject 组合。 反过来，目录里有、进程里没有的，单列成 absent 一行：可加载，但此刻不在。

§9.5现场造一个工具

到这里为止都是别人写好的东西。这一节你自己写。 下面文本框里是一段 host 半：一个 async 函数体，必须 return 一个 cordis plugin。 它能看见的全局只有沙箱给的那几个：harness、console， 加上 require / fetch / setTimeout 这三个一调用就抛错的 trap。

按钮和真实动词一一对应，各自只做各自的事：

  • cordis_define：只编译，不执行。语法过了就铸一个 id 记下来。你把代码改坏，这里会给你一个真的 SyntaxError。
  • cordis_run：在沙箱里求值，用白名单 façade 包住 ctx，挂成 cordis-dynamic 组下的一个子 fiber。你的工具真的进入工具表。
  • cordis_stop：fiber.dispose()。第 3 章的反序回收把这个插件注册过的一切按相反顺序摘掉。
  • 「不给 disposer 的插件」不是真实动词，是一个反面演示：绕开 ctx.effect() 注册工具，然后你会看到 stop 之后它还赖在表里。

§9.6沙箱不是安全边界

你刚才挂上去的东西，跑在与 harness 本体同一个进程里。dsh 的源码对这件事的表述没有任何修饰， cordis-host-runner/src/sandbox.ts 的模块注释第一段就写着：

This keeps cooperative packages inspectable and disposable but is not containment: host-realm helper functions remain an escape route.

沙箱到底做了什么、没做什么，摊开是这样：

做了没做
一个全新的 node:vm realm，全局污染不外泄不限制已授予服务的权限：ctx.bash 就是宿主 executor 的权限
Node API 变成会抛错的 trap，错误文案直接告诉你该用哪个 cordis 服务宿主 realm 的 helper 函数仍在可达范围内，逃逸是可能的
ctx 换成白名单 façade，框架内部一律拒绝façade 允许的服务照样改动真实运行时，并可能影响同进程的其他会话
vmTimeoutMs 限制求值只限制同步部分；async 函数体一 await 就出界了

只有函数形状的全局才被 trap。process 和 Buffer 留成 undefined， 因为一个会抛错的取值器会让常见的 typeof process 探测在解析那一刻就炸掉。 btoa / atob 是闭包在宿主 Buffer 上的两个函数，一个被明确记录的例外； Buffer 自己永不暴露。

Agent Note 里那段自辩说得更直白：trap 和 façade 的目的是把 API 收窄成正确的那一套， 把文件、网络、进程、定时器都导向 cordis 服务，从而可被检查、可被回收。安全不在目标里。 真正的安全边界需要独立进程和权限提示，那与"把活的运行时交给模型"这件事本身冲突。 所以官方结论只有一句：把一个动态包当成 bash 权限来对待。

换成别的 harness 这是 dsh 明显弱于别人的地方，得说清楚。MCP 工具住在另一个进程里，进程边界是操作系统给的真边界： 它崩了不会带走 harness，它也读不到 harness 的堆。Codex 有 approval mode 和沙箱策略。 omp 在这条轴上和 dsh 站在一起，有些地方还要往后一点。它的扩展也在主进程里跑，文档的说法是 in-process with no isolation：一个脱离 handler 派发的 setTimeout 回调里抛出异常， 会浮成进程级 uncaughtException，postmortem handler 按 fatal 处理，整个会话被拆掉。 工具执行那一侧它只有审批策略，三档 always-ask / write / yolo， 默认那档是 yolo，底下没有内核。 dsh 自己在 packages/sandbox 里有 Landlock / seatbelt 那一层，Windows 上换成受限令牌与 ACL， 可那一层管的是模型跑的命令，不管模型现场写进本进程的插件。 所以两条轴要分开记：命令执行这条 dsh 手里有内核给的东西，omp 手里只有一个确认框； 模型写的代码跑在主进程这条，两边一样敞着。 动态 package 的好处是可检查、可回收、能直接拿到活的 ctx；它没有隔离，这条没法两全。 tool-cordis/README.md 把这笔账写在了小标题里： the sandbox is containment for honest code, not a security boundary。

Demo 9.3façade 拒绝什么，放行什么
这才是重点 十二个探针里被拒的那九条，没有一条是因为"危险"。它们要么是框架内部 （ctx.fiber、ctx.registry、ctx.plugin）， 要么是没在 inject 里声明的服务，要么是被 trap 掉的 Node API，而最后这一类的理由是"可回收、可检查"。 第二个按钮里的插件规规矩矩声明了 inject: ['fs']，于是它可以把工作区的文件覆写成任何内容， façade 全程没有意见，因为这正是它被授予的能力。 "bash 级别的信任"是对这个 demo 的准确描述，不是一句免责声明。

到这里为止，这一节的证据全是 dsh 自己的注释、文档，加上本页这个 demo。 开源第二天，外面有人把这句自述当成一条待验的命题跑了一遍。

审计把这件事切成两条轴 Fz0x00 的披露报告（GitHub Discussion #454）把 dsh 切成两条轴分开评。 面向模型那一条它给的词是 production-grade：工具执行管线、fail-closed 审批、进程沙箱、凭据引用模型、 append-only 审计，还有浏览器那道 confusion-deputy 围栏（对活实例验到 403/415）。 面向插件那一条，原话是 plugin code currently has no security design： 插件在宿主进程里以宿主权限运行，install、update、篡改、持久化、热重载这几条路径上没有签名、 完整性校验、来源，也没有确认闸门；!!js 配置在加载期就是宿主级 RCE， 而这个标签是官方 cordis 教程明文教的。xiejin77 在 Discussion #587 上独立走到同一处， 他补的是时序：插件能在 boot 期改写 harness 的配置树（sandbox mode、approval policy、凭据）， 时间点在任何运行时防护激活之前，而 dsh plugin add <pkg> 字面上就是 pnpm add <pkg>。 这一章从头到尾在做的事，落点正是第二条轴：cordis_define 加 cordis_run 挂上去的那个插件，和任何一个第三方插件一样在宿主进程里、以宿主权限跑， 只不过作者是模型。审计的头号风险和本章的前提是同一件事，区别在于这里是从里面看的。

边界两位作者自己都划了。模型写的插件要能跑起来，会话先得挂在 cordis 这个 preset 上， 而那份 yml 开头的 TRUST 注释已经把话说在前面：挂在这个 preset 上的会话，请当 shell 权限对待， 和上面那句"bash 级别的信任"是同一个意思。动态 package 只活在这个进程的内存里，不落盘也不改配置， 重启就没了。官方落地页写的是「在内存中试验」，工具目录写明额外工具活到 stop、undefine 或重启。 内测用户 @jiayuan_jy 把这件事叫「自进化软件的雏形」，下一句立刻补上「也还不能自动沉淀成一个永久插件」。 宝玉 @dotey 的反驳更短： 插件要么一次性扔掉，要么要设计、验证、维护，不是现在模型能力可以自进化的。 要触发插件这条轴上的事，还得受害者自己去跑 dsh plugin add， 它不是零点击的远程 RCE。Fz0x00 另外专门列了 dsh 已经做对的几项， pnpm 的 registry integrity、0600/0700 的文件权限、特权 RPC 的 loopback pinning， 报告称它们是 real mitigations。

所以上面那段横向对照的结论一个字不用改，只是从判断变成了有出处的判断。 命令执行这条轴上 dsh 手里有内核给的东西，packages/sandbox 里那层 Landlock 与 seatbelt 是真的，同一份审计管这一半叫 production-grade。 模型现场写进本进程的代码这条轴上，dsh 是这份审计的头版，比 MCP 那种把可执行扩展放到进程外的做法差。 完整的账在 横向对照 那一页的 §A.6。

mini 版本刻意省掉的东西：

  • 真的另一个 realm。我们用 new AsyncFunction(...) 加参数遮蔽来模拟沙箱全局； 真实实现是 node:vm 的 createContext，还额外打了一个 dual-realm instanceof 补丁：只改 vm 侧构造器的 Symbol.hasInstance， 让 x instanceof Array 对 vm 值和宿主值都成立，宿主 intrinsics 一个不动。 没有这个补丁，跨边界传进来的参数、事件、服务返回值全都会在类型判断上诡异地失败。
  • 跨 realm 的 JSON 物化。动态工具的 schema 和注解要跨 realm，真实实现用的是迭代式克隆与 schema 归一化 （显式工作栈，没有递归），所以深层声明受内存限制而不受调用栈限制； 带有 JSON 不可见键的记录、被子类化或装饰过的 schema 数组，在归一化之前就被拒绝。
  • 浏览器那一半。整个 cordis-client-runner：approval 往返、按 (id, rev) 收敛的加载、 slot 的遮蔽优先级、渲染崩溃的两路上报（回给模型一份，页面自己留一份）。
  • @pluginId 注入。tool-cordis 在 agent/pre-step 瀑布上挂了一个监听器： 用户消息里写 @dyn-3，它就把那个 plugin 的当前状态渲染成一条 user message 追加进这个 step。 这是第 4 章的瀑布在真实产品里的一个典型用法。
  • 失败的可诊断性。真实报错会附上出错的源码行与插入符，还会按启发式判断你是不是写了 TypeScript （只检查出错那一行里有没有 as，否则一个描述字符串里的 " as " 就会误导出一条错误建议）。

三个值得偷走的设计

要自己写一个 harness，只从这本书里带走三样东西的话，我会挑这三个。它们都不需要 219 个包。

一、用 surfaceOp 折叠出模型视图。 会话日志只追加，永不修改；每一条会产生消息的事件记录自己的 surfaceOp； 模型看到的历史是沿着这些标记折叠出来的一个投影。 压缩于是不再是破坏性操作：一次 compaction 只追加一条 replace， 把被它遮蔽的节点从投影里去掉，原始事件仍然躺在日志里可查、可导出、可重新投影。 审计、fork、时间旅行、"模型可见即已记录"这条不变量，全是它的推论。 只有三种事件类型能进入这个表面（user/message、assistant/message、tool/result）， 所以一个 chunk、一个 turn 边界"正确地不在其中"。 见 packages/core/session/src/surface.ts 与 packages/core/session/src/index.ts 的 deriveMessages()。

二、辅助状态只进日志，不进上下文。 todo_write 每次调用都把整份列表作为一个 todo/write 事件追加进会话日志， 当前列表就是最后一条这样的事件（重放时 last-write-wins）。 而 todo/write 不在上面那三种表面事件类型里，它永远不会变成一条模型消息。 计划、待办、目标于是有了持久化、有了历史、有了 UI，却不占用任何上下文预算， 压缩时也不和真正的对话内容抢空间。 把 todo 列表塞回 system prompt 里反复重发的做法，是在为一个本可以零成本的功能付 token。 见 packages/todo/tool-todo/README.md 与上面那份 SURFACE_EVENT_TYPES。

三、给模型读的东西一律生成，再闸住新鲜度。 API catalog、client slot catalog、工具目录，全部由 AST 扫描生成， 再由 verify-cordis-api / verify-client-catalog 之类的脚本在 CI 里重新生成一遍并比对， 有 diff 就失败。配套的是提示词层面的逐字断言：system prompt 的组装测试直接 expect(render(...)).toBe('…') 比对整串文本，改一个字就红。 这两件事治的是同一个病：模型读到的描述和代码的真实行为悄悄分叉。 §9.2 那张"四个版本的工具名"是这条纪律的反面教材，手写散文没有闸门，于是它是唯一漂走的那个。

下一页：横向对照

这本书从头到尾只讲一个 harness。哪些设计是 dsh 的选择、哪些是所有 harness 都得这么干， 要把别的实现摊在旁边才看得出来。附录 横向对照：Pi、Claude Code、Codex、OpenCode、omp 把前九章的每个机制逐条对齐，也收着一些 dsh 自己不太好意思讲的细节， 比如它那个多 provider 适配层依赖的是 Pi 的 @earendil-works/pi-ai。 那一页比的是架构，不是效果。

效果这件事目前谁都没有数据。同一个 HN 线程里 flaburgan 问的就是这个：没有人做过同模型、同 prompt、 跨 harness 的质量对比。这本书也没做。所以本书里所有"更好"的说法，都只针对结构，不针对结果。

同一条线程里还有一句更短的比较，217 写的：「if it's not better than omp im not trying it」。 omp 是我自己每天在用的 harness，也是这本书唯一被人拿来当过尺子的东西，所以这句要单独交代。 它和 dsh 还算亲戚：omp 是 Mario Zechner 的 pi-mono 的下游 fork，而 dsh 的模型层依赖 Pi 的 @earendil-works/pi-ai。

mini-dsh 写完、两边的源码和文档都翻过一遍之后，我能落到纸上的差别是这些。 dsh 有而 omp 没有的：agent loop 可以整个换掉（omp 的循环由 @oh-my-pi/pi-agent-core 硬编码持有， 扩展只能拦事件、改消息、steer）；命令执行底下有一层 OS 内核沙箱（只覆盖这一条轴， 插件那条轴上的审计见 §9.6，全文在 横向对照 的 §A.6）；子 agent 可以是外面的 claude 或 codex 进程；还有第 8 章那个 presentation 折叠，一行 preset 把整张工具面收成一条代码入口， 而 omp 的 eval 是与另外 30 个并列的一个工具，不动工具面。 omp 有而 dsh 没有的：snapcompact 把要丢的历史用像素字体画成 PNG 位图交给视觉模型，不调 LLM，也不联网； 性能路径是 Rust N-API；会话是一棵带 rewind 和 checkpoint 的 entry 树， 被放弃的探索分支留在盘上；记忆可以落到本地 SQLite 加向量召回；30 多家 provider 带多凭据轮询； 还有一个真正的 TUI。

逐行的版本在 横向对照：Pi、Claude Code、Codex、OpenCode、omp 那一页。 217 那句问的是效果，这本书答不上来，它从头到尾只量了结构。

读完这九章，你手上应该有两样东西：一个能跑的 mini-dsh，以及看到一个 harness 时问得出来的三个问题： 你的工具表能在运行时被写入吗，你的压缩是破坏性的吗，你的 todo 列表占上下文吗。
